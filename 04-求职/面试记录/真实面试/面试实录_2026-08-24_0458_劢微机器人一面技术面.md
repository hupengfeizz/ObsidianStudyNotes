### Q03–Q09 · PV 辅助监督：被追问 4 分钟，最后被定性为「基本操作」 `05:03:29` – `05:09:31`

> **这是本场最长、也最失败的一段。值得逐帧复盘。**

**面试官的追问链**
1. 「辅助监督具体怎么实现呢？」
2. 「意思是你们是基于 BEVFusion 改的？」
3. 「计算 loss 的时候，把雷达检测的结果反投影到图像上，是这意思吧？」
4. 「**他正常你标注的时候，就已经反投影过去了呀**」「你不可能图像标一遍、雷达又标一遍吧？」
5. → **「这个不叫优化呀，这就基本操作呀，我觉得。」**
6. 「那你们怎么标注的嘛？」
7. 「图像上那个框肯定不需要标嘛，对不对？」→「那不就是直接反投影过去就行了吗？**那这个叫什么优化呢？**」

**你的回应轨迹**
- 前 3 分钟一直在解释「3D 标注反投到各个相机」这件事本身——**而这正是面试官认为「本来就要做」的部分**。
- 直到 `05:06:33` 才说出关键的一句：「它是进行一个反投影，**加上一个检测头**……会接一个轻量的检测头，比如 2D 的检测头，来作为一个辅助 loss，来监督这个 2D 的特征提取。」
- 但已经晚了——面试官的「这不叫优化」已经说出口，后面又花了 3 分钟在澄清「2D 框加在哪里」「是在 BEV 空间之前还是之后」。

**问题在哪**
- ❌ **方案是对的，是表达把它讲丢了。** 你把 90% 的时间花在「反投影」上，而反投影确实是标注复用的常规操作；**真正的创新点是「在图像 backbone 后面挂一个轻量 2D 检测头做辅助 loss」**，这句话你压到最后才说。
- ❌ **面试官的质疑其实给了你最好的切入口**——他说「标注的时候就反投过去了」，你应该立刻接：「**对，反投影确实是现成的，正因为现成，这个方案才划算**——我们没有增加任何标注成本，只是把已有的 2D 真值利用起来，在图像 backbone 后面加了一个轻量头做辅助监督。」
- ❌ 中间还出现了一次理解错位：面试官说「图像上它输出的也是 3D 框嘛」，你说「不是不是吧」，然后绕了很久。**其实他的意思是「相机支路最终参与的是 3D 输出」，你应该直接说「相机支路的最终输出确实是 3D，但辅助头是挂在 BEV 之前的 2D 特征上的」——一句话就解决了。**

**该怎么答（30 秒版，第一句就要给要害）** ✅
> 「核心不是反投影，**反投影是现成的、零成本的**——我们的 3D 真值本来就要投到各相机上。
> **优化的点是：在图像 backbone 之后、进 BEV 之前，挂一个轻量的 2D 检测头**，用这些反投得到的 2D 框做**辅助 loss**。
> 为什么要这么做：BEVFusion 的链路很长——图像 backbone → DepthNet → LSS 抬升 → BEV 融合 → 检测头，而**检测 loss 只作用在 BEV 空间**，回传到图像 backbone 时梯度已经衰减得很厉害，图像特征的判别力上不去，表现出来就是误检。
> **收益是白拿的**：不增加标注、**推理时这个头直接摘掉、零算力开销**，只在训练期生效。落到指标上，凭空误检专题通过率提升 **5.1%**，泊车误检率降 **3.7%**。」
>
> 💡 **三个关键顺序**：① 先说「不是反投影，是加了个头」堵住「这是基本操作」的质疑；② 再说为什么需要（梯度衰减）；③ 最后说白拿的收益（零标注成本 + 零推理开销 + 数字）。

`#致命` `#方案对但讲丢了` `#必背`

### Q12 · 低速速度估计失效怎么解决？ `05:10:30`

**你当时怎么答的**
> 低速场景比如等红绿灯时前车缓慢移动、又停又移动，模型容易把动的检成静止。速度可能在零点几米每秒。我们针对 loss 做优化，原来是 L1 loss，比较粗，对零点几米每秒这个范围收敛性不够好，所以改用 **Smooth L1**，改善零点附近的收敛性。然后跟动静属性进行**联合约束**——速度值输出 0 的时候，动静 tag 也绑定输出静止，这样提高整个速度动静的检出稳定性。

**评价**
- ✅✅ **答得完整、有场景、有机制。** 等红绿灯前车走走停停这个例子很具体，L1→Smooth L1 的动机说清楚了，联合约束也讲对了。**这是本场答得最好的技术题。**
- 🟠 缺 beta 取值的依据（位置标注误差 10cm ÷ 0.1s → 速度噪声 ~1 m/s，所以 beta 取 1 量级）和结果数字（专题通过率 +3.5%）。

`#低速` `#答得好`

### Q13 · 多帧点运动补偿怎么做的？每个点具体怎么做？ `05:14:32` – `05:18:33`

> 面试官追问了**四轮**：「能不能讲具体，当前车和对向车的运动补偿怎么算的」→「能不能讲具体一点」→「它有很多点，每个点你都要做运动补偿对不对」→「每个点具体是怎么做的」

**你的回应轨迹**
- 第一轮：先讲**他车**（拖影、剔除、根据标注预测位置做补偿），**自车讲了一半被打断**
- 第二轮：还是讲他车（卡尔曼滤波预测目标轨迹）
- 第三轮：终于说到点上——「**雷达扫过去，每个点有不同的时间**」
- 第四轮：「自车的话通过 IMU 的自车运动信息，通过**刚体变换**模型把点云投到当前帧坐标系」「**利用每个点的时间戳**」

**评价**
- ✅ **最终答案是对的，而且「每个点时间戳不同、要逐点补偿」这一点答得很准**——这是激光雷达**运动畸变去除（deskew）**的核心，很多人不知道。
- ❌ 但**又是先讲目标、后讲自车**，被追问四轮才说完整。**这是连续第四场同一个顺序错误**（普渡、优奇、无人机场、本场）。
- ❌ 「用卡尔曼滤波预测目标轨迹来做运动补偿」——这个说法在**离线生成训练真值**的场景下是不准确的。生成深度真值时用的是**标注框轨迹**，不需要卡尔曼预测；卡尔曼是在线跟踪时用的。**两个场景混了。**

**该怎么答（一次说完，不给追问的机会）** ✅
> 「分三层，从精确到不精确：
> **第一层 · 逐点去畸变**——激光雷达一圈 100ms，**每个点的时间戳不同**，扫到不同方位的时刻不一样。所以第一步是用 ego pose 把每个点按自己的时间戳补偿到扫描起始（或结束）时刻，这一步叫运动畸变去除。20m/s 的车在一圈内能跑 2 米，不做这一步点云本身就是歪的。
> **第二层 · 自车运动补偿**——把 t−k 帧整帧点云从当时的车体系变换到 t 帧车体系：`P_t = T_t⁻¹ · T_{t−k} · P_{t−k}`，就是一个刚体变换。位姿来自定位模块。对**静态环境**这一步是精确的。
> **第三层 · 动态目标补偿**——静态对齐后运动目标还有拖影。因为我们是**离线生成训练真值**，可以直接用**标注框轨迹**：落在 t−k 帧标注框内的点，按该目标的标注位移搬到 t 帧的框内。补偿后仍然落在框外或偏差超阈值的点直接丢弃——**宁可稀疏，不要错误的深度真值**。
> 在线跟踪那边才用卡尔曼，这两个场景是分开的。」

`#运动补偿` `#连续第四场顺序错误` `#必背`

**必须背下来的标准答案** ✅

**智能指针**
> 「智能指针是 C++11 引入的 **RAII 包装**，用来自动管理动态内存的生命周期，避免手动 new/delete 导致的内存泄漏和悬空指针。三种：
> - **`unique_ptr`**：独占所有权，不可拷贝只可移动，**开销和裸指针几乎一样**，是默认首选；
> - **`shared_ptr`**：共享所有权，内部维护**引用计数**，计数归零才析构。代价是引用计数的原子操作开销，而且**会有循环引用问题**；
> - **`weak_ptr`**：配合 shared_ptr 用，**不增加引用计数**，专门用来打破循环引用，用之前要 `lock()` 提升成 shared_ptr。
>
> 实际工程里的原则是：**默认用 unique_ptr，确实需要共享才用 shared_ptr**，因为 shared_ptr 的所有权关系不清晰，容易写出谁也不释放的代码。」

**纯虚函数**
> 「纯虚函数是**只声明不实现**的虚函数，写法是 `virtual void foo() = 0;`。
> 作用：
> - **含有纯虚函数的类是抽象类，不能实例化**，只能被继承；
> - **强制派生类必须实现它**，否则派生类也是抽象类；
> - 它定义的是一个**接口契约**——基类规定「你必须能做这件事」，但不管你怎么做。
>
> 典型用法就是接口基类。**这个概念我在项目三里实际用过**：评测防护网的 checker 框架就是这个结构——一个基类抽象出『匹配 → 判定 → 统计』三段流程，`check_fp` / `check_fn` / `check_unstable` 这些是纯虚接口，每种问题类型的 checker 各自实现，加一个新问题类型只需要新增一个子类。**虽然我是用 Python 写的，但设计模式是一样的。**
>
> 另外要注意：**基类的析构函数应该声明为 virtual**，否则通过基类指针删除派生类对象时，派生类的析构函数不会被调用，会泄漏。」
>
> 💡 **注意最后那个 checker 框架的类比——这是你把「不会 C++」转化成「我懂面向对象设计」的最好方式，而且是真事。**

PV 辅助监督这件事，**方案本身是有含量的**（零标注成本 + 零推理开销 + 5.1% 的收益），但你花了 4 分钟解释「反投影」，把创新点（挂轻量 2D 头做辅助 loss）压到最后才说，结果被面试官定性为「这不叫优化」。

**根因**：你讲方案的顺序是**按实现步骤讲**（先标注、再反投、再加头），而面试官需要的是**按价值讲**（我加了什么 → 为什么需要 → 白拿了什么）。

**改法**：所有方案的第一句话必须是「**我加了/改了什么**」，不是「我们的数据是怎么来的」。

#### 问题三 · 答案自己说过，但没有连起来

本场最典型的是 Q19：你在 `05:06:15` 说过「**在世界坐标系上进行标注**」，而这就是 `05:27:04` 那个问题的全部答案。中间只隔了 20 分钟，你没有连起来。

## 五、为什么这场能过（重点）

> **这是全轮最值得研究的一节。**

### 5.1 分数与结果的背离

### 5.2 这场能过的四个真实原因

**① 场景是降维的，面试官自己说了**
> 「无人叉车主要在室内……**当然比那种自动驾驶肯定要简单，因为它的速度不会很快**。」

速度慢 → 你在华为花最多力气的两件事（速度估计失效、中远距深度）在这里都不是主要矛盾。**你的经验对这个场景是超配的。**

**② 他要的是「全都会」，不是「懂得深」**
> 「在我们这里你需要**都要会**——比如模型训练，还有一个它的部署，**都要会**。」

这句话解释了全场的提问逻辑：**他问 C++ 不是要考你八股，是在确认你能不能碰部署**。你答不出智能指针，但你在自我介绍里说了「Jetson Orin 和 RK3588 板端部署全链路自己做的」——**对他来说，后者比前者重要得多**。

**③ 你的实习经历在这家是决定项，在别家只是加分项**

这是最关键的一点。**同一段经历（项目四：数据 → 模型 → Jetson Orin / RK3588 部署全链路），在不同公司的权重完全不同：**

| 公司类型 | 这段经历的权重 |
|---|---|
| 大厂 / 有专门部署组 | 几乎无关，甚至显得「不够专精」 |
| **要求全栈的中小公司** | **决定性**——它证明你一个人能把链路走完 |

而你在 8/23 初筛场**完全没提这段**，在 8/20 普渡场也是被追问到才提。**你把自己最匹配中小公司的那张牌，长期压在手里没打。**

**④ 华为车 BU 量产 BEV 的背景，对这家是稀缺的**

对方明说「你说的这套 BEV，我们其实也要用到这一套」——他们正要从零建这套能力，而你是从量产线上下来的。**这个信息差本身就值一个 offer。**

### 5.3 从这场能提炼出的判断方法

**面试开场三分钟内，先判断这家属于哪一类，然后决定打哪张牌：**

| 信号 | 这家要的是 | 你该主推 |
|---|---|---|
| 「我们没有专门的部署组 / code 自己写」 | **全栈能干活** | 项目四全链路 + Jetson/RK3588 + 量化部署 |
| 「我们也要建这套 BEV / 我们刚开始做」 | **成熟经验迁移** | 量产踩过的坑 + 评测防护网 + 数字 |
| 「我们在做端到端 / VLA / OCC」 | **前沿方向匹配** | BEVFormer 被 pass 的教训 + 端到端并入的参与 |
| 「团队规模大 / 分工明确」 | **专精深度** | 三个专项的完整闭环 + 原理深挖 |

**本场你打对了牌（自我介绍里的实习全链路），但是无意识打对的**——因为你没有在反问环节把它再强化一遍。下次要**有意识地打**。

### 5.4 但也要清醒：过了不代表答得好

这场如果换一个把 C++ 当门槛、或者会深挖原理的面试官，**IMU、速度真值、PV 辅助监督这三题足以让你出局**。

**已经确认的事实是：二面业务面也过了、准备发 offer。** 所以后续对这家的重点不是复盘失分，而是：
- **入职后会直接面对部署工作**（对方明说了训练和部署都要会），C++ 和板端这块**必须在入职前补起来**，否则进去就露馅；
- 人形机器人那条线要上 **VLA**，如果你对这个方向有兴趣，可以在谈 offer 时争取参与。
