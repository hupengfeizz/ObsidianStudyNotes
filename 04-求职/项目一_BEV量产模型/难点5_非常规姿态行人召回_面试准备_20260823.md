# 难点五:非常规姿态行人召回偏低 —— 面试准备

> 简历定稿口径
> **难点:** 非常规姿态行人召回偏低——坐姿、弯腰、推车等姿态行人的召回明显低于站立行人。
> **优化方案:** 小目标正样本补偿——针对非站立姿态行人 BEV 占格少、自适应高斯半径触底的问题,调整 heatmap 标签生成的最小半径策略,提升坐姿、弯腰等姿态行人的召回。

---

## 一、口头展开的标准版本(60 秒)

**顺序:数据在前,模型在后。** 数据是主要手段,也是你最能守住的部分。

> 这个问题是评测里按姿态细分之后暴露出来的:站立行人召回正常,但坐地、蹲坐、弯腰、推车这几类明显低一档。
>
> 我们从两侧一起治:
>
> 一侧是数据。针对这几类姿态做专项采集,把场景清单定下来——路沿坐地、蹲下系鞋带、弯腰捡东西、推婴儿车、推行李箱这些,同时在标注要求里把姿态属性带上,这样评测才能按姿态分档看。采完把这类样本在训练集里的占比提上来。
>
> 另一侧是模型。这类目标在 BEV 上占的格子本来就少,CenterPoint 的高斯半径是按目标尺寸自适应算的,算出来会顶到下限,heatmap 上的正样本区就只剩一两格,监督信号太弱,学不动。所以调了标签生成里的最小半径策略,给这类小足迹目标做正样本补偿。

**收尾一句(把战场留在自己手里):**
> 效果上主要看两个:该姿态档的召回有没有起来,以及整体 mAP 和误检有没有被带坏——这个参数是配平性质的,调过头会涨误检。

---

## 二、机理链(能自己接下来的部分)

```
非站立姿态(坐地/蹲坐)
  → 3D 框俯视足迹小(0.6×0.6 量级)
  → BEV 特征图上只覆盖一到两格
  → CenterPoint 的 gaussian_radius 按目标尺寸自适应计算,算出来触底
  → 半径被 clamp 到 min_radius(默认 2)
  → heatmap 上高响应区极小,正样本严重不足
  → Gaussian Focal Loss 下这类目标贡献的梯度太弱
  → 学不动 → 推理时峰值起不来 → 过不了阈值 → 漏检
```

### 关键概念:标注 ≠ 标签

- 标注员交付的是 **3D 框**(中心、长宽高、朝向、类别、属性)。
- 网络输出的是 **heatmap + offset + 尺寸 + 朝向 + 速度** 多个分支。
- 两者格式不匹配,所以训练时有一步 **target assignment**:把框现场编码成各分支的真值。
- **高斯半径就活在这一步里,不在网络结构里,推理时根本不存在。**

### 半径怎么算的

CenterPoint 沿用 CenterNet 的 `gaussian_radius(det_size, min_overlap)`:

- 输入是目标在 BEV 特征图上的长宽,和一个期望的最小 IoU(配置里叫 `gaussian_overlap`,常见 0.1)。
- 解三个二次方程(预测框外接 GT、内接 GT、部分重叠三种情况),取最小解。
- 物理含义:**半径内的任意一格作为中心画出来的框,和真值框的 IoU 都不低于 `min_overlap`。**
- 最后 `radius = max(min_radius, int(radius))`,`min_radius` 常见配置是 2。
- 画高斯时 `sigma = (2*radius+1)/6`,用 `maximum` 叠加进 heatmap(重叠目标取大)。

### 为什么调半径会有收益

heatmap 用的是 **Gaussian Focal Loss**:峰值那一格是正样本,**周围格子按高斯值做软负样本,惩罚权重是 `(1-gt)^4`。**

- 半径变大 → 峰值周围的软负样本惩罚被削弱 → 网络更容易在这片区域出高响应 → **召回上升。**
- 代价:高响应区扩大 → **中心定位精度下降、误检上升。**

**所以这是一个配平参数,不是解决方案。** 单独调它的收益一般在一个点以内,真正把召回拉起来的是数据侧。

### 真正该动的旋钮

| 旋钮 | 作用 | 风险 |
|---|---|---|
| `min_radius` 下限 | **专管小目标**,把触底的那批捞起来 | 调大会波及所有小目标(锥桶、自行车) |
| `gaussian_overlap` | 全局放大半径 | 影响所有类别,大目标也变松,不推荐 |
| 按 task/类别分开设 | CenterPoint 的 head 是分 task 的,可以只动行人那组 | 需要确认配置结构支持 |

**面试里主动说"我们动的是下限,不是全局 overlap",显得你知道分寸。**

## 三、数据侧(你最硬的部分,多讲)

### 为什么 CBGS 不解决这个问题 —— 这是加分点

- **CBGS 解决的是类间不平衡**(行人 vs 卡车 vs 锥桶),按类别做重采样。
- 姿态问题是 **类内长尾**——都是 pedestrian 这一类,CBGS 眼里它们是同一个类别,采样权重一样。
- 所以 CBGS 跑得再好,坐地行人在训练集里还是那么少。**必须靠专项采集 + 属性标注,才能把这一档单独提出来。**

> 这一条如果面试官问"你们不是有 CBGS 吗",直接甩这个答案,非常干净。

### 专项采集怎么做

- **场景清单先定死**:路沿坐地、蹲下系鞋带、弯腰捡东西、蹲着看手机、推婴儿车、推行李箱、推购物车、推共享单车。
- 采集要覆盖不同距离、不同方位角(尤其近距侧向)、不同光照。
- **标注要求里加姿态属性字段**,否则评测没法分档,也没法做定向采样。
- 采完做数据验收:属性字段填得对不对、框打得准不准、场景比例够不够。
- 回灌训练集,调这一档的采样比例。

### 标注上的细节(被追问时能顶两层)

- 3D 框仍然是外接立方体,姿态变化主要体现在 **高度降低、长宽比变化**。
- 坐地行人:高度可能从 1.7 掉到 1.0 左右,俯视足迹大致不变或略小。
- 弯腰行人:高度降低,但 **俯视足迹可能变大**(身体前倾展开)。
- 推车行人:人和车是否合并成一个框、还是分开打,这是标注规则里要明确的一条,直接影响评测口径。

> ⚠️ **这里有个诚实的技术风险,先说给你:**
> "非站立姿态 → BEV 占格少"这个因果在 **坐地、蹲坐** 上成立,在 **弯腰、推车** 上不完全成立(弯腰的俯视足迹可能反而更大)。
> 如果面试官较真问"弯腰行人俯视投影不是更大吗",**别硬撑**,照下面这样答:

> 「对,这几类的成因不完全一样。坐地和蹲坐主要是足迹小、半径触底;弯腰和推车更多是形态跟训练集里主导的站立姿态差异大,加上样本量本来就少,属于类内长尾。所以数据侧的补充对这几类都有效,半径策略主要是把足迹小的那批捞回来。」

**这句话答出来,比强行统一归因加分得多。**

## 四、评测侧

- 按姿态属性分档统计各档的 **召回 / AP**,和站立档对比。
- 收益验证看三件事:
  1. 目标姿态档的召回提升了多少;
  2. **整体 mAP 有没有掉**(半径调大最容易伤定位精度,NDS 里的 mATE 会体现);
  3. **误检有没有涨**(尤其是行人误检,半径放松最直接的副作用)。
- 分档评测的前提是标注里有姿态属性 —— **所以数据侧和评测侧是一件事的两端,这个逻辑闭环讲出来很扎实。**

## 五、危险追问清单 + 应对

### A 类:数字类(你答不上来,也不该编)

| 追问 | 应对 |
|---|---|
| 最小半径具体调到几? | 「这个参数跟训练配置绑在一起、按车型维护,具体数值我得回去确认。逻辑上是把下限从默认的 2 往上抬一档。」 |
| 提升了多少个点? | 「这类配平参数单独的收益一般在一个点以内,真正把召回拉起来的是数据侧的补充,两条一起看这一档的召回是有明显改善的。」 |
| 专项样本加了多少?占比调到多少? | 「是跟着采集批次滚动调的,具体比例我记不准了。」 |
| 每个车型都单独调过吗? | 「配置是按车型维护的,具体是不是每个车型都单独调过这一项,我得回去确认。」 |
| gaussian_overlap 设的多少? | 「默认那档,我们没动全局 overlap,只动了下限。」 |

**统一模板:先把确定的部分说满,再标出不确定的那一小块。** 不要一上来就说"我不确定"。

### B 类:实现类(方向对了就行,不必假装写过)

| 追问 | 应对 |
|---|---|
| 这段代码在哪? | 「在 target assigner 里,标签生成阶段,`gaussian_radius` 这个函数,大概三十行。跟网络结构无关,推理时不走这段。」 |
| 你自己改的? | 「方案是组里讨论定的,实现是负责那个模块的同学做的,我这边负责问题定位、数据准备和效果验证。」 |
| 高斯核怎么画的? | 「以中心那一格为峰值,sigma 由半径推出来,往外二维高斯衰减,多目标重叠的地方取大。」 |

### C 类:延伸技术题(答得上就是加分)

| 追问 | 答法要点 |
|---|---|
| 为什么用 heatmap 不用 anchor? | anchor-based 对小目标要预设尺度和比例,行人这类尺度单一但姿态多变的目标匹配率低;heatmap 是无锚的,只回归中心,对小目标更友好,而且省掉 anchor 匹配的超参。 |
| 半径调大为什么会掉定位精度? | 高响应区变大,峰值不够尖锐,NMS 或 top-k 取出来的中心容易偏,offset 分支要补的偏移变大。 |
| 除了调半径还有别的解法吗? | 提高 BEV 分辨率(代价是算力)、按类别设不同半径、用 soft label 或 IoU-aware 加权、图像分支上做高分辨率小目标增强。**说得出多个方向,显示你知道半径只是其中一条。** |
| 只调行人会不会影响别的类? | 如果 min_radius 是全局的,会波及所有小足迹类别(锥桶、自行车),所以要看 head 的 task 分组能不能单独配;这也是为什么要盯整体 mAP 有没有掉。 |
| 为什么不直接降检测阈值提召回? | 降阈值是推理侧的事,召回上来误检同步上来,而且不解决"根本没学出响应"的问题——**这个目标在 heatmap 上压根就没有峰值,降阈值也捞不出来。** |

> 最后那条是杀手锏。**它把"标签监督不足"和"推理阈值"这两件事分得很清楚,能答出来的人不多。**

## 六、绝对不能说的

| 内容 | 原因 |
|---|---|
| 相机装在 C 柱 / 具体安装位置 | 前司硬件信息,且会引来 FOV、各车型参数这类你守不住的追问 |
| 适配了多少款车型 | 同上,而且会被追问"车型间怎么泛化" |
| 具体的传感器型号、线束数、分辨率 | 同上 |
| 数据集规模、路测里程 | 前司敏感信息 |
| 任何具体参数值 | 你不确定,编了会被拆穿;而且这是唯一真正有商业价值、值得被"套"的东西 |

**C 柱那层只在口头、只在他追问"为什么会占格少"的时候说,说法是「某些车型侧向相机的安装位置比较特殊,近距的俯角比较大」。说出去就消失,不落纸面。**
