### 真实数据流（按材料重绘）

```

                    ↓

                    ↓

鱼眼 4 路 ──→ ResNet-Auto-FPN2 (768×512 → 128ch，独立权重) │
                    ↓                                     │
```

**三个值得注意的点**：

### 为什么把高度拍平（原理不变）

1. 俯视图下目标不重叠，二维平面足够表达空间关系
2. 保留 z 维会让特征图变 3D，计算量涨一个数量级

代价是丢失高度信息，所以检测头单独回归 `height`（材料里确实有这个分支，1 通道）。

### 分辨率与算力（可现场推算）

```
±51.2m、0.8m 网格 → 128×128
±51.2m、0.4m 网格 → 256×256   面积 4 倍 → 后续卷积算力 4 倍
```

**你们用的是 0.4m**，属于量产远距的细网格档位。

### 口语（面试用，只说量级）

> 具体的网格范围和分辨率属于内部配置，我不方便说准确数。量级上纵向覆盖前后一两百米、横向几十米，网格是 0.4 米这一档。分辨率提一倍，BEV 特征图面积就是四倍、后面卷积算力也是四倍，所以这是很贵的决定。

## 0.4 LSS 三步全流程 ★★★【Splat 部分重写】

### 0.4.1 Lift 在解什么（不变）

单目 3D 的困难是"一个像素对应一条射线，缺深度"。三条路：IPM（只在平地成立）、单目深度+反投影（估错就彻底错）、**LSS（不选一个深度，把所有可能深度都保留，用概率加权）**。

### 0.4.2 Lift：外积怎么得到视锥特征【改数】

图像经 Backbone + FPN 后：`1280×704 → 多尺度 [128,256,512] → FPN 融合 256ch`

**DepthNet（针孔，`lite_decoder`）**：

```
Conv2d(128 → 128, k=3) + BN + ReLU
Conv2d(128 → 101, k=3) + BN + ReLU
                  ↑
        100 深度 bin + 1 dustbin
```

| 参数 | 材料真值 | 原文写的 |
|---|---|---|
| 深度 bin 数 | **100（+1 dustbin）** | 118 |
| 深度范围 | **0 ~ 60 m** | — |
| 离散化 | **UD（均匀），~0.6m/bin** | 说"量产常用 LID" ⚠️ |
| 空间分辨率 | 160 × 88 | — |
| 上下文通道 | **32**（`Conv1x1(256→32)`） | 64/80 |

> **🆕 dustbin 是原文没有的概念**：第 101 个通道表示"不在 0~60m 这个范围内"。softmax 之后**去掉 dustbin 通道**再做外积——超出量程的像素因此不会往 BEV 里贡献特征。这是一个很实用的设计，被问到"60m 以外的像素怎么办"时可以答。

**外积**：

```
depth_probs = softmax(depth_logits)[:, :-1]      # 去掉 dustbin
image_features = Conv1x1(fv_featmap)              # (B, 32, H', W')
frustum = depth_probs * image_features            # (B, 32, D, H', W')
```

**物理含义（不变）**：每个像素的语义特征按深度概率"撒"到这条视线上的 D 个位置。三种情形对应三种下游失效（尖锐位置错 → 位置跳变；平坦 → 远距漏检；多像素同时错到一处 → 凭空误检）。

### 0.4.3 Splat：拍扁怎么发生的 ⚠️【重写】

> **原文写的是「pillar + sum pooling + cumsum trick」，这是 LSS 原论文的做法。**
> **材料显示你们的实现不是这样。**

**实际实现（材料原文）**：

```python
# Step 1: Softmax 归一化
depth_probs = F.softmax(depth_logits, dim=1)   # (B*n, D+1, H', W')
depth_probs = depth_probs[:, :-1]              # 去掉 dustbin 通道

# Step 2: 外积（深度概率 × 图像特征）
image_features = Conv1x1(fv_featmap)           # (B, 32, H', W')
frustum = depth_probs * image_features         # (B, 32, D, H', W')

# Step 3: 高度池化（沿 H 维度 mean）
frustum_feats = frustum.mean(dim=3)            # (B, 32, D, W')

# Step 4: Grid Sample → BEV 网格
bev_featmap = F.grid_sample(frustum_feats, grid_map)
```

配置：`weighted_aggr: False（标准 LSS 平均池化）`、`save_memory: True（分块处理）`

**和 LSS 原论文的区别**：

| | LSS 原论文 | **你们的实现** |
|---|---|---|
| 拍扁方式 | 点分配到 pillar（z 不参与索引） | **沿图像 H 维度做 mean** |
| 聚合 | **sum pooling** | **mean（平均池化）** |
| 落格子 | 排序 + cumsum + 区间差分 | **grid_sample 重采样** |
| 几何映射 | 运行时计算 | **预计算 grid_map** ← 重要 |

> **🆕 关键发现：`几何投影（预计算 grid_map）`**
> 材料里明确写了几何映射是**预计算**的。这说明「内外参固定 → 映射可离线算」这个核心思想**在你们系统里是成立的**，只是落地形式是 grid_map（供 grid_sample 用）而不是 BEVPoolv2 的索引表。
>
> **这对你的表述是个支撑**——你可以说"视图变换的几何映射是预计算的"，这句是真的。

### 0.4.4 Splat 一步同时干三件事（不变）

统一坐标系（多相机 → 一个自车系）、拍扁、多相机融合。材料里 `MultiViewFusion` 明确写了：zero-padding 空间对齐 → 通道 cat → 3×3 Conv 压到 64ch。

> ⚠️ 注意：**你们的多视图融合是 `cat + Conv`，不是 sum pooling 叠加**。所以"重叠区自然相加"这个说法要改成"重叠区由卷积学习融合"。

### 0.4.5 Shoot（不变）

原论文是轨迹模板打分做规划；检测任务中整段换成 BEV Encoder + 检测头。时序融合不属于原始 LSS 三步（BEVDet4D 之后引入）。

### 0.4.6 白纸默写八步【按实际改写】

```
① 7 路针孔 → Backbone + FPN → 多尺度融合 256ch
② DepthNet(2 层卷积) → 100 bin + 1 dustbin 的深度分布（0~60m，均匀离散）
③ softmax → 去掉 dustbin → 与 Conv1x1 降到 32ch 的上下文特征做外积
④ 得到视锥特征 (B, 32, D, H', W')
⑤ 沿图像 H 维度做 mean 池化 → (B, 32, D, W')   ← 高度信息在这一步没了
⑥ 按【预计算的 grid_map】做 grid_sample → BEV 网格
⑦ MultiViewFusion：多视图 zero-padding 对齐 → cat → 3×3 Conv → 64ch
⑧ 与鱼眼 / LiDAR / Radar 在 MultiFusion 合并 → 时序 → 检测头

训练期旁路：激光投影 → 深度真值 → 监督 ②
离线旁路：  内外参固定 → 预计算 grid_map → 供 ⑥ 使用
```

### 0.4.7 高频追问【改写】

**Q：视图变换怎么加速的？**

`安全说法`（核实前）：

> 视图变换的几何映射是**预计算**的——内外参在车上固定，投影关系可以离线算好，运行时直接查。这一步原本是相机支路最大的耗时项，优化之后基本不再是瓶颈，省下来的时延投给了更重的深度网络。

⚠️ **不要说"BEVPoolv2"这个名字，直到你在 v18 里确认它确实存在。**

**Q：内外参更新了怎么办？**
预计算的 grid_map 要重算。有在线标定的系统需要设计更新机制，一般不每帧重算。

**Q：多个相机的视野重叠区怎么处理？**
多视图 BEV 特征 zero-padding 对齐后 **cat 再卷积**，由网络学习融合权重（不是简单相加）。

## 0.5 深度为什么用分类不用回归 ★★☆【局部改数】

### 三条主答案（不变）

① **深度歧义/多峰** —— 回归会输出"平均脸"（20m 和 80m 双峰 → 回归输出 50m，特征涂进空气）
② **不确定性可表达** —— 分布的熵天然是置信度；LSS 里表现为"不确定时特征自动摊薄"
③ **与 splat 天然兼容** ← 最关键 —— softmax 分布本身就是 splat 的权重，不需要额外造分配核

### bin 划分【改数】

| 方式 | 公式 | **你们用的** |
|---|---|---|
| **UD（均匀）** | `d_i = d_min + i·(d_max−d_min)/D` | ✅ **针孔 0~60m / 100 bin / 0.6m；鱼眼 0~7m / 32 bin / 0.22m** |
| LID（线性递增） | `d_i = d_min + (d_max−d_min)·i(i+1)/(D(D+1))` | ❌ |
| SID（对数） | `d_i = d_min·(d_max/d_min)^{i/D}` | ❌ |

> ⚠️ **原文写"量产长距常改用 LID"，你们实际用 UD。**
> **改后的说法**：理论上远处 bin 该更宽（远处物理上分辨不了，划细是浪费容量），LID/SID 就是这个思路；但工程上 UD 实现简单、部署友好，**在 60m 这个量程内均匀划分（0.6m/bin）的精度损失可以接受**——0.6m 的深度分辨率在 BEV 0.4m 网格下已经够用了。
>
> **这个"够用"的论证很重要**：深度 bin 宽 0.6m ≈ BEV 网格 0.4m 的 1.5 倍，再细也落不到更精确的格子里。**这条能把"为什么用 UD 而不是 LID"答成一个有依据的工程判断，而不是"没想那么多"。**

### 鱼眼的 bin 划分（🆕 补充）

鱼眼近场用 **0~7m / 32 bin / 0.22m**——近处需要更高的深度分辨率，因为泊车场景对近距精度要求高。**两条支路的 bin 是独立配置的**，这本身就是"按需求分配容量"的例子。

### 训练细节

- **dustbin**：第 101 个通道吸收量程外的像素（🆕）
- **软标签、mask 归一化**：材料不可见，保留原文说法但标注「待核实」

## 0.8 前向投影 vs 后向 query ★★☆【补材料证据】

**你们的系统同时用了两条路线，而且材料里有一张现成的对比表：**

| 方法 | 使用相机 | 深度估计 | 几何先验 | 计算量 | 范围 |
|---|---|---|---|---|---|
| **LSS（LiftSplat）** | 针孔 7 路 | **需要（100 bin）** | 强（显式几何投影） | 中 | **远程 0~60m** |
| **Transformer** | 鱼眼 4 路 | **不需要** | 弱（隐式学习） | 高 | **近程 0~7m** |

**算力账（可现场推算）**：

```
针孔 BEV：448 × 224 ≈ 10 万 query
鱼眼 BEV：16 × 16   =   256 query
                    差约 390 倍
```

交叉注意力计算量与 query 数成正比。**10 万 query 的 transformer 在车端不可行，256 个可行。**

> **这是算力约束下的分治，不是最优设计。理想是统一架构。** —— 这句主动说出来。

**鱼眼 transformer 的配置**（面试只说定性，不说数值）：
2 层 Decoder，cross-attention only 无 self-attention；BEV query 是可学习参数 + 位置编码；Image Memory 用 FPN 特征 + 球面坐标 3D 位置编码；有 attention mask 遮挡无效鱼眼区域。

**稀疏 query 系（DETR3D/PETR）**：连 BEV 网格都不构造，计算量与探测范围无关。你们不用是因为 BEV 特征要同时供多个下游任务（检测/跟踪/儿童/近处）用，需要稠密表征。

| 分支 | 通道 | 含义 | 原文有吗 |
|---|---|---|---|
| heatmap | **6** | 中心点热力图（6 类） | ✓ |
| reg | 2 | 中心点局部偏移 (dx, dy) | ✓ |
| height | 1 | Z 坐标 | ✓ |
| dim | 3 | 3D 尺寸 (w, l, h) | ✓ |
| rot | 2 | 旋转 (sin, cos) | ✓ |
| vel | 2 | 速度 (vx, vy) | ✓ |
| **dir_cls** | **1** | **方向分类（前/后）** | ❌ 🆕 |
| movement | 1 | 运动状态（静止/运动） | ✓ |
| **rot_lidar** | **2** | **LiDAR 坐标系旋转** | ❌ 🆕 |
| **close_heatmap** | **6** | **近处专用热力图** | ❌ 🆕 |

**🆕 `dir_cls` 值得单独讲**：`sin/cos` 表示的朝向有 **180° 歧义**（一辆车正着开和倒着开，sin/cos 回归出来可能一样）。`dir_cls` 是一个二分类分支，专门判"前还是后"，用来消歧。

> **这是一个很好的加分点**：被问"sin-cos 解决了周期性，那 180° 歧义怎么办"时，答案就是这个额外的方向分类分支。

**🆕 `rot_lidar`**：另一套坐标系下的旋转输出，配合 `use_lidar_rt: True`。

### 检测类别：6 类（原文写 3 类）

```
CAR, TRUCK, PEDESTRIAN, CYCLIST, HEAD, CONETANK
```

**`CONETANK`（锥桶）在 BEV 模型里也检**——这和你项目二的前视锥桶任务是同一类目标，**可以串讲**：前视做 2D 成排检测给改道意图，BEV 做 3D 单目标检测给位置。

### Loss 构成

```
heatmap loss:          GaussianFocalLoss(reduction='mean')
bbox regression loss:  L1Loss(reduction='mean', loss_weight=0.25)
code_weights: [1, 1, 1, 1, 1, 1, 3, 3, 1, 1]
              [reg_u, reg_v, height, w, l, h, sin_rot, cos_rot, vx, vy]
                                              ↑______↑  朝向权重 3 倍
gaussian_overlap: 0.1
gaussian_sigma:  [-1, -1, 0.6, 0.65, -1, -1, -1, -1]
                 [CAR, TRUCK, PED, CYC, HEAD, CONETANK, -, -]
min_radius: 2
```

**🆕 `gaussian_sigma` 按类别覆盖**：只有 PEDESTRIAN(0.6) 和 CYCLIST(0.65) 手动设了值，其余用默认自适应公式。这是针对小目标的调优——它们在 BEV 上只占 1~2 格，默认的大高斯核会把周围背景标成"半正样本"，稀释真正的峰值。

### 为什么 anchor-free 适合 BEV（不变）

俯视图下目标不重叠 → "一个中心点对应一个目标"成立 → 省掉 3D anchor 的设计与匹配。

### 后处理

Rotated NMS；置信度按类别和距离段设阈值；`export_instance_embeddings: True` 输出实例 embedding 供跟踪用。

## 0.10 多模态融合与时序融合 ★★☆【重写】

> **这两块仍然不是你做的，三段式应答不变。但材料给出了实际做法，被问到时能答得更具体。**

### 融合的实际做法

**MultiFusion 的四路输入**：

| 输入 | 通道 | BEV 尺寸 |
|---|---|---|
| 图像 BEV（LSS） | 64 | 448×224 |
| **鱼眼 BEV（Transformer）** | 32 | **16×16** |
| LiDAR BEV | 64 | 352×224 |
| Radar BEV | 64 | 352×224 |

**融合流程（三种方式混用）**：

```
① 图像 BEV(64) + LiDAR BEV(64) → concat → 128ch
② + Radar BEV → Conv1x1(64→64) → 【逐元素相加】
③ + 鱼眼 BEV  → 靠近处处理 → 【mean 聚合】
```

> **这比原文写的"Concat + Conv 最常用"具体得多**：三路模态用了三种不同的融合方式，而且是按**空间覆盖范围**决定的——同尺寸的 concat，稀疏的相加，局部小块的 mean 聚合。

**可选融合策略**（YAML 里可切 7 种）：concat / conv_concat / gated_fusion_v2 / gated_fusion_v4 / attention_fusion / sk_layer

**LiDAR 与 Radar 先在各自的 UNet 入口处合过一次**（各自 Conv1x1(64→32) 后逐元素相加），然后在 MultiFusion 里 Radar 又叠一次——**两阶段融合**。

### 时序融合的实际做法【改数】

| 项 | 材料真值 | 原文写的 |
|---|---|---|
| **历史长度** | **当前帧 + 2 历史 = 共 3 帧** | "量产典型 4–8 帧" ⚠️ |
| 融合方式 | **CONCAT（通道拼接）** | concat / 加权 / 可变形注意力 |
| 对齐方式 | 历史帧按自车位姿 warp 到当前帧坐标系 | ✓ 一致 |
| 缓存内容 | BEV 特征 + 位姿信息 | — |
| 触发条件 | 仅在 10Hz 流式推理下激活 | — |

**可选时序模块**（可切换）：CONCAT（当前使用）/ ConvGRU / ConvLSTM / Transformer / TransformerLSTM / BevCrossAtten（Deformable Cross-Attention）

> **改后的说法**：我们用的是 3 帧、CONCAT 融合。**帧数少的好处是显存和时延可控**——SOLOFusion 那种 16 帧长时序精度更高，但显存翻倍、时延增加，量产付不起。而且**帧数不是越多越好**：历史越久，自车位姿累积误差越大，warp 之后特征对不齐反而是噪声。

### 三段式应答（不变，练到条件反射）

1. **划界**：「这块不是我负责的，融合模块是组里另一位同事在做。」
2. **给出你知道的**：「我们是在 BEV 空间做特征级融合，图像和点云 concat，Radar 逐元素叠加，鱼眼因为只覆盖近场一小块是 mean 聚合进去的。」
3. **拉回主场**：「跟我关系比较大的是融合前相机这一侧的 BEV 特征质量——深度估不准，融合层拿到的就是被涂错格子的特征。」
