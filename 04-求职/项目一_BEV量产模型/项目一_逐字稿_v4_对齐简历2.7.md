# 项目一 逐字稿 v4 对齐简历2.7

**项目一 · 多传感器融合 BEV 3D 目标检测量产模型迭代**

华为车 BU ｜ 2024.08 – 至今 ｜ 面试主战场，投入时间应占全部项目准备的一半以上

本版对齐简历 2.7。红色 = 本轮修正（原说法有误，不要再用旧版）　绿色 = 本轮新增　蓝色 = 待核实/风险提示

用法：先讲主线，讲完停住等追问；后面的「分层展开」是被追问时才拿出来的，不要主动一次性倒完。如果面试官只给 1 分钟，就讲【开场】+【划边界】+【优化一】+【成果】四段。主线正文约 1150 字，正常语速约 4 分钟——第一次一定要出声念并掐表。

**一、主线逐字稿（讲完停住，等追问）**

**【开场 · 一句话说清是什么】**

这个项目是我现在的主线工作，面向量产的行车和泊车场景做多传感器融合的 BEV 3D 目标检测。输入是 7 路针孔加 4 路环视鱼眼，再融合激光和毫米波点云，是一套多模态输入、多任务输出的框架，在 BEV 空间统一输出车、人、骑行人的 3D 框、速度和动静属性，给下游规控用。

**【我负责什么 · 讲产出，不讲边界】**

我在这个项目里做的是模型迭代和优化。整个链路我都参与过，主要精力和最深的部分在针孔支路——深度估计和视图变换，LSS 那一整套是我最熟的。具体的产出是三块：路测和客户反馈的高频问题由我复现、定位、制定并落地专项优化方案；难例数据的挖掘、回流和专项集构造；还有版本送测前的评测自验和准入回归。

**【难点 · 只讲三个，别铺开】**

量产模型的难点跟刷榜不太一样。我们的高频问题主要集中在几块：一个是凭空误检，护栏、尾气、地库闸机的纹理跟真车很像，模型会看见不存在的车，直接触发误刹；一个是中远距，目标在图像上就几个像素，激光投过去也稀疏，深度线索很弱，位置容易漂、检出距离上不去；还有低速跟车——前车挪得慢的时候，帧间在 BEV 上走不出一个格子，速度解不出来，容易判成静止。

> ▲ 顺序按简历 2.3 调过了：误检打头（后果最重、最有画面感），中远距第二（技术含量最重、数字最亮），低速跟车第三。原版的「速度和动静属性容易跳变」太笼统，换成具体场景。

**【优化一 · 深度这条线，投入最多，讲最细】**

我先讲中远距，这是我投入最多的。先做分距离段评测，确认劣化主要出在中远距，再顺着深度这条线找原因——我们针孔这边是 LSS 路线，图像特征最后落在 BEV 的哪个格子，完全由 DepthNet 预测的深度分布决定，深度歪了后面检测头是救不回来的。

所以做了三件事：第一，深度真值加密，把多帧点云做运动补偿之后聚合，生成更稠密的真值；第二，把 DepthNet 加深，后面接一个 CRF 做空间平滑；第三，把 Splat 那一步的实现换成 BEVPoolv2 的索引池化。

这里要说清楚一点：BEVPoolv2 和原来的实现在数学上是等价的，它本身不涨点，纯粹是省时间。省下来的时延正好覆盖了更重的 DepthNet 和 CRF——所以精度是涨的，时延反而还降了一点。合起来中远距的深度误差降了约 15%，检出距离也上去了。

> ▲ 原版说「等于用加速换了精度」，容易被听成 BEVPoolv2 涨点。BEVPoolv2 论文明确是数学等价、不报指标差异，懂的人一听就知道说错了。现在的说法把因果讲对：涨点的是省出来的预算买到的东西，不是加速本身。

**【优化二 · PV 辅助监督】**

第二个是图像特征判别力的问题。检测 loss 只作用在 BEV 空间，回传到图像端的梯度很弱。我的做法是把 BEV 的 3D 真值反投到各个相机生成 2D 监督，在 image backbone 后面接一个轻量检测头做辅助 loss，只在训练期生效，推理时摘掉，零开销。有个细节是反投过去的目标有些是被遮挡的，直接监督就是噪声，要做过滤和降权。

**【优化三 · 误检和速度，快带过】**

误检那块，这类难例在数据湖里没有现成标签、捞不出来。我用「连续几帧突然出现、又突然消失」这个时序判据去自动挖，把地库、闸机这些难负样本回流做成专项集回灌，泊车误检率降了三个多点。

速度那块的核心是低速。我们把速度 loss 按速度区间分段加权，低速那两段权重给到最高；L1 换成 Smooth L1，因为低速段速度本身就小、误差落在零点附近，L1 在那儿梯度是常数，会在真值噪声上反复震荡，Smooth L1 在零点附近梯度趋于零，收敛更稳；再跟动静属性联合约束，避免出现「判成静止但速度不为零」这种自相矛盾的输出。

> ▲ 两处硬伤已删：① 极坐标解耦（你没做过，简历 2.3 已移除）；② 「Smooth L1 抑制离群梯度」——那是相对 L2 说的，从 L1 改过来的正确理由是改善零点附近收敛。这两个错误原版都有。

**【成果 + 主动降调】**

整体对比商发基线，检出距离提到 131.5 米，动静属性和凭空误检这两个专题分别提了 3.5 个点和 5.1 个点，版本准入回归没有引入恶化项，跟着量产版本交付了。部署侧的数据是端到端时延降了 1.1 毫秒、内存没有增长——视图变换省出来的，比深度网络加深花掉的还多一点。这些是版本级的结果，也不全是我一个人的贡献。

> ▲ 「全评测项无恶化」改成「版本准入回归无恶化项」，把它限定成某一次评测的结论，不是永久保证。时延那句是本轮新增——它补上了原来缺的工程视角。

**二、分层展开（被追问时才拿出来）**

下面每一段都是一个独立的回答，被问到哪个讲哪个。不要在主线里提前倒出来——留着被问，效果比自己交代好得多。

**▸ 如果被问「讲一下 LSS 的完整流程」**

LSS 分三步。Lift 是对每个像素预测一个离散的深度分布，把探测范围切成 D 个 bin 做 softmax，同时图像特征给出一个 C 维的上下文向量，两个做外积，得到这条视线上 D×C 的视锥特征——相当于把 2D 特征按深度概率涂到光线上。Splat 是用内外参把视锥点变换到自车系、落进 BEV 网格。Shoot 在检测任务里就是接检测头。

这里可以补一句：原论文的 Splat 是 pillar 分配加 sum pooling、用 cumsum trick 加速。我们实际的实现不是照搬——是外积之后沿高度维做 pooling，再用预计算好的 grid_map 做一次 grid_sample 采到规则 BEV 网格上。所以严格说我们的基线本身就已经不是朴素 LSS 了。

关键点是深度是整条链的命门。深度分布歪了有三层后果：第一层，特征被涂到错误的格子，表现为位置跳变；第二层，目标真实所在的格子拿不到特征，那儿响应弱，就是漏检；第三层最麻烦——那个格子在训练时是有正样本标签的，模型被迫在「没有特征」的地方学出响应，等于把有效的监督信号抑制掉了，训练本身就被污染了。

> ▲ 第三层是本轮新增的。原版只讲了前两层。这一层是内部讲解视频里的原话（「你给他投歪了，那个地方没有监督，你会把那个信号相当于给他抑制掉」），讲出来密度明显高一档。

**▸ 如果被问「深度真值具体怎么生成，动态目标怎么办」**

基本做法是把激光点云按外参投到图像平面，取每个像素对应的深度，再按 bin 离散化，对 DepthNet 输出的深度分布做监督。单帧太稀疏，所以我做多帧聚合——但多帧不能直接叠，要先按自车位姿做运动补偿把历史帧对齐到当前帧。静态背景这么处理没问题；动态目标会拖影，需要按目标框的运动做单独补偿或者干脆剔除掉，这块是实际做的时候最花时间的地方。另外投影过去的点还要做遮挡剔除，不然前景背景的深度会混在一起。

如果他继续追「运动补偿到底有多大收益」，可以讲一个我复现过的对照实验（原本是同事做的，我进组后在他环境里复现了一遍）：三帧输入，做和不做运动补偿两组对比，速度误差还能再降两到三个点；更明显的是静止段——motion prediction 的 L2 距离，车从 0.22 降到 0.14，卡车从 0.15 降到 0.076，接近腰斩。还有个反直觉的结论：叠五帧反而不如叠三帧，因为帧间隔拉大之后，补偿误差累积过去了。

> ▲ 那组实验是 Radar 输入叠帧，和深度真值生成不是同一件事，讲的时候要说清楚是「同类方法的对照实验」，别混成一件事。「我复现过同事的实验」这句本身是加分的——说明你进组之后主动趟过别人的工作。

**▸ 如果被问「你们推理时到底用不用激光」**

用。点云在我们模型里其实有两个角色，这两个角色不一样。一个是训练期的：投影到图像上生成深度真值去监督 DepthNet，这是 BEVDepth 那一套，训练完就不需要了。另一个是推理期的：点云走 LidarNet 出一份 BEV 特征，跟视觉的 BEV 特征在 BEV 空间做融合，再进时序融合和检测头，这是推理时真实的输入。所以把激光拔掉，这条支路就断了。不过团队整体的方向是提升纯视觉的能力、降低对激光的依赖，我做的深度优化也是服务这个目标的。

**▸ 如果被问「鱼眼为什么要单独处理」　【本轮重写】**

两条支路是完全独立的两套管线，连 image backbone 的权重都不共享，最后在 MultiFusion 那一层才合并。

针孔走 LSS：显式的几何投影，DepthNet 预测 100 个 bin 的深度分布，再按内外参投到 BEV。鱼眼走 Transformer：不预测深度，而是把图像上每个位置沿射线采样出来的 3D 点，转到自车系之后用 MLP 编码成球面坐标的位置编码，注入到图像特征里，再让 BEV query 做 cross-attention 去取。

为什么不统一？主要是算力。BEV query 的数量正比于覆盖面积——针孔要覆盖全场，BEV 网格是 448×224、十万个格子，每个 query 都做 cross-attention，量产上受不了；鱼眼只管近场十二米多，网格是 16×16、两百多个 query，差了将近三个数量级，才付得起。

鱼眼那边也确实更适合 transformer：畸变太强，显式几何投影不好做，注意力是隐式学映射，不依赖精确标定，还省掉了深度估计这一环。

不过要交代一句：这在我们内部的定位是个折中方案，理想状态应该是两条支路统一。现在分成两套独立管线，维护成本是有的。

> ▲ 原版有两处要不得：① 说「深度真值那块鱼眼支路按自己的畸变模型独立投」——这条已从简历 2.3 删掉，而且和真实机制对不上；② 把这个设计讲成了精心设计的最优解，但内部讲解视频里的原话是「最理想的应该是都用一样的，那现在是一个折中的方案」。承认局限反而更可信。
>
> ▲ 还有一处机制错误已改：原来说「反投采样」，那是 BEVFormer 的做法（query 反投到图像找参考点做 deformable attention）。你们实际是 PETR 风格——3D 位置编码注入图像特征，标准 TransformerDecoder。材料原话是「无显式几何映射」「球面坐标仅提供粗略位置先验」。被问参考点怎么算就会穿帮。

**▸ 如果被问「速度 loss 具体怎么做的」　【本轮重写，原极坐标段作废】**

三件事。第一，按速度区间分段加权，低速那两段权重给到最高。第二，L1 换成 Smooth L1。第三，跟动静属性联合约束。

为什么低速要加权：BEV 格子 0.4 米，时序用 3 帧也就是 0.2 秒，前车一米每秒的话 0.2 秒只走 0.2 米、半个格子，0.5 米每秒就只有四分之一格——位移信号被网格量化吃掉了，速度根本解不出来。而这个区间恰恰最关键，0.1 和 1.0 米每秒的区别就是刹不刹车。所以最难解的区间和最关键的区间是重叠的。

为什么 Smooth L1：速度真值是位置差分出来的，噪声在一米每秒量级。低速目标真实速度才零点几，信噪比小于一。L1 在零点附近梯度恒为常数，会在噪声水平上反复震荡、收敛不到精细值；Smooth L1 在零点附近梯度趋于零，收敛更平稳。所以它的收益在低速段最大。

> 注意：如果他问「Smooth L1 不是抑制离群梯度吗」，要答对——Smooth L1 相对 L2 才是抑制离群梯度爆炸；相对 L1 是改善小误差区间的收敛。我们是从 L1 改过来的，所以是后者。

**▸ 如果被问「速度分段的边界是怎么定的」　【新增】**

边界不是我拍的，是沿用业务侧已有的速度档位定义——0.2 米每秒是动静属性的判定阈值，1.67 也就是 6 公里每小时是低速跟车和行人步速的上界，8 米每秒是城区中速。这几个点规控那边本来就在用，评测专题也是按这个分的。

我和一位同事在这套既有分档上做的是权重调优：他负责制定实验策略，我负责起实验任务、跑对照、收数据。先看各段的速度误差分布，再看哪些段的误差会真正影响下游决策，低速那两段最后给到最高。权重值是几轮实验试出来的，不是推导出来的。

> ▲ 这个答法的分寸：边界不邀功（诚实），权重调优认领（真做了），同事的分工主动交代。而且顺带展示你知道这几个数字的业务含义——0.2 是动静阈值、1.67 是 6km/h，这不是查代码能知道的。

**▸ 如果被问「131.5 米和你们 BEV 范围是什么关系」　【新增】**

检出距离指的是目标首次被稳定检出时离自车的距离，它不可能超出 BEV 的覆盖范围。131.5 米这个数是新版本扩了 BEV 范围之后测的——老版本的前向边界只有九十多米，装不下这个数。

顺带说一句：范围扩大之后 BEV 格子数是变多的，视图变换的开销会跟着涨，这也是为什么我们要在那一步上省算力。

> ▲ 待核实：v18 的 BEV_AREA_SIZE / post_center_range 前向边界具体是多少。这是目前唯一可能被当场问穿的点——面试官问一句「你们 BEV 覆盖多大」，你答完他心算就会追。查到之后把上面那句里的具体数字填进去。

**▸ 如果被问「BEVPoolv2 能带来多少加速」　【新增】**

论文报的是十几倍，但那是相对朴素实现说的。我们的基线本身在算子层面已经优化过一轮，所以实际提升没有论文那么大。我这边能给的是端到端的净结果：视图变换省出来的时延，覆盖掉更重的 DepthNet 和 CRF 之后，整体还净降了 1.1 毫秒，内存没有增长。

> ▲ 千万别报论文的 18.9×。内部讲解视频里明确说过「我们那个 LSS 推理的时候，算子那边优化过一步了，你可能不一定有你预期那么大的提升」。报了会被追着要实测数据。

**▸ 如果被问「部署这块你做过吗」　【新增·中小厂高频】**

分三块说。第一，在这个 BEV 项目里，部署是专门的同事负责，但算力预算是我们做模型优化时的硬约束——比如视图变换那一步换成 BEVPoolv2，出发点就是省时延，省出来的才敢往深度网络上加。所以我做优化是带着时延预算做的，不是只看指标涨没涨。

第二，上一份工作焊缝检测那个项目，我参与了 TensorRT INT8 量化和工控机部署，配合做了多线程 pipeline 的推理流程优化。

第三，端侧我自己动手做过两条线：一条是 NVIDIA 线——在 Jetson Orin 上把 BEVFusion 部署跑通了，用 C++ 做的端到端推理，从 ONNX 导出、TensorRT engine 构建，到点云体素化和图像的前处理、多模态输入的显存管理，再到后处理解码，整条链路自己趟了一遍；另一条是国产芯片线——YOLO 在瑞芯微 RK3588 上走 RKNN 量化部署，跑通了实时视频流的检测。

> （这里接一句你实际踩的最深的坑，比如 BEVPool 这类自定义算子 TensorRT 不支持、要自己写 plugin；或者点云体素化在 C++ 侧的实现；或者多模态输入的显存拷贝开销。挑一个能讲两分钟的。）
>
> ▲ 这一段对中小厂的分量比任何指标都重——它直接回答「你能不能一个人把东西落地」。而且和简历里的 BEVPoolv2 天然呼应：你在个人部署里真碰过 BEVPool 算子的坑，就不是纸上谈兵。建议主动找机会讲出来，别等着被问。
>
> ⚠ 一个诚实的边界：说清楚这是个人实践、不是量产交付。个人跑通和量产上车的差距（车规、功能安全、长时间稳定性、多路同步）要能说出来，说得出来反而显得你知道量产的门槛在哪。

**▸ 如果被问「这些优化里哪一个是你独立主导的」**

（挑一个从定位到落地全程你做的讲，讲完整链条，不要贪多。建议选深度监督加密或者误检难例挖掘——这两个的问题定位、方案设计、数据准备、训练验证、评测回归你都能说出细节。）

**三、这个项目的注意事项**

- 这个项目是重头，面试官会往下追三层。主线讲完一定要停，让他挑方向，不要自己一路讲到底。

- 标题写了「多传感器融合」，面试官一定会追融合细节（在哪一层融、什么算子、时空同步、激光降级）。所以开场那句边界必须说出口：融合模块是团队的，你的工作在针孔支路。标题放大了、内容接不住，是净亏。

- 不要主动说「这不是我做的」。开场只讲产出。被问到你没深做的部分（融合层、鱼眼支路、训练平台），答「这块主要是 XX 同事负责，我了解的是……」，然后把你知道的讲出来——说明你懂、只是没主导，这和「我不会」是两回事。面试官不会把所有边界都问一遍，主动交代反而是自己关门。

- 「LSS 的完整流程」和「深度真值怎么生成」这两问几乎必被问到，要练到能边说边在纸上画。

- 数字口径：131.5m、15%、3.7%、3.5%、5.1%、1.1ms这几个数在讲的时候可以用约数，但心里要清楚基线是什么版本、在哪个评测集上测的、样本量多大。被追问答不上，比不说这个数更糟。

- 三个待核实项（都在内网查得到，不用做实验）：① v18 的 BEV 前向边界——支撑 131.5m；② 视图变换优化前后的分段时延——支撑 1.1ms 这个数怎么拆的；③ 速度分段权重里哪些参数是你调的。

- 如果面试官质疑「这些不都是论文里的方法吗」，坦率承认方法来自 BEVDepth、BEVNeXt、BEVFormerV2，然后讲落地时论文不碰的部分：鱼眼畸变、遮挡过滤、真值噪声、时延预算——这才是你的价值。

**四、通用口播提醒**

- 别背。背出来的东西面试官一听就知道，而且一旦被打断就接不上。记熟的是"讲哪几块、每块的第一句话"，中间的词现场组织。

- 语速放慢，比你平时说话再慢一点。紧张时会不自觉加速，60 秒的稿子 40 秒讲完，听起来很急。

- 数字只说自己核对过、能解释来源的。说了"131.5 米"就要能答"基线是多少、怎么测的"，答不上比不说更糟。

- 主动说边界。"架构是团队既有的，我做的是在这上面的专项优化"——这句话不减分，反而显得实在，也能挡掉后面"这也是你做的？"的尴尬。

- 介绍完停住，不要往下续。让面试官接话，主动权交给他。
