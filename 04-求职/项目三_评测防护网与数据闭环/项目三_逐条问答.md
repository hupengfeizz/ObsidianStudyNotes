## 0.1 这套体系在解决什么 ★★★

### 一句话

量产感知每两三个月发一个版本。每个版本都会改动模型，而**每次改动都可能修好一个问题、同时弄坏三个已经修好的问题**。

**这套体系回答两个问题**：

> **① 路测反馈的历史问题，这一版有没有复现？**
> **② 这个候选版本，到底能不能送测？**

这两个问题，`mAP = 0.53` 一个字也答不了。

### 软件工程类比（最有效的解释方式）

本质上这是**感知模型的回归测试体系（Regression Test Suite）**：

| 软件工程 | 本项目 |
|---|---|
| 单元测试 | 单个 checker |
| 测试用例 | 防护网用例（一个场景片段 + 一组预期） |
| 测试套件 | 防护网用例集（10+ 大类、50+ 专题） |
| CI / 门禁 | 版本准入回归 |
| 回归 bug | 历史问题复现 |
| golden test / 基准对比 | 基线 diff |
| 测试报告 | 通过率 + 优化 / 恶化 diff 报表 |
| **修一个 bug 补一条测试用例** | **修一个问题加一条防护网用例** |

**最关键的是最后一条**：软件工程里，每修一个 bug 就补一条测试用例，保证它永不复现。这套体系做的就是同一件事——**每一个路测反馈的问题，都被固化成一条防护网用例，从此永久监控**。

**用例集只增不减，随版本累积。这就是"防护网"这个名字的来源。**

> 被问「你做的是不是就是写测试脚本」时，就用这个类比 —— 然后把话题引到「量产准入」这个词上：**这套东西是版本能不能送测的依据，不是可有可无的辅助工具。**

### 与项目一的关系

**项目一和项目三是一条闭环的两半**：

```
项目一：发现问题 → 定位 → 做优化
项目三：提供挖掘工具 + 验证优化有没有效、有没有副作用 → 供给下一轮数据
```

项目一里「用时序判据挖掘凭空误检」这件事，**挖掘工具和回灌链路就是项目三建的**。「分距离段评测定位中远距劣化」，用的也是这套体系的分层统计能力。

**两个项目串起来讲，是一个完整的量产迭代方法论。**

## 0.2 为什么 mAP 回答不了量产的问题 ★★★

### mAP 的数学性质决定了它会掩盖长尾

mAP 是整个测试集上的**平均量**。举个具体例子：

```
测试集              100,000 帧
其中地库闸机场景        200 帧（占 0.2%）
新版本在这 200 帧上误检数    2 次 → 8 次
在其余 99,800 帧上         略有提升

→ mAP 上涨
→ 实际：地库误刹频率翻了 4 倍，用户会立刻感知到
```

**平均量对小比例子群的变化不敏感——这是数学性质，不是指标设计得不好。**

学术评测追求的是模型的整体能力排序，量产追求的是**不能在任何一个已知场景上退步**。两者的目标函数根本不同。

### 三组对照

| 维度 | 学术指标（mAP / NDS） | 量产防护网 |
|---|---|---|
| 回答的问题 | 这个模型整体水平如何 | **这个版本能不能上车** |
| 统计对象 | 整个测试集的平均 | **每一个具体场景的具体问题** |
| 粒度 | 一个标量 | **分层 diff 报表** |
| 判据 | 越高越好 | **任一项恶化即不准入** |
| 数据来源 | 固定的公开集 | **真实路测反馈，持续累积** |
| 用途 | 横向比模型 | **纵向比版本** |

### 两者是互补不是替代（这句话一定要说）

- **mAP / NDS**：适合横向对比不同模型、不同技术路线，回答"我们的模型比竞品强吗"
- **防护网**：适合纵向对比版本，回答"这次改动引入了什么副作用"

**量产团队两套都要有。** 只有 mAP 会漏掉长尾退化；只有防护网会失去对整体能力的把握（用例集里的场景毕竟有限，可能整体能力下降但恰好没触发任何用例）。

### 量产真正关心的九类问题

| 问题类 | 业务后果 |
|---|---|
| **凭空误检（FP）** | 误刹 —— 最严重 |
| 漏检（FN） | 追尾 / 未减速 |
| **3D 不稳** | 框抖动 → 规控轨迹抖 → 乘客不适 |
| 动静误判 | 静止判动 → 无谓减速；动态判静 → 危险 |
| 速度误差 | 跟车距离错、变道时机错 |
| **检出时延（鬼探头）** | 目标出现到稳定输出的延迟，直接决定能不能刹住 |
| 检出距离 | 决定能多早发起变道 |
| **AEB 误 / 漏触发** | 最高优先级的安全项 |
| 区域入侵 | 自车周围危险区域内是否有目标 |

**这九类问题的判定逻辑完全不同——这就是 checker 框架要解决的第一个难点。**

## 0.3 四段闭环全景 ★★★

```
                    ┌─────────────────────────────────────┐
                    ↓                                     │
        ┌───────────────────────┐                         │
        │ ① 场景 checker        │  单个问题的判定逻辑      │
        │ check_fp/fn/unstable… │                         │
        └───────────┬───────────┘                         │
                    ↓                                     │
        ┌───────────────────────┐                         │
        │ ② 防护网用例集         │  路测问题 → 用例        │
        │ 10+ 大类 50+ 专题      │  只增不减，永久监控      │
        └───────────┬───────────┘                         │
                    ↓                                     │
        ┌───────────────────────┐                         │
        │ ③ 基线 diff           │  与冻结基线逐项对比      │
        │ 通过率 + 优化/恶化     │  → 版本准入判定         │
        └───────────┬───────────┘                         │
                    ↓                                     │
        ┌───────────────────────┐                         │
        │ ④ 难例挖掘与回灌       │  失败 case → 数据       │
        │ 数据湖检索 → 送标      │  → 训练 → 新版本 ───────┘
        └───────────────────────┘
```

**这是一个真正的闭环**：评测发现问题 → 定位到具体场景 → 挖掘同类数据 → 标注回灌 → 训练新版本 → 再评测 → 该问题变成永久监控的用例。

**每转一圈，模型变强一点，用例集变厚一点，覆盖的长尾变多一点。**

> 这正是特斯拉说的 **Data Engine** 的思路：**模型的能力上限不由结构决定，由数据闭环转动的速度决定。**

## 0.4 匹配层：整个评测最容易错的地方 ★★★

> **这一层的 bug 最隐蔽、破坏力最大**——匹配错了，所有下游指标都是错的，而且错得看不出来。

### 0.4.1 时间戳对齐

**问题**：真值和预测的时间戳是异步的。

- 真值按标注帧给出（可能是 2Hz 抽帧标注）
- 模型推理输出有自己的时间戳（10Hz）
- 中间还会**偶发缺帧**（数据丢包、解码失败、推理超时）

**错误做法**：按索引顺序配对（第 i 个预测配第 i 个真值）。一旦有一帧丢失，后面**全部错位**，指标会莫名其妙地崩掉，而且**极难排查**——因为没有报错，只是数字变差了。

**正确做法**：

```python
def align_timestamp(pred_seq, gt_seq, time_window=50):  # ms
    pairs, missing = [], []
    for gt in gt_seq:
        nearest = min(pred_seq, key=lambda p: abs(p.ts - gt.ts))
        if abs(nearest.ts - gt.ts) <= time_window:
            pairs.append((nearest, gt))
        else:
            missing.append(gt)     # 缺帧单独统计，不算漏检
    return pairs, missing
```

**最关键的一条**：

> **缺帧必须单独统计，不能默默算成漏检。**

如果缺帧被算成漏检：指标变差了，但原因是**数据管线故障**不是模型问题；你会花几天去查模型，最后发现是解码器丢了 3% 的帧。

### 0.4.2 分类别匹配

**核心洞察：不同类别的目标，"检出算不算成功"的判据不一样。**

#### 车辆类：3D IoU

```
匹配条件：3D IoU ≥ 阈值（如 0.4）
```

车辆尺寸大（4.5×1.8×1.5m），IoU 是稳定可靠的判据。

#### 行人：中心点距离

**为什么 3D IoU 对行人失效——用数字说话**：

```
行人框：0.6m × 0.6m × 1.7m
中心横向误差 0.3m

→ IoU ≈ 0.2，低于 0.4 的阈值 → 判为漏检
```

**中心只偏了 30cm，IoU 就掉到 0.2。** 但从感知使用的角度，这个检出**完全有效**——规控知道那里有个行人，30cm 的误差不影响任何决策。

> **用一个 IoU 阈值，把"有没有检出"和"位置准不准"这两件事混在了一起。**

**正确做法是分开**：

```
"有没有检出"  → 中心点距离匹配（阈值按类别和距离段设定）
"位置准不准"  → 匹配成功后，单独统计中心误差、尺寸误差、朝向误差
```

**这个设计不是独创的——nuScenes 官方评测就是这么做的**：

> nuScenes 的 mAP 使用**中心距离**匹配（阈值 0.5 / 1 / 2 / 4m 取平均），而不是 3D IoU。官方给出的理由正是"IoU 对小目标过于苛刻，且无法区分'检到了但位置略偏'和'完全没检到'"。匹配成功后再单独计算 mATE（平移误差）、mASE（尺寸误差）、mAOE（朝向误差）、mAVE（速度误差）、mAAE（属性误差）。

> **这一条很值钱**——它把你的设计从"权宜之计"变成"和顶级公开基准同一个思路"。

**中心距阈值怎么定**：

| 因素 | 说明 |
|---|---|
| 物理尺寸 | 行人 0.6m 宽，阈值取 0.5–1.0m 合理 |
| 下游容忍度 | 规控对行人横向位置的容忍是多少 |
| **距离分段** | **近处严、远处松**——远距几何精度天然差，同一阈值远距全是漏检 |

#### 跨类等价集

**问题**：类别边界本身就模糊，模型和标注员的判断可能不一致。

| 混淆对 | 说明 |
|---|---|
| TRUCK / TRAM | 大型车辆，远距外观相似 |
| CYCLIST / TRICYCLE | 骑行人与三轮车 |
| CAR / VAN | 小型车与面包车 |
| PEDESTRIAN / CYCLIST（推行状态） | 推着自行车走的人 |

严格按类别匹配的话，模型把卡车判成电车就算"漏检卡车 + 误检电车"——**一次错误被记成两次**，而这个错误对下游几乎没有影响（都是大型障碍物，规控处理方式一样）。

**解法**：

```yaml
equivalence_groups:
  large_vehicle:  [TRUCK, TRAM, BUS]
  two_wheeler:    [CYCLIST, TRICYCLE, MOTORCYCLE]
  small_vehicle:  [CAR, VAN]
```

同组内的类别混淆**不计为误检 / 漏检**，但**单独统计为"类别混淆"**——既不虚高地惩罚，也不隐藏问题。

### 0.4.3 匹配算法本身

匹配是一个**二分图最优匹配**问题：

| 算法 | 复杂度 | 特点 |
|---|---|---|
| **贪心匹配** | O(n²) | 按 IoU / 距离降序依次配对，已匹配的跳过。简单快速，可能非全局最优 |
| **匈牙利算法**（Kuhn-Munkres） | O(n³) | 全局最优。`scipy.optimize.linear_sum_assignment` |

单帧目标数通常几十个，两者都很快，匈牙利更严谨。**注意匈牙利要求代价矩阵完整**，对"不允许匹配"的组合（超阈值、类别不等价）要设成极大代价。

```python
from scipy.optimize import linear_sum_assignment
import numpy as np

def match(preds, gts, cost_fn, max_cost):
    if len(preds) == 0 or len(gts) == 0:
        return [], list(range(len(preds))), list(range(len(gts)))
    cost = np.array([[cost_fn(p, g) for g in gts] for p in preds])
    cost[cost > max_cost] = 1e9              # 不允许的匹配设极大代价
    row, col = linear_sum_assignment(cost)
    matches, um_p, um_g = [], set(range(len(preds))), set(range(len(gts)))
    for r, c in zip(row, col):
        if cost[r, c] < max_cost:
            matches.append((r, c)); um_p.discard(r); um_g.discard(c)
    return matches, sorted(um_p), sorted(um_g)
    #      匹配对    未匹配预测(FP候选)  未匹配真值(FN候选)
```

### 0.4.4 3D 旋转框 IoU 怎么算

3D 框（BEV 平面上带朝向的矩形 + 高度）的 IoU 不能用轴对齐框的公式。标准做法是**分解为 BEV 交集 × 高度交集**：

```
① BEV 平面交集面积：
   两个旋转矩形求交 → 凸多边形裁剪
   常用 Sutherland-Hodgman 算法 或 shapely 库
   → 交集多边形 → 面积 A_inter

② 高度方向交集：
   h_inter = max(0, min(z1_top, z2_top) − max(z1_bot, z2_bot))

③ 体积：
   V_inter = A_inter × h_inter
   V_union = V1 + V2 − V_inter
   IoU_3D  = V_inter / V_union
```

**BEV IoU vs 3D IoU**：很多场景只用 BEV IoU（忽略高度），因为自动驾驶关心的是平面位置关系、高度的标注和预测都不太准（尤其 z 中心）、计算更快。

### 0.4.5 距离分段统计

```
所有指标按 [0-30m] / [30-60m] / [60-90m] / [90m+] 分段统计
```

**为什么必须分段**（三条）：

1. **目标数量分布极不均匀**——80% 以上的目标在 50m 以内。不分段的话整体指标基本等于近距指标，远距问题被完全淹没
2. **不同距离段的难度和容忍度完全不同**
3. **项目一「分距离段评测定位中远距劣化」依赖的就是这个能力** ← 两个项目的连接点

## 0.5 时序指标与跨帧关联 ★★☆

### 为什么单帧指标不够

| 现象 | 单帧看到的 | 实际问题 |
|---|---|---|
| 检出闪烁 | 每帧的 P/R 都还行 | 目标在"有/无"之间反复跳，规控无法跟踪 |
| 鬼探头时延 | 每帧都"检出了" | **第一帧检出得太晚，来不及刹** |
| 动静跳变 | 每帧属性准确率 90% | 同一目标的属性在帧间翻转 20 次 |
| ID 切换 | — | 跟踪 ID 频繁重置，下游历史信息全丢 |

> **这些问题的共同点：它们是"序列"的属性，不是"帧"的属性。**

### 跨帧目标关联

```
真值侧：标注本身带 track_id（同一目标跨帧一致）
预测侧：
   方案 A：模型输出带跟踪 ID（如果有跟踪模块）
   方案 B：评测时自己做关联（帧内匹配 + 帧间 IoU / 距离传播）
```

**关联建立后可统计的时序指标**：

| 指标 | 定义 |
|---|---|
| 连续命中长度 | 一个真值 track 被连续正确检出的最长帧数 |
| **连续丢失长度** | 连续漏检的最长帧数（比总漏检率更能反映严重性） |
| 首帧检出距离 | 连续 N 帧稳定检出时，首次稳定那刻的距离 |
| 触发时延 | 目标首次可见 → 连续 N 帧稳定输出的时间 |
| 属性跳变次数 | 同一 track 上属性翻转的次数 |
| **IDSW** | ID Switch，同一物理目标被分配了几个不同 ID |
| track 完整度 | 检出帧数 / 真值 track 总帧数 |

> 可以借鉴 **MOT（多目标跟踪）**领域的成熟指标：MOTA、MOTP、IDF1、IDSW、MT/ML（Mostly Tracked / Mostly Lost）。这些指标专门为时序设计，可以直接借用。

### 容忍失败帧数

一个重要配置项：**允许连续失败几帧**。

```
tolerate_fail_frames: 2
```

理由：单帧的偶发失败对下游影响有限（跟踪器会用历史信息补上），但**连续失败**就是真问题。这个配置让 checker 能区分"偶发抖动"和"持续失效"。

## 0.6 防护网用例集与准入规则 ★★★

### 一条用例长什么样

**用例 = 数据片段 + 一组 checker + 一组阈值 + 预期结果**

```yaml
- case_id: FP_GARAGE_GATE_001
  description: "地库闸机横杆凭空检出车辆"
  source: "路测问题单 #12345, 2024-09-12"      ← 关键字段
  data:
    clip: "clip_20240912_143022"
    frames: [1200, 1450]
  checkers: [false_positive, region_intrusion]
  overrides:
    false_positive:
      confidence_threshold: 0.2
      tolerate_fail_frames: 0
  expected: pass
  priority: P0
```

**关键字段是 `source`**：每条用例都能追溯到一个真实的路测问题或客诉。这保证了用例集不是凭空设计的，而是**真实问题的固化**。

### 用例集结构（10+ 大类、50+ 细分专题）

```
防护网用例集
├ 误检类：地库闸机 / 停车场立柱 / 前车尾气 / 护栏隔离带 / 路面污渍井盖 / 树影光斑
├ 漏检类：中远距小目标 / 强逆光 / 雨雾天 / 夜间无路灯 / 异形车
├ 3D 稳定性：大型车框抖动 / 密集车流
├ 动静与速度：起步刹停临界 / 横穿目标 / 静止车队
├ 检出时延：鬼探头行人 / 遮挡后车辆窜出
├ 检出距离：高速中远距车辆 / 施工区
├ AEB：应触发场景 / 不应触发场景
├ 区域入侵
├ 泊车专项
└ 恶劣天气专项
```

### 白名单机制（核心）

「白名单用例集」的含义：**这些用例是已知必须通过的**。

- 每一条都对应一个已经修复的历史问题
- 新版本必须全部通过才能送测
- **只增不减**——修好一个问题就加一条，永久监控

> **这是防护网最核心的机制：它保证了模型能力单调不减。** 没有它，量产迭代会陷入"修好一个坏三个"的循环。

### 优先级

| 级别 | 含义 | 失败后果 |
|---|---|---|
| **P0** | 安全相关（AEB、误刹、区域入侵） | **直接阻塞版本** |
| **P1** | 高频体验问题 | 需要说明原因并评审 |
| P2 | 长尾场景 | 记录，允许暂时不通过 |

### 基线 diff

**基线 = 当前已量产的版本（商发版本）**，它的所有评测结果被冻结保存。

```
┌────────────────────┬────────┬────────┬────────┬────────┐
│ 专题                │ 基线    │ 新版本  │  Δ     │ 状态   │
├────────────────────┼────────┼────────┼────────┼────────┤
│ 误检-地库闸机       │ 92.3%  │ 95.6%  │ +3.3   │ 优化 ✓ │
│ 误检-前车尾气       │ 88.1%  │ 88.4%  │ +0.3   │ 持平 - │
│ 漏检-中远距         │ 85.0%  │ 89.2%  │ +4.2   │ 优化 ✓ │
│ 3D稳定-大型车       │ 91.5%  │ 87.2%  │ -4.3   │ 恶化 ✗ │ ← 阻塞
│ 检出距离-高速       │ 118.2m │ 131.5m │ +13.3m │ 优化 ✓ │
│ AEB-不应触发        │ 100%   │ 100%   │  0     │ 持平 - │
└────────────────────┴────────┴────────┴────────┴────────┘
结论：存在 1 项恶化，不予准入
```

### 两种通过率（都要有）

| 口径 | 定义 | 用途 |
|---|---|---|
| **帧通过率** | 通过的帧数 / 总帧数 | 细粒度，反映问题的普遍程度 |
| **case 通过率** | 通过的用例数 / 总用例数 | 粗粒度，直接对应"有几个问题没解决" |

**两个都要**：一个 case 里 99% 的帧通过、1% 失败，帧通过率很好看，但这个 case 本身是**失败**的（那 1% 就是问题所在）。反过来，case 通过率不能反映失败的严重程度。

### 噪声阈值（容易被忽略但必被问）

**多小的变化算"恶化"？**

模型训练本身有随机性（初始化、数据顺序、cudnn 非确定性），同一份配置训两次，指标可能差 **0.3–0.5%**。所以：

```
|Δ| < noise_threshold → 判为"持平"
```

**噪声阈值需要通过同配置多次重训实测得出，不能拍脑袋。** 否则会有大量假阳性的"恶化"，消耗大量排查时间。

### 准入规则

```
版本准入 = 目标专题达成预期提升
         AND 无 P0 恶化
         AND P1 恶化项已评审并有明确结论
         AND 全量回归完成
```

**「无恶化引入」的深层含义**：

> 每一个历史 bad case 背后，可能都是一次真实的客诉甚至事故。**允许它复现，等于让用户再经历一次。**

这就是为什么量产迭代慢——不是技术难，是每次改动都要证明"没有破坏任何已有能力"，而这个证明的成本极高。**这套体系做的事，正是把这个证明成本从"两天人工"降到"半天自动"。**

## 0.7 数据闭环上半环：难例挖掘 ★★☆

### 核心矛盾

**问题场景在数据湖里"捞不出来"。**

数据湖里有百万级 clip，但检索能力只有：按时间/地点/车辆 ID、按已有标签（如果标注过）、按触发事件（接管、急刹）。

而你要找的是"地库闸机横杆导致误检"这样的场景——**它没有标签，因为没人标注过"闸机"这个东西**。

### 组合条件过滤

**思路：用已有的弱信号组合出目标场景。**

| 目标场景 | 组合条件 |
|---|---|
| 地库 | GPS 信号丢失 + 车速 <20km/h + 环境亮度低 + 转向频繁 |
| 闸机 | 地库条件 + 车辆完全停止 + 停止时长 3–20s |
| 前车尾气 | 车速 >40km/h + 前方有跟车目标 + 环境温度低 + 检出目标生命周期极短 |
| 隧道 | GPS 丢失 + 车速高 + 亮度骤变 |
| 施工区 | 检出锥桶类目标 + 高速路段 |
| 雨天 | 雨刮器状态 + 环境光 |
| 强逆光 | 时间为日出/日落时段 + 车辆朝向与太阳方位角接近 |

> **关键洞察**：车上有大量**非视觉信号**（GPS、CAN 总线、IMU、雨刮、车灯、时间、天气 API），它们**不需要标注就能用**，组合起来可以精确圈定场景。

### 基于模型行为的挖掘（更精准）

| 判据 | 找什么 |
|---|---|
| **时序突现突消** | 凭空误检 ← **项目一用的就是这条** |
| 高置信度但生命周期短 | 同上 |
| 置信度在阈值附近震荡 | 模型不确定的边界样本 |
| 相邻帧预测剧烈变化 | 不稳定场景 |
| **多模型分歧**（Query by Committee） | 几个版本跑同一份数据，预测不一致的帧信息量最高 |
| **区域入侵报警** | 免标注的大规模筛查（见 §42） |
| 与规控决策冲突 | 感知说有障碍但人类驾驶员没减速 |

**这类挖掘的价值：它直接指向模型的能力边界**，比随机采样的数据信息量高一个数量级。

> **主动学习（Active Learning）**的核心思想就是这个：标注预算有限时，优先标注模型最不确定的样本。

### 挖掘 → 送标 → 回灌链路

```
① 组合条件 / 模型行为判据 → 候选片段（可能几万帧）
② 自动去重（相似帧只保留代表帧）
③ 人工快速筛查（确认确实是目标场景，几秒/帧）
④ 送标注（3D 框标注，最贵的一环，市价 10–50 元/帧）
⑤ 标注质检
⑥ 构造专项训练集 / 评测集
⑦ 回灌训练 → 新版本 → 评测验证是否收敛
```

**去重很重要**：10Hz 采样下相邻帧几乎相同，不去重会花大量标注预算买重复信息，还会让训练分布偏斜。

### 回灌的副作用必须监控

**加数据一定有副作用**：加大量地库负样本 → 地库误检下降，但**可能带来地库漏检上升**；加某个场景的数据 → 训练分布偏移，其他场景可能退化。

所以每次回灌后都要跑**全量防护网**，而不只看目标专题。

## 0.8 数据闭环下半环：标注质检与错标治理 ★★☆

### 错标是一个被严重低估的问题

**公开数据集的错标率**（Northcutt et al., *Pervasive Label Errors in Test Sets*, NeurIPS 2021）：

| 数据集 | 测试集错标率 |
|---|---|
| ImageNet | **5.8%** |
| CIFAR-100 | 5.9% |
| QuickDraw | 10.1% |
| MNIST | 0.15% |

**这还是精心维护的公开数据集。** 大规模外包标注的量产数据集，错标率只会更高。

**3D 标注的错标形式**：

| 类型 | 说明 |
|---|---|
| 漏标 | 远距、遮挡、小目标最常见 |
| 多标 | 把噪声点云标成目标 |
| 类别错误 | 卡车标成巴士 |
| 框不准 | 尺寸、朝向、位置偏差 |
| **朝向反向** | **yaw 差 180°，非常常见且危害极大**（速度方向全反） |
| ID 关联错误 | 跨帧 ID 串了 |

### 错标的双重危害

1. **污染训练**——模型学到错误的模式。尤其是**系统性错标**（某个标注员一贯的偏差），危害远大于随机噪声
2. **污染评测**——**这个更隐蔽**。真值错了、模型对了，评测判模型错——你会去"修复"一个不存在的问题，浪费大量时间，甚至把模型改坏

### 用模型推理反查标注

**核心思路：把模型当成"第二标注员"。**

```
① 用当前最好的模型跑全量训练集推理
② 预测与标注做匹配
③ 挑出偏差最大的帧：
     · 模型高置信度检出，但标注里没有  → 可能是漏标
     · 标注里有，但模型完全没响应       → 可能是多标 / 噪声目标
     · 匹配上了，但尺寸/朝向差异巨大    → 可能是框标错
     · 朝向差约 180°                   → 高度疑似反向错标
④ 按偏差程度排序，推给人工复核
⑤ 复核结论回写，修正标注
```

**关键前提（必须主动说清楚）**：

> **偏差大 ≠ 标注一定错**，也可能是模型确实差。
> **所以复核必须由人做，模型只负责排序**——它的作用是把有限的人力集中到最可能有问题的地方。

**效率对比**：

```
人工全量清查 50 万帧      →  不可能
模型排序后复核 top 5000 帧 →  几个人几天，覆盖绝大部分严重错标
```

### 学界的对应方法

| 方法 | 思路 |
|---|---|
| **Confident Learning**（Northcutt et al., JAIR 2021） | 用模型的预测概率估计标注错误的联合分布，理论上有保证。开源实现 **cleanlab** |
| Loss-based 筛选 | 训练时 loss 一直很高的样本，大概率是错标 |
| Co-teaching（Han et al., NeurIPS 2018） | 两个网络互相筛选干净样本训练 |
| 交叉验证反查 | K 折交叉验证，用没见过该样本的模型来判断它 |
| 多标注员一致性 | 同一批数据多人标注，取不一致的部分复核 |

> **你做的"模型反查 + 人工复核"，本质上就是 Confident Learning 的工程化简化版。** 这个对应关系值得知道——它说明这个做法不是土办法，是有理论支撑的标准做法。

### 前置管理（比补救更重要）

| 措施 | 说明 |
|---|---|
| 标注规范 + 图示 | 每条规则配正例 / 反例 / 边界案例 |
| 金标准集考核 | 标注员上岗前必须通过 |
| **预标注模型** | 用离线大模型出初始框，人工只做修正，效率和一致性都更高 |
| 逐批抽检 | 每批交付抽 5–10%，不合格整批返工 |
| 一致性度量 | 多人标同一批，算 IoU 一致性 / Kappa |
| 争议案例评审 | 定期评审，结论更新进规范 |

## 0.9 工程实现与性能 ★☆☆

### 数据量级

```
一次全量回归：
  用例数      50+ 专题，数百条 case
  总帧数      10 万 – 50 万帧
  单帧目标数  10 – 100 个
  匹配计算    单帧 O(n×m)，全量数亿次
```

### 性能优化手段

| 手段 | 说明 |
|---|---|
| **多进程并行** | 按 case / clip 切分，`multiprocessing.Pool`。评测天然是尴尬并行 |
| **NumPy 向量化** | 3D IoU、距离矩阵的批量计算，避免 Python 循环。**这是最大的单点优化** |
| pandas 聚合 | 结果统计用 groupby，比手写循环快一个数量级 |
| 缓存推理结果 | 推理和评测解耦，同一份推理结果可跑多套 checker |
| 增量评测 | 只跑受影响的用例（调试时用） |
| 结果落库 | 历史结果持久化，支持任意两版本对比 |

**向量化的威力**：

```python
# 慢：Python 双重循环，1000×1000 需要数十秒
for p in preds:
    for g in gts:
        iou[i][j] = compute_iou_3d(p, g)

# 快：批量计算 BEV 交集面积 + 高度交叠，NumPy 广播，毫秒级
iou_matrix = batch_iou_3d(pred_boxes, gt_boxes)   # (N, M)
```

### 可重复性（评测系统的基本要求）

- 相同输入必须给出相同输出
- 配置、代码版本、数据版本都要记录在结果里
- **基线结果冻结存档，不能被覆盖**

否则会出现"上周跑的结果和这周不一样"这种无法排查的情况。

### 可视化与看板

**推理可视化网页化前后的对比**：

```
优化前：想看某个 case 的推理结果
       → 本地拉数据（几 GB）→ 本地跑推理 → 本地起可视化脚本 → 逐帧翻看
       每次几十分钟，且只有会用脚本的人能做

优化后：浏览器打开 → 选 case → 直接看渲染好的 BEV + 多相机视图 + 时序曲线
```

**收益**：降低门槛（测试、产品、规控同事都能自己看）、加速定位（问题单可直接附链接）、跨版本对比（同一 case 两个版本并排看）、沟通成本（从"我描述给你听"变成"你自己看"）。

**看板最有价值的功能是「从数字下钻到帧」**——看到一个恶化的数字，能一路点到具体哪些帧失败了、失败时的可视化是什么样。这把"指标掉了"变成"我知道为什么掉了"。

**Q1 · 为什么需要框架？**

`原理`　**因为判定规则异构，但流程同构。**

九类问题的**判定逻辑完全不同**（误检看有没有多报、3D 不稳看跨帧抖动、时延看首次稳定的帧数），但它们的**流程是一样的**：加载数据 → 时间戳对齐 → 目标匹配 → 判定 → 统计汇总。

如果每个问题各写一个脚本：

- 公共逻辑（对齐、匹配）被复制 N 份，改一处要改 N 处
- 各脚本的匹配口径可能不一致，**指标之间不可比**
- 加新问题类型要从头写一遍
- 一个对齐的 bug 修一次只能修一个脚本

`口语`　因为这些问题的判定规则完全不一样，但流程是一样的。误检看有没有多报，3D 不稳看跨帧抖动，时延看首次稳定的帧数——判定逻辑各不相同；但都要经过加载数据、时间戳对齐、目标匹配、判定、统计这几步。
如果每个问题各写一个脚本，公共逻辑会被复制很多份，改一处要改很多处；而且各脚本的匹配口径可能不一致，指标之间就不可比了。最麻烦的是一个对齐的 bug 修一次只能修一个脚本。

**Q2 · 基类怎么设计？**

`原理`

```python
class BaseChecker:
    """所有 checker 的基类，封装公共流程"""

    def run(self, pred_seq, gt_seq, case_config):
        # ---- 公共流程（基类实现，子类不碰）----
        aligned = self.align_timestamp(pred_seq, gt_seq)   # 时间戳对齐
        matched = self.match(aligned, case_config)         # 目标匹配
        # ---- 判定（子类实现的唯一部分）----
        results = self.check(matched, case_config)
        # ---- 公共统计 ----
        return self.aggregate(results, case_config)

    def align_timestamp(self, pred, gt): ...   # 最近邻对齐 + 缺帧统计
    def match(self, aligned, cfg): ...         # 分类别匹配策略
    def aggregate(self, results, cfg): ...     # 帧级 / case 级通过率

    def check(self, matched, cfg):
        raise NotImplementedError              # 子类必须实现


class FalsePositiveChecker(BaseChecker):
    def check(self, matched, cfg):
        # 只需要写"什么算误检"这一件事
        ...

class UnstableChecker(BaseChecker):
    def check(self, matched, cfg):
        # 只需要写"什么算不稳"这一件事
        ...
```

**四个收益**：

| 收益 | 说明 |
|---|---|
| 加新问题成本极低 | 只写判定逻辑（几十行），不碰数据加载、对齐、匹配、统计 |
| 公共逻辑只有一份实现 | 时间戳对齐的 bug 修一次，所有 checker 受益 |
| **行为一致可比** | 所有 checker 的匹配口径相同，指标之间可以横向对比 |
| 易于测试 | 公共流程和判定逻辑可以分别单测 |

`口语`　核心是把所有问题的共性抽出来，就是"匹配 → 判定 → 统计"这三步。基类负责数据加载、时间戳对齐、目标匹配和结果汇总这些公共逻辑，子类只实现判定这一步，暴露成一个独立接口。
这样加一个新问题类型，只要写判定逻辑和配一份阈值，不用碰公共流程。而且所有 checker 的匹配口径是一样的，指标之间才可以横向对比。

**Q3 · 为什么阈值要做成用例级配置？**

`原理`　**因为同一个 checker 在不同用例下的容忍度不同。**

```
市区用例：车速低、目标近、精度要求高 → 位置误差容忍 0.3m
高速用例：车速高、目标远、几何精度天然差 → 位置误差容忍 1.0m
地库用例：低速、狭窄 → 误检零容忍
```

**如果把阈值写死在代码里**，每加一个用例就要改代码，很快会失控（要么代码里堆满 if-else，要么复制出无数个 checker 变体）。

**分两层配置**：

```yaml
# 第一层：checker 默认配置
checker_defaults:
  false_positive:
    iou_threshold: 0.4
    confidence_threshold: 0.3
    tolerate_fail_frames: 2
  unstable:
    size_error_threshold: 0.3      # 尺寸相对误差
    yaw_error_threshold: 0.26      # rad，约 15°
    center_jitter_threshold: 0.5   # m

# 第二层：用例级覆盖
cases:
  - name: "地库_闸机_凭空误检"
    checkers: [false_positive, unstable]
    overrides:
      false_positive:
        confidence_threshold: 0.2   # 地库误检零容忍，阈值调低更严格
        tolerate_fail_frames: 0     # 一帧都不能错
```

> **核心设计原则：阈值是配置，不是代码。** 新增用例只需要加一段 YAML，不改任何 Python。

`口语`　因为同一个 checker 在不同用例下容忍度不一样。市区车速低、目标近，位置误差可能容忍三十厘米；高速车速高、目标远，几何精度天然差，可能要放到一米；地库的误检是零容忍的。
如果阈值写死在代码里，每加一个用例就要改代码，很快就失控了——要么代码里堆满 if-else，要么复制出一堆 checker 变体。所以做了两层配置，一层是 checker 级的默认阈值，一层是用例级的覆盖。加新用例只要加一段 YAML，不碰代码。

**Q4 · checker 之间怎么划分？**（考设计原则）

`原理`　**正交性：每个 checker 只负责一件事，彼此不重叠。**

**反例（不好的设计）**：

```
❌ check_quality()  ← 同时判断误检、位置精度、尺寸精度
```

问题：这个 checker 失败了，你不知道是哪个维度失败的，无法定位。

**正确做法**：

```
✓ check_fp()       ← 只判断有没有凭空检出
✓ check_center()   ← 只判断中心位置误差
✓ check_size()     ← 只判断尺寸误差
```

**正交的价值**：diff 报表能精确指出恶化发生在哪个维度，而不是给一个笼统的"质量下降"。

`口语`　原则是正交——每个 checker 只负责一件事，彼此不重叠。反面例子是做一个"质量检查"的 checker，同时判误检、位置精度、尺寸精度，这样它失败了你不知道是哪个维度失败的，没法定位。
拆开之后，diff 报表能精确指出恶化发生在哪个维度，而不是给一个笼统的"质量下降"。

**Q7 · 怎么保证 checker 本身是对的？**（很好的追问）

`原理`　**评测系统本身也需要被测试**，否则你在用一把不准的尺子量东西。

| 手段 | 说明 |
|---|---|
| **单元测试** | 构造已知答案的 pred/gt 对，验证 checker 输出符合预期 |
| **边界用例** | 完全重合、完全不重合、恰好在阈值上、空输入、只有 pred 没有 gt |
| **人工交叉验证** | 抽一批 checker 判定的结果，人工看可视化确认判得对不对 |
| **可重复性** | 同一输入必须给出同一输出（记录配置、代码版本、数据版本） |
| **指标间的一致性检验** | 比如 TP+FN 应该等于真值总数，不等就说明匹配有 bug |

`口语`　评测系统本身也要测，不然你是在用一把不准的尺子量东西。主要几条：一是单元测试，构造已知答案的预测和真值验证输出；二是边界用例，完全重合、完全不重合、恰好卡在阈值上、空输入这些都要覆盖；三是人工交叉验证，抽一批判定结果看可视化确认判得对不对；四是可重复性，同一份输入必须给出同一份输出；五是指标之间的一致性检验，比如 TP 加 FN 应该等于真值总数，不等就说明匹配有 bug。

**Q1 · 时间戳对齐**

`原理`　真值按标注帧给出（可能 2Hz 抽帧），预测有自己的时间戳（10Hz），中间还会偶发缺帧。

**错误做法**：按索引顺序配对。一旦丢一帧，后面**全部错位**，指标崩掉且**没有报错**，极难排查。

**正确做法**：最近邻匹配 + 时间窗过滤。

```python
for gt in gt_seq:
    nearest = min(pred_seq, key=lambda p: abs(p.ts - gt.ts))
    if abs(nearest.ts - gt.ts) <= time_window:   # 如 50ms
        pairs.append((nearest, gt))
    else:
        missing.append(gt)
```

`口语`　真值是按标注帧给的，模型推理输出有自己的时间戳，两边不一定对齐，而且偶尔会缺帧。不能按索引顺序配对——一旦丢一帧，后面全部错位，指标会莫名其妙崩掉，而且不报错，非常难查。
正确做法是做最近邻匹配，超出一定时间窗的就不配对。

**Q3 · 行人为什么 IoU 失效？**（必须用数字）

`原理`

```
行人框：0.6m × 0.6m × 1.7m
中心横向误差 0.3m

→ 重叠区域只剩一半宽度
→ IoU ≈ 0.2，低于 0.4 阈值 → 判为漏检
```

**中心只偏了 30cm，IoU 就掉到 0.2。** 但从感知使用的角度，**这个检出完全有效**——规控知道那里有个行人，30cm 不影响任何决策。

**根本问题**：

> **用一个 IoU 阈值，把"有没有检出"和"位置准不准"这两件事混在了一起。**

**正确做法**：分开看。

```
"有没有检出" → 中心点距离匹配
"位置准不准" → 匹配成功后单独统计中心 / 尺寸 / 朝向误差
```

`口语`　3D IoU 对小目标特别敏感。行人的框本身就小，大概 0.6 米见方，中心偏个 30 厘米，重叠区域只剩一半宽度，IoU 就从 0.5 掉到 0.2 了，低于阈值就判成漏检。但从感知使用的角度，这个检出其实是有效的——规控知道那儿有个行人，30 厘米的误差不影响任何决策。
根本问题是用一个 IoU 阈值把"有没有检出"和"位置准不准"这两件事混在一起了。所以行人改成中心点距离匹配，判定检没检出来和位置准不准分开看。

**Q5 · 跨类等价集**

`原理`　**问题**：类别边界本身模糊，模型和标注员判断可能不一致。模型把卡车判成电车，严格按类别匹配就是"漏检卡车 + 误检电车"——**一次错误被记成两次**，而这个错误对下游几乎没有影响（都是大型障碍物，规控处理方式一样）。

**解法**：

```yaml
equivalence_groups:
  large_vehicle:  [TRUCK, TRAM, BUS]
  two_wheeler:    [CYCLIST, TRICYCLE, MOTORCYCLE]
  small_vehicle:  [CAR, VAN]
```

同组内混淆**不计为误检/漏检**，但**单独统计为"类别混淆"**——既不虚高地惩罚，也不隐藏问题。

`口语`　类别边界本身就模糊，卡车和电车远距外观很像，骑行人和三轮车也容易混。如果严格按类别匹配，模型把卡车判成电车就算漏检一个卡车加误检一个电车，一次错误记成两次，而这个错误对下游几乎没影响——都是大型障碍物，规控的处理方式一样。
所以设了跨类等价集，同组内的混淆不计为误检漏检，但单独统计成"类别混淆"，既不虚高地惩罚，也不把问题藏起来。

**Q7 · 3D 旋转框 IoU 怎么算？**（手撕代码高频题）

`原理`　不能用轴对齐框的公式。标准做法是**分解为 BEV 交集 × 高度交集**：

```
① BEV 平面交集面积
   两个旋转矩形求交 → 凸多边形裁剪（Sutherland-Hodgman 或 shapely）
   → 交集多边形 → 面积 A_inter

② 高度方向交集
   h_inter = max(0, min(z1_top, z2_top) − max(z1_bot, z2_bot))

③ 体积
   V_inter = A_inter × h_inter
   V_union = V1 + V2 − V_inter
   IoU_3D  = V_inter / V_union
```

**BEV IoU vs 3D IoU**：很多场景只用 BEV IoU（忽略高度），因为自动驾驶关心平面位置关系、高度的标注和预测都不准、计算更快。

`口语`　3D 框在 BEV 平面上是带朝向的矩形，不能用轴对齐的公式。标准做法是分解成 BEV 交集乘高度交集：BEV 平面上两个旋转矩形求交，用凸多边形裁剪算出交集面积；高度方向就是两个区间的交集长度；两者相乘得体积交集，再算并集，相除就是 3D IoU。
实际很多场景只用 BEV IoU，忽略高度——因为自动驾驶关心的是平面位置关系，高度的标注和预测都不太准，而且计算更快。

---

**Q8 · 贪心还是匈牙利？**

`原理`

| 算法 | 复杂度 | 特点 |
|---|---|---|
| 贪心 | O(n²) | 按 IoU/距离降序依次配对。简单快速，可能非全局最优 |
| **匈牙利** | O(n³) | 全局最优，`scipy.optimize.linear_sum_assignment` |

单帧目标数通常几十个，两者都很快，**匈牙利更严谨**。注意匈牙利要求代价矩阵完整，"不允许匹配"的组合（超阈值、类别不等价）要设成极大代价。

`口语`　单帧目标数一般就几十个，贪心和匈牙利都很快，我们用匈牙利更严谨一些，直接用 scipy 的 linear_sum_assignment。有个细节是匈牙利要求代价矩阵是完整的，对于不允许匹配的组合——超出阈值的、类别不等价的——要设成一个极大的代价，不然它会强行配上。

**Q9 · 和 nuScenes 官方什么关系？**（这条很值钱）

`原理`　**思路一致，不是我们独创。**

> nuScenes 官方评测的 mAP 使用**中心距离**匹配（阈值 0.5 / 1 / 2 / 4m 取平均），而不是 3D IoU。官方理由：
> 1. IoU 对小目标过于苛刻
> 2. IoU 无法区分"检到了但位置略偏"和"完全没检到"
> 3. 中心距更符合下游需求
>
> 匹配成功后再单独统计 mATE / mASE / mAOE / mAVE / mAAE 五项误差。

**这是"匹配"与"精度"解耦的典范**，也是我们分类别匹配策略的理论依据。

`口语`　这个思路不是我们独创的，nuScenes 官方评测就是这么设计的——它的 mAP 用的是中心距离匹配，不是 3D IoU，阈值取 0.5、1、2、4 米四档取平均。官方给的理由跟我们一样：IoU 对小目标太苛刻，而且无法区分"检到了但位置略偏"和"完全没检到"。匹配成功之后再单独统计平移、尺寸、朝向、速度、属性五项误差。
所以这套"匹配与精度解耦"的做法是有公开基准背书的。

**Q2 · 跨帧关联怎么建立？**

`原理`

```
真值侧：标注本身带 track_id（同一目标跨帧一致）
预测侧：
   方案 A：模型输出带跟踪 ID（如果有跟踪模块）
   方案 B：评测时自己做关联
          （帧内匹配 pred↔gt，再借 gt 的 track_id 把 pred 串起来）
```

**方案 B 的巧妙之处**：不需要自己实现跟踪器——先在每一帧把预测和真值匹配上，然后**借用真值的 track_id** 就能把预测串成序列。

⚠️ **待核实**：你们用的是哪个方案。

`口语`　真值侧标注本身带 track_id，同一个目标跨帧是一致的。预测侧有两种做法：如果模型输出带跟踪 ID 就直接用；如果不带，评测的时候自己做关联——先在每一帧把预测和真值匹配上，然后借用真值的 track_id 把预测串成序列，这样就不用自己实现一个跟踪器。具体我们用的哪种我回去确认一下。

**Q3 · 首帧检出距离 vs 触发时延**

`原理`　**两个不同的指标，容易混**：

| 指标 | 定义 | 适用场景 | 单位 |
|---|---|---|---|
| **首帧检出距离** | 目标从远处接近，连续 N 帧稳定检出时，首次稳定那刻的距离 | **远距目标逐渐接近**（高速车辆、施工区） | 米 |
| **触发时延** | 目标首次可见（真值出现且可见性 > 阈值）→ 连续 N 帧稳定输出 | **目标突然出现**（鬼探头、遮挡后窜出） | 帧数 / 毫秒 |

**区别的本质**：前者衡量"能看多远"，后者衡量"反应多快"。

> **项目一的 131.5m 和项目二的 89m→114m，都是「首帧检出距离」这个 checker 的输出，口径完全一致。**

`口语`　这是两个不同的指标。首帧检出距离是目标从远处慢慢接近，连续几帧稳定检出时记录那一刻的距离，衡量的是"能看多远"，适用于高速车辆、施工区这种。触发时延是目标突然出现，从真值里首次可见到模型连续几帧稳定输出的时间，衡量的是"反应多快"，适用于鬼探头、遮挡后窜出这种。
项目一那个 131.5 米和锥桶那个 89 到 114 米，都是首帧检出距离这个 checker 出的，口径是一样的。

**Q4 · 动静跳变怎么统计？**

`原理`

```
对每个 track：
  统计属性序列 [静, 静, 动, 静, 动, 动, 静, ...]
  跳变次数 = 相邻帧属性不同的次数
```

**要处理的细节**：

- **真实的状态变化不算跳变**——车起步、刹停是真实的动静转换，需要和真值对比，只统计**与真值不符的**翻转
- **容忍窗口**——状态转换的临界期（速度在阈值附近）允许几帧不一致
- **单帧误判 vs 持续误判**——单帧翻转和连续 10 帧误判的严重性完全不同

`口语`　对每个 track 统计属性序列，数相邻帧属性不同的次数。但要处理几个细节：一是真实的状态变化不算跳变，车起步、刹停是真实的动静转换，得跟真值对比，只统计与真值不符的翻转。二是状态转换的临界期，速度在阈值附近的时候允许几帧不一致。三是单帧误判和连续误判的严重性完全不同，要分开统计。

**Q5 · 区域 checker 为什么不需要标注？**（**这条是这个项目最聪明的设计**）

`原理`　**传统 checker 都需要真值，而真值标注是最贵、最慢的环节。**

区域入侵判定只需要**预测结果 + 几何定义**：

```
在自车坐标系下定义若干危险区域：
  · 正前方 0–5m 的紧急制动区
  · 左右侧的变道盲区
  · 倒车时的后方区域

判定：预测框与区域的几何交叠 → 判定为"目标入侵该区域"
```

**为什么这个设计有巨大价值**：

> 因为不需要真值，它可以**在任何数据上跑，包括海量的无标注路测数据**。

于是它变成一个**大规模筛查工具**：在百万帧无标注数据上跑，找出所有"报告有目标侵入紧急制动区"的片段，人工快速过一遍就能发现大量误检。

```
标注成本：3D 框标注 10–50 元/帧
区域 checker：0 元，只要有推理结果
```

**这是一个用几何规则替代标注的典型例子——成本极低而覆盖极广。**

`口语`　传统的 checker 都要有真值才能判，而真值标注是最贵最慢的一环。区域入侵这个 checker 只需要预测结果加上几何定义——在自车坐标系下定义几个危险区域，比如正前方五米内的紧急制动区、左右侧的变道盲区，然后看预测框跟区域有没有交叠。
它的价值在于不需要标注，所以可以在任何数据上跑，包括海量的无标注路测数据。这就变成了一个大规模筛查工具——在百万帧无标注数据上跑，把所有"报告有目标侵入紧急制动区"的片段找出来，人工快速过一遍就能发现大量误检。3D 标注一帧要几十块，这个是零成本。

**Q6 · 区域怎么定义的？**

**Q7 · 能借鉴 MOT 的哪些指标？**

`原理`　MOT（多目标跟踪）领域有一套成熟的时序指标，可以直接借用：

| 指标 | 含义 |
|---|---|
| **MOTA** | 综合 FP、FN、IDSW 的准确度：`1 − (FP+FN+IDSW)/GT` |

MT 和 ML 特别有用，它直接回答有多少目标是基本能稳定跟住的、多少是基本跟不住的，比平均召回更能反映时序稳定性。

**Q3 · 还有别的挖法吗？**

**Q4 · 挖出来之后怎么处理？**

`原理`

```
① 候选片段（可能几万帧）
② 自动去重 ← 关键
③ 人工快速筛查（几秒/帧，确认确实是目标场景）
④ 送标注（3D 框，最贵的一环，市价 10–50 元/帧）
⑤ 标注质检
⑥ 构造专项训练集 / 评测集
⑦ 回灌训练 → 评测验证是否收敛
```

**去重为什么关键**：10Hz 采样下相邻帧几乎相同。不去重会花大量标注预算买重复信息，还会让训练分布偏斜。

常见去重方式：时间间隔采样、特征相似度聚类、场景多样性采样。

`口语`　挖出来是候选，可能有几万帧。先自动去重——十赫兹采样相邻帧几乎一样，不去重会花大量标注预算买重复信息，还会让训练分布偏斜。然后人工快速筛查，几秒钟一帧，确认确实是目标场景。再送标注，这是最贵的一环，3D 标注市价一帧几十块。标完质检，构造专项训练集和评测集，回灌训练，再评测验证这个问题有没有收敛。

**Q5 · 推理反查标注怎么筛？**

`原理`　**把模型当成"第二标注员"。**

```
① 用当前最好的模型跑全量训练集推理
② 预测与标注做匹配
③ 挑出偏差最大的帧：
   · 模型高置信度检出，但标注里没有  → 疑似漏标
   · 标注里有，但模型完全没响应       → 疑似多标 / 噪声目标
   · 匹配上了但尺寸/朝向差异巨大      → 疑似框标错
   · 朝向差约 180°                   → 高度疑似反向错标
④ 按偏差排序，推给人工复核
⑤ 复核结论回写，修正标注
```

**朝向差 180° 这条要单独提**——这是 3D 标注最常见也最有害的错误之一（速度方向全反），而且用规则一抓一个准。

`口语`　思路是把模型当成第二个标注员。跑完全量推理之后，把预测和标注做匹配，挑出偏差最大的那些帧——模型高置信度检出但标注里没有的，可能是漏标；标注有但模型完全没响应的，可能是多标或者噪声目标；匹配上了但尺寸朝向差得离谱的，可能是框标错了。
还有一类特别值得单独抓：朝向差大约 180 度的。这是 3D 标注里最常见也最有害的错误之一，速度方向全反了，而且用规则一抓一个准。

**Q5 · 帧通过率 vs case 通过率**

`原理`

| 口径 | 定义 | 用途 |
|---|---|---|
| **帧通过率** | 通过帧数 / 总帧数 | 细粒度，反映问题的普遍程度 |
| **case 通过率** | 通过用例数 / 总用例数 | 粗粒度，直接对应"有几个问题没解决" |

**为什么两个都要**：

- 一个 case 里 99% 的帧通过、1% 失败 → 帧通过率很好看，但**这个 case 本身是失败的**（那 1% 就是问题所在）
- 反过来，case 通过率不能反映失败的严重程度（失败 1 帧和失败 100 帧在 case 层面一样）

`口语`　帧通过率是通过的帧数除以总帧数，反映问题的普遍程度；case 通过率是通过的用例数除以总用例数，直接对应有几个问题没解决。
两个都要，因为它们互相补。一个 case 里百分之九十九的帧通过、百分之一失败，帧通过率很好看，但这个 case 本身是失败的，那百分之一就是问题所在。反过来 case 通过率又反映不出失败的严重程度，失败一帧和失败一百帧在 case 层面是一样的。

```
|Δ| < 噪声阈值 → 判为"持平"
```

噪声阈值必须通过**同配置多次重训实测**得出，否则会有大量假阳性的"恶化"消耗排查时间。

`口语`　要先定噪声阈值。训练本身有随机性，同一份配置训两次指标可能差零点三到零点五个点，小于这个量的判成持平。这个阈值是拿同配置多次重训实测出来的，不能拍脑袋，不然会有一堆假的"恶化"，白白消耗排查时间。

**Q3 · 为什么这么严？**

`原理`

> **每一个历史 bad case 背后，可能都是一次真实的客诉甚至事故。允许它复现，等于让用户再经历一次。**

防护网用例集**只增不减**——每修好一个问题就加一条永久监控。**这个机制保证了模型能力单调不减。** 没有它，量产迭代会陷入"修好一个坏三个"的循环。

`口语`　因为每一个历史 bad case 背后可能都是一次真实的客诉甚至事故，允许它复现就等于让用户再经历一次。我们的用例集是只增不减的，每修好一个问题就加一条永久监控，这样才能保证模型能力单调不减。没有这个机制，迭代很容易陷入修好一个坏三个的循环。

**Q4 · 一项恶化但整体更好？**

`原理`　**分优先级**：

- **P0（安全相关）恶化** → 直接阻塞，没有商量余地
- **P1 恶化** → 需要评审：说明原因、评估影响面、给出后续计划，评审通过才能带着这个恶化项上
- **P2** → 记录，允许暂时不通过

实践中大部分 P1 恶化的结论是"这一版先不合入，下一版一起解"。

`口语`　分优先级。安全相关的恶化直接阻塞，没商量。体验类的要评审，说清楚原因、影响面和后续计划，评审通过才能带着这个恶化项上。长尾的可以记录、暂时允许不通过。实际上大部分情况的结论是这一版先不合入，下一版一起解。

**Q5 · 系统级测试 vs 自验**

`原理`

| | 自验（你做的） | 系统级测试 |
|---|---|---|
| 对象 | 感知模型单模块 | 整车、全链路 |
| 数据 | 离线数据集、防护网用例 | 实车路测、场景库 |
| 执行方 | **你** | 测试团队 |
| 目的 | 决定能不能**送测** | 决定能不能**上车** |

`口语`　我做的自验是模型单模块的，跑离线数据集和防护网用例，决定这一版能不能送测。系统级测试是测试团队做的，是整车全链路的，实车路测加场景库，决定能不能上车。我的自验是送测的准入门槛，过不了就不往下走。

# 使用建议

## 这个项目怎么讲才不被低估

**核心话术**：被问「你做的是不是就是写测试脚本」时——

> 从代码形态上确实是脚本，但它的定位不一样：**这套东西是版本能不能送测的准入依据，不是可有可无的辅助工具**。量产迭代很快，mAP 这种整体指标回答不了两个最关键的问题——路测反馈的历史问题这一版有没有复现、候选版本到底能不能上车。我们建的是感知模型的回归测试体系，用例集只增不减，每修好一个问题就加一条永久监控，这样才能保证模型能力单调不减。

**三个最能立住的点**：

| 点 | 为什么能立住 |
|---|---|
| **行人中心距匹配** | **nuScenes 官方评测就是这么设计的**，理由完全一致 |
| **区域 checker 免标注** | 用几何规则替代标注，零成本大规模筛查，这是个聪明的设计 |
| **推理反查标注** | 对应 Confident Learning，有理论支撑，且引用了 ImageNet 错标率 5.8% 这个数据 |
