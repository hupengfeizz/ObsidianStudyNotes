## 1. 项目概况：这套体系在解决什么

| 项 | 内容 |
|---|---|
| **定位** | BEV 感知模型的评测体系 + 数据闭环基础设施 |
| **核心产出** | 场景化 checker 框架、防护网用例集、基线 diff 报表、难例挖掘与回灌链路、可视化看板 |
| **业务地位** | **版本送测的准入依据**——不是辅助工具，是流程上的强制闸门 |
| **周期** | 2024.08 – 至今 |
| **技术栈** | Python、NumPy / pandas、3D IoU 匹配、跨帧目标关联、多进程并行、数据湖检索、Flask + Vue |

### 1.1 一句话说清它的价值

量产感知每两三个月发一个版本。每个版本都会改动模型，而每次改动都可能：

- 修好一个问题，同时**弄坏三个已经修好的问题**；
- 整体指标持平，但**某个特定场景的误检翻倍**；
- 在测试集上更好，在**真实路测反馈的历史 case 上退步**。

**这套体系回答的是两个问题：**

> **① 路测反馈的历史问题，这一版有没有复现？**
> **② 这个候选版本，到底能不能送测？**

这两个问题，`mAP = 0.53` 一个字也答不了。

### 1.2 软件工程类比

这套东西本质上是**感知模型的回归测试体系（Regression Test Suite）**：

| 软件工程 | 本项目 |
|---|---|
| 单元测试 | 单个 checker |
| 测试用例 | 防护网用例（一个场景片段 + 一组预期） |
| 测试套件 | 防护网用例集（10+ 大类、50+ 专题） |
| CI / 门禁 | 版本准入回归 |
| 回归 bug | 历史问题复现 |
| golden test / 基准对比 | 基线 diff |
| 测试报告 | 通过率 + 优化 / 恶化 diff 报表 |
| bug 复现用例入库 | 路测问题 → 防护网用例 |

**最关键的类比是最后一条**：软件工程里，每修一个 bug 就补一条测试用例，保证它永不复现。这套体系做的就是同一件事——**每一个路测反馈的问题，都被固化成一条防护网用例，从此永久监控。**

用例集只增不减，随版本累积。这就是"防护网"这个名字的来源。

## 2. 为什么 mAP 回答不了量产的问题

### 2.1 mAP 的数学性质决定了它会掩盖长尾

mAP 是在整个测试集上的平均量。假设：

```
测试集 100,000 帧
其中地库闸机场景     200 帧（占 0.2%）
新版本在这 200 帧上误检数从 2 次涨到 8 次
在其余 99,800 帧上略有提升
```

**结果**：mAP 上涨。**实际**：地库误刹频率翻了 4 倍，用户会立刻感知到。

**平均量对小比例子群的变化不敏感**——这是数学性质，不是指标设计得不好。学术评测追求的是模型的整体能力排序，量产追求的是**不能在任何一个已知场景上退步**，两者的目标函数根本不同。

### 2.2 三组对照

| 维度 | 学术指标（mAP / NDS） | 量产防护网 |
|---|---|---|
| 回答的问题 | 这个模型整体水平如何 | **这个版本能不能上车** |
| 统计对象 | 整个测试集的平均 | **每一个具体场景的具体问题** |
| 粒度 | 标量 | **分层 diff 报表** |
| 判据 | 越高越好 | **任一项恶化即不准入** |
| 数据来源 | 固定的公开集 | **真实路测反馈，持续累积** |
| 用途 | 横向比模型 | **纵向比版本** |

### 2.3 两者是互补不是替代

- **mAP / NDS**：适合横向对比不同模型、不同技术路线，回答"我们的模型比竞品强吗"；
- **防护网**：适合纵向对比版本，回答"这次改动引入了什么副作用"。

**量产团队两套都要有。** 只有 mAP，会漏掉长尾退化；只有防护网，会失去对整体能力的把握（用例集里的场景毕竟是有限的，可能整体能力下降但恰好没触发任何用例）。

### 2.4 量产真正关心的问题类型

| 问题类 | 业务后果 |
|---|---|
| **凭空误检（FP）** | 误刹 —— 最严重 |
| **漏检（FN）** | 追尾 / 未减速 |
| **3D 不稳** | 框抖动，规控轨迹抖，乘客不适 |
| **动静误判** | 静止判动 → 无谓减速；动态判静 → 危险 |
| **速度误差** | 跟车距离错、变道时机错 |
| **检出时延（鬼探头）** | 目标出现到稳定输出的延迟，直接决定能不能刹住 |
| **检出距离** | 决定能多早发起变道 |
| **AEB 误 / 漏触发** | 最高优先级的安全项 |
| **区域入侵** | 自车周围危险区域内是否有目标 |

**这 9 类问题的判定逻辑完全不同**——这就是 checker 框架要解决的第一个难点。

## 3. 体系全景：四段闭环

```
                    ┌─────────────────────────────────────┐
                    │                                     │
                    ↓                                     │
        ┌───────────────────────┐                         │
        │  ① 场景 checker       │  单个问题的判定逻辑      │
        │  check_fp / check_fn  │                         │
        │  check_unstable ...   │                         │
        └───────────┬───────────┘                         │
                    ↓                                     │
        ┌───────────────────────┐                         │
        │  ② 防护网用例集        │  路测问题 → 用例       │
        │  10+ 大类 50+ 专题     │  只增不减，永久监控     │
        └───────────┬───────────┘                         │
                    ↓                                     │
        ┌───────────────────────┐                         │
        │  ③ 基线 diff          │  与冻结基线逐项对比      │
        │  通过率 + 优化/恶化    │  → 版本准入判定         │
        └───────────┬───────────┘                         │
                    ↓                                     │
        ┌───────────────────────┐                         │
        │  ④ 难例挖掘与回灌      │  失败 case → 数据       │
        │  数据湖检索 → 送标     │  → 训练 → 新版本 ───────┘
        │  → 训练集             │
        └───────────────────────┘
```

**这是一个真正的闭环**：

- **评测发现问题** → 问题定位到具体场景 → **挖掘同类数据** → 标注回灌 → **训练新版本** → 再评测 → 该问题变成永久监控的用例。

每转一圈，模型变强一点，用例集变厚一点，覆盖的长尾变多一点。

> 这正是特斯拉所说的 **Data Engine** 的思路：模型的能力上限不由结构决定，由**数据闭环转动的速度**决定。

### 3.1 与项目一的关系

**项目一和项目三是一条闭环的两半**：

```
项目一：发现问题 → 定位 → 做优化
项目三：验证优化有没有效、有没有副作用 → 供给下一轮数据
```

比如项目一里"用时序判据挖掘凭空误检难例"这件事，**挖掘工具和回灌链路就是项目三建的**。两个项目串起来讲，是一个完整的量产迭代方法论。

## 4. checker 框架设计

> `▸ 你的位置`：框架设计与开发由你负责。

### 4.1 要解决的问题：判定规则异构

**难点**：9 类问题的判定逻辑完全不同。

| 问题 | 判定逻辑 |
|---|---|
| 误检 | 预测有、真值无 → 但要排除"真值漏标"的情况 |
| 漏检 | 真值有、预测无 → 但要考虑遮挡、超出探测范围 |
| 3D 不稳 | 跨帧的框尺寸 / 朝向抖动超过阈值 |
| 动静 | 属性判定与真值不符，且持续 N 帧 |
| 检出时延 | 目标进入视野到稳定输出的帧数 |
| 检出距离 | 首次稳定检出时的距离 |
| AEB | 是否在应该触发时触发、不该触发时未触发 |
| 区域入侵 | 目标框与自车周围危险区域的交叠 |

**更麻烦的是：同一个 checker 在不同用例下阈值不同。**

```
市区用例：车速低、目标近、精度要求高 → 位置误差容忍 0.3m
高速用例：车速高、目标远、几何精度天然差 → 位置误差容忍 1.0m
地库用例：低速、狭窄 → 误检零容忍
```

如果把阈值写死在代码里，每加一个用例就要改代码，很快就会失控。

### 4.2 解法：统一基类 + 判定接口 + 分层配置

**核心抽象：所有 checker 都是「匹配 → 判定 → 统计」三步。**

```python
class BaseChecker:
    """所有 checker 的基类，封装公共流程"""

    def run(self, pred_seq, gt_seq, case_config):
        # ---- 公共流程（基类实现，子类不碰）----
        aligned  = self.align_timestamp(pred_seq, gt_seq)   # 时间戳对齐
        matched  = self.match(aligned, case_config)         # 目标匹配
        # ---- 判定（子类实现的唯一部分）----
        results  = self.check(matched, case_config)
        # ---- 公共统计 ----
        return self.aggregate(results, case_config)

    def align_timestamp(self, pred, gt): ...   # 最近邻对齐 + 缺帧统计
    def match(self, aligned, cfg): ...         # 分类别匹配策略
    def aggregate(self, results, cfg): ...     # 帧级 / case 级通过率

    def check(self, matched, cfg):
        raise NotImplementedError   # 子类必须实现


class FalsePositiveChecker(BaseChecker):
    def check(self, matched, cfg):
        # 只需要写"什么算误检"这一件事
        ...

class UnstableChecker(BaseChecker):
    def check(self, matched, cfg):
        # 只需要写"什么算不稳"这一件事
        ...
```

**这个设计的价值**：

| 收益 | 说明 |
|---|---|
| **加新问题类型成本极低** | 只写判定逻辑（几十行），不碰数据加载、对齐、匹配、统计 |
| **公共逻辑只有一份实现** | 时间戳对齐的 bug 修一次，所有 checker 受益 |
| **行为一致可比** | 所有 checker 的匹配口径相同，指标之间可以横向对比 |
| **易于测试** | 公共流程和判定逻辑可以分别单测 |

### 4.3 分层配置

配置分两层，用例级覆盖 checker 级：

```yaml
# 第一层：checker 默认配置
checker_defaults:
  false_positive:
    iou_threshold: 0.4
    confidence_threshold: 0.3
    tolerate_fail_frames: 2
  unstable:
    size_error_threshold: 0.3      # 尺寸相对误差
    yaw_error_threshold: 0.26      # rad，约 15°
    center_jitter_threshold: 0.5   # m

# 第二层：用例级覆盖
cases:
  - name: "地库_闸机_凭空误检"
    scene: parking_garage
    checkers: [false_positive, unstable]
    overrides:
      false_positive:
        confidence_threshold: 0.2   # 地库误检零容忍，阈值调低更严格
        tolerate_fail_frames: 0     # 一帧都不能错

  - name: "高速_中远距_检出距离"
    scene: highway
    checkers: [detection_range, false_negative]
    overrides:
      false_negative:
        iou_threshold: 0.3          # 远距几何精度天然差，放宽
        distance_bins: [30, 60, 90, 120]
```

**关键设计原则：阈值是配置，不是代码。** 新增用例只需要加一段 YAML，不需要改任何 Python。

### 4.4 checker 的正交性

设计时的一条重要约束：**每个 checker 只负责一件事，彼此正交。**

反例（不好的设计）：

```
❌ check_quality()  ← 同时判断误检、位置精度、尺寸精度
```

问题是：这个 checker 失败了，你不知道是哪个维度失败的，无法定位。

正确做法：

```
✓ check_fp()        ← 只判断有没有凭空检出
✓ check_center()    ← 只判断中心位置误差
✓ check_size()      ← 只判断尺寸误差
```

**正交的好处**：diff 报表能精确指出恶化发生在哪个维度，而不是给一个笼统的"质量下降"。

## 5. 匹配层：整个评测最容易错的地方

> 这一层的 bug **最隐蔽、破坏力最大**——匹配错了，所有下游指标都是错的，而且错得看不出来。

### 5.1 时间戳对齐

**问题**：真值和预测的时间戳是异步的。

- 真值按标注帧给出（可能是 2Hz 抽帧标注）；
- 模型推理输出有自己的时间戳（10Hz）；
- 中间还会**偶发缺帧**（数据丢包、解码失败、推理超时）。

**错误做法**：按索引顺序配对（第 i 个预测配第 i 个真值）。一旦有一帧丢失，后面全部错位，指标会莫名其妙地崩掉，而且**极难排查**——因为没有报错，只是数字变差了。

**正确做法**：

```python
def align_timestamp(pred_seq, gt_seq, time_window=50):  # ms
    pairs, missing = [], []
    for gt in gt_seq:
        # 找时间戳最近的预测帧
        nearest = min(pred_seq, key=lambda p: abs(p.ts - gt.ts))
        if abs(nearest.ts - gt.ts) <= time_window:
            pairs.append((nearest, gt))
        else:
            missing.append(gt)     # 缺帧单独统计，不算漏检
    return pairs, missing
```

**最关键的一条**：**缺帧必须单独统计，不能默默算成漏检。**

如果缺帧被算成漏检：

- 指标变差了，但原因是数据管线故障不是模型问题；
- 你会花几天去查模型，最后发现是解码器丢了 3% 的帧。

> `▸ 你的经验`：这是你最早踩的坑之一。这类工程细节看起来琐碎，但对不齐的话整套评测结果都是错的，**而且错得很隐蔽**。

### 5.2 分类别匹配策略

**核心洞察：不同类别的目标，"检出算不算成功"的判据不一样。**

#### 车辆类：3D IoU

```
匹配条件：3D IoU ≥ 阈值（如 0.4）
```

车辆尺寸大（4.5m×1.8m×1.5m），IoU 是稳定可靠的判据。

#### 行人：中心点距离

**为什么 3D IoU 对行人失效**——用数字说话：

```
行人框：0.6m × 0.6m × 1.7m
中心位置误差 0.3m（横向）

IoU ≈ (0.6-0.3) / (0.6+0.3) × ... ≈ 0.2
```

**中心只偏了 30cm，IoU 就掉到 0.2，低于 0.4 的阈值 → 判为漏检。**

但从感知使用的角度看，**这个检出是完全有效的**——规控知道那里有个行人，30cm 的误差不影响任何决策。

**用一个 IoU 阈值，把"有没有检出"和"位置准不准"这两件事混在了一起。** 正确做法是分开：

```
"有没有检出"  → 中心点距离匹配（阈值按类别和距离段设定）
"位置准不准"  → 匹配成功后，单独统计中心误差、尺寸误差、朝向误差
```

**这个设计不是我们独创的——nuScenes 官方评测就是这么做的**：

> nuScenes 的 mAP 使用**中心距离**匹配（阈值 0.5 / 1 / 2 / 4m 取平均），而不是 3D IoU，官方给出的理由正是"IoU 对小目标过于苛刻，且无法区分'检到了但位置略偏'和'完全没检到'"。
> 匹配成功后再单独计算 mATE（平移误差）、mASE（尺寸误差）、mAOE（朝向误差）。

**中心距阈值怎么定**：

| 因素 | 说明 |
|---|---|
| 物理尺寸 | 行人 0.6m 宽，阈值取 0.5–1.0m 合理 |
| 下游容忍度 | 规控对行人的横向位置容忍是多少 |
| **距离分段** | **近处严、远处松**——远距几何精度天然差，用同一个阈值远距全是漏检 |

#### 跨类等价集

**问题**：类别边界本身就模糊，模型和标注员的判断可能不一致。

| 混淆对 | 说明 |
|---|---|
| TRUCK / TRAM | 大型车辆，远距外观相似 |
| CYCLIST / TRICYCLE | 骑行人与三轮车 |
| CAR / VAN | 小型车与面包车 |
| PEDESTRIAN / CYCLIST（推行状态） | 推着自行车走的人 |

如果严格按类别匹配，模型把卡车判成电车就算"漏检卡车 + 误检电车"——**一次错误被记成两次**，而且这个错误对下游几乎没有影响（都是大型障碍物，规控的处理方式一样）。

**解法：设跨类等价集**

```yaml
equivalence_groups:
  large_vehicle:  [TRUCK, TRAM, BUS]
  two_wheeler:    [CYCLIST, TRICYCLE, MOTORCYCLE]
  small_vehicle:  [CAR, VAN]
```

同组内的类别混淆**不计为误检 / 漏检**，但**单独统计为"类别混淆"**——这样既不虚高地惩罚，也不隐藏问题。

### 5.3 匹配算法本身

匹配是一个**二分图最优匹配**问题：

| 算法 | 复杂度 | 特点 |
|---|---|---|
| **贪心匹配** | O(n²) | 按 IoU / 距离降序，依次配对已匹配的跳过。简单快速，可能非全局最优 |
| **匈牙利算法**（Kuhn-Munkres） | O(n³) | 全局最优。`scipy.optimize.linear_sum_assignment` |

**实践中的选择**：单帧目标数通常几十个，两者都很快，匈牙利更严谨。但要注意**匈牙利要求代价矩阵完整**，对于"不允许匹配"的组合（如超出阈值、类别不等价）要设成极大代价。

### 5.4 距离分段统计

```
所有指标按 [0-30m] / [30-60m] / [60-90m] / [90m+] 分段统计
```

**为什么必须分段**：

1. 目标数量分布极不均匀——**80% 以上的目标在 50m 以内**。不分段的话，整体指标基本等于近距指标，远距的问题被完全淹没；
2. 不同距离段的**难度和容忍度完全不同**；
3. 项目一里"分距离段评测定位中远距劣化"这件事，**依赖的就是这个能力**。

> `▸ 项目一与项目三的连接点`：项目一的第一步"分距离段评测确认劣化主要在中远距"，用的就是这套评测体系。

## 6. 判定层：各类 checker 详解

### 6.1 check_fp（误检）

```
判定：预测框在真值中找不到匹配 → 候选误检
```

**必须处理的排除项**：

| 情况 | 处理 |
|---|---|
| 真值漏标 | 真值本身不完整（尤其远距、遮挡目标），需要人工复核后加白名单 |
| 超出标注范围 | 标注只标了 ±50m，模型检出 60m 的真车不算误检 |
| 置信度过低 | 低于下游使用阈值的预测不参与评测 |
| 目标类型不在评测范围 | 如锥桶、水马等静态物 |

**统计口径**：绝对次数（不是率）。因为误检是安全事件，一次就是一次，用率会被大量正常帧稀释。

### 6.2 check_fn（漏检）

```
判定：真值框在预测中找不到匹配 → 候选漏检
```

**必须处理的排除项**：

| 情况 | 处理 |
|---|---|
| 完全遮挡 | 真值标注里通常有 visibility 字段，完全不可见的不算漏检 |
| 超出探测范围 | 模型设计探测范围外的目标 |
| 点数过少 | 激光点数少于阈值的真值目标（可能是噪声） |
| 截断严重 | 只有一角在视野内 |

### 6.3 check_unstable（3D 不稳）

**这是一个纯时序 checker**，单帧无法判定。

```
对同一个跟踪 ID 的目标，跨帧统计：
  · 尺寸抖动：相邻帧 (l,w,h) 的相对变化 > 阈值
  · 朝向抖动：yaw 变化 > 阈值（注意角度周期性，359°→1° 是 2° 不是 358°）
  · 中心跳变：位置变化超出物理可能（速度 × Δt）
  · 类别翻转：同一目标的类别标签在帧间切换
```

**为什么重要**：框抖动会直接传导到规控——预测轨迹抖 → 控制指令抖 → 乘客感觉车在"犹豫"。这是体验类问题里最高频的一个。

### 6.4 check_attribute（动静 / 速度）

```
动静：预测的动静属性与真值不符，且持续 N 帧（单帧误判可容忍）
速度：速度误差（模长误差 + 方向误差）超过阈值
一致性：判为"静止"但速度输出不为零 → 自相矛盾，直接判失败
```

> `▸ 与项目一的连接`：项目一里"速度 loss 优化后动静专题通过率 +3.5%"，这个 3.5% 就是这个 checker 算出来的。

### 6.5 check_latency（检出时延 / 鬼探头）

**场景**：目标从遮挡后突然出现（车辆后方窜出的行人、路口盲区）。

```
判定：从目标首次可见（真值中出现且可见性 > 阈值）
     到模型连续 N 帧稳定输出
     的帧数 / 毫秒数
```

**为什么这是独立指标**：鬼探头场景下，**检出得晚 = 刹不住**。100ms 的延迟在 60km/h 下就是 1.7m 的制动距离差。而这个问题在任何单帧指标里都看不出来——每一帧都可能是"检出了"的，但第一帧检出得太晚。

### 6.6 check_detection_range（检出距离）

```
判定：目标从远处接近，连续 N 帧（通常 3 帧）稳定检出时，
     记录首次稳定那一刻的自车中心到目标的直线距离
```

> 项目一的 **131.5m** 和项目二的 **89m → 114m**，都是这个 checker 的输出。口径完全一致。

### 6.7 check_aeb（AEB 误 / 漏触发）

最高优先级。

```
误触发：不该刹的时候触发了 AEB
漏触发：该刹的时候没触发
```

**这类用例通常是零容忍的**——一条失败就直接阻塞版本。

### 6.8 check_region（自车系区域入侵）`▸ 你的设计`

**这个 checker 的特殊之处：不依赖标注。**

```
在自车坐标系下定义若干危险区域：
  · 正前方 0–5m 的紧急制动区
  · 左右侧的变道盲区
  · 倒车时的后方区域

判定：预测框与区域的几何交叠 → 判定为"目标入侵该区域"
```

**为什么免标注很重要**：

- 传统 checker 都需要真值，而真值标注是最贵、最慢的环节；
- 区域入侵只需要**预测结果 + 几何定义**，可以在任何数据上跑，包括没有标注的海量路测数据；
- 因此它可以做成一个**大规模筛查工具**——在百万帧无标注数据上跑，找出所有"报告有目标侵入紧急制动区"的片段，人工快速过一遍就能发现大量误检。

**这是一个用几何规则替代标注的典型例子**，成本极低而覆盖极广。

## 7. 时序指标与跨帧关联

### 7.1 为什么单帧指标不够

| 现象 | 单帧看到的 | 实际问题 |
|---|---|---|
| 检出闪烁 | 每一帧的 P/R 都还行 | 目标在"有/无"之间反复跳，规控无法跟踪 |
| 鬼探头时延 | 每一帧都"检出了" | 第一帧检出得太晚，来不及刹 |
| 动静跳变 | 每帧属性准确率 90% | 同一目标的属性在帧间翻转 20 次 |
| ID 切换 | — | 跟踪 ID 频繁重置，下游的历史信息全丢 |

**这些问题的共同点：它们是"序列"的属性，不是"帧"的属性。**

### 7.2 跨帧目标关联

要统计时序指标，必须先建立"同一个目标在不同帧之间的对应关系"。

```
真值侧：标注本身带 track_id（同一目标跨帧一致）
预测侧：
   方案 A：模型输出带跟踪 ID（如果有跟踪模块）
   方案 B：评测时自己做关联（按帧内匹配 + 帧间 IoU / 距离传播）
```

**关联建立后可统计的时序指标**：

| 指标 | 定义 |
|---|---|
| **连续命中长度** | 一个真值 track 被连续正确检出的最长帧数 |
| **连续丢失长度** | 连续漏检的最长帧数（比总漏检率更能反映严重性） |
| **首帧检出距离** | 见 §6.6 |
| **触发时延** | 见 §6.5 |
| **属性跳变次数** | 同一 track 上属性翻转的次数 |
| **ID 切换次数** | 同一物理目标被分配了几个不同 ID（借鉴 MOT 的 IDSW 指标） |
| **track 完整度** | 检出帧数 / 真值 track 总帧数 |

> **可以参考 MOT（多目标跟踪）领域的成熟指标**：MOTA、MOTP、IDF1、IDSW、MT/ML（Mostly Tracked / Mostly Lost）。这些指标专门为时序设计，可以直接借用。

### 7.3 容忍失败帧数

一个重要的配置项：**允许连续失败几帧**。

```
tolerate_fail_frames: 2
```

理由：单帧的偶发失败对下游影响有限（跟踪器会用历史信息补上），但**连续失败**就是真问题。这个配置让 checker 能区分"偶发抖动"和"持续失效"。

## 8. 防护网用例集的组织

> `▸ 你的位置`：用例集设计由你负责。

### 8.1 用例是什么

一条用例 = **一个数据片段 + 一组 checker + 一组阈值 + 预期结果**

```yaml
- case_id: FP_GARAGE_GATE_001
  description: "地库闸机横杆凭空检出车辆"
  source: "路测问题单 #12345, 2024-09-12"
  data:
    clip: "clip_20240912_143022"
    frames: [1200, 1450]
  checkers:
    - false_positive
    - region_intrusion
  overrides:
    false_positive:
      confidence_threshold: 0.2
      tolerate_fail_frames: 0
  expected: pass
  priority: P0
```

**关键字段是 `source`**：每条用例都能追溯到一个真实的路测问题或客诉。这保证了用例集不是凭空设计的，而是**真实问题的固化**。

### 8.2 用例集的规模与结构

**10+ 大类，50+ 细分专题**：

```
防护网用例集
├── 误检类
│   ├── 地库闸机
│   ├── 停车场立柱
│   ├── 前车尾气
│   ├── 护栏 / 隔离带
│   ├── 路面污渍 / 井盖
│   └── 树影 / 光斑
├── 漏检类
│   ├── 中远距小目标
│   ├── 强逆光
│   ├── 雨雾天
│   ├── 夜间无路灯
│   └── 异形车（工程车、挂车）
├── 3D 稳定性
│   ├── 大型车框抖动
│   └── 密集车流
├── 动静与速度
│   ├── 起步 / 刹停临界
│   ├── 横穿目标
│   └── 静止车队
├── 检出时延
│   ├── 鬼探头行人
│   └── 遮挡后车辆窜出
├── 检出距离
│   ├── 高速中远距车辆
│   └── 施工区
├── AEB
│   ├── 应触发场景
│   └── 不应触发场景
├── 区域入侵
├── 泊车专项
└── 恶劣天气专项
```

### 8.3 白名单机制

"白名单用例集"的含义：**这些用例是已知必须通过的**。

- 每一条都对应一个已经修复的历史问题；
- 新版本必须全部通过才能送测；
- **只增不减**——修好一个问题就加一条，永久监控。

这是防护网最核心的机制：**它保证了模型能力单调不减**。没有它，量产迭代会陷入"修好一个坏三个"的循环。

### 8.4 用例的优先级

| 级别 | 含义 | 失败后果 |
|---|---|---|
| **P0** | 安全相关（AEB、误刹、区域入侵） | **直接阻塞版本** |
| **P1** | 高频体验问题 | 需要说明原因并评审 |
| **P2** | 长尾场景 | 记录，允许暂时不通过 |

## 9. 基线 diff 与版本准入

### 9.1 基线的概念

**基线 = 当前已量产的版本（商发版本）**，它的所有评测结果被冻结保存。

新版本的每一项指标都与基线逐项对比，输出三种状态：

```
优化（improved）：新版本更好
持平（neutral） ：变化在噪声范围内
恶化（degraded）：新版本更差 ← 关键
```

### 9.2 diff 报表的结构

```
┌────────────────────┬────────┬────────┬────────┬────────┐
│ 专题                │ 基线    │ 新版本  │  Δ     │ 状态   │
├────────────────────┼────────┼────────┼────────┼────────┤
│ 误检-地库闸机       │ 92.3%  │ 95.6%  │ +3.3   │ 优化 ✓ │
│ 误检-前车尾气       │ 88.1%  │ 88.4%  │ +0.3   │ 持平 - │
│ 漏检-中远距         │ 85.0%  │ 89.2%  │ +4.2   │ 优化 ✓ │
│ 3D稳定-大型车       │ 91.5%  │ 87.2%  │ -4.3   │ 恶化 ✗ │  ← 阻塞
│ 动静-起步刹停       │ 90.0%  │ 93.5%  │ +3.5   │ 优化 ✓ │
│ 检出距离-高速       │ 118.2m │ 131.5m │ +13.3m │ 优化 ✓ │
│ AEB-不应触发        │ 100%   │ 100%   │  0     │ 持平 - │
└────────────────────┴────────┴────────┴────────┴────────┘

结论：存在 1 项恶化（3D稳定-大型车），不予准入
```

### 9.3 两种通过率

| 口径 | 定义 | 用途 |
|---|---|---|
| **帧通过率** | 通过的帧数 / 总帧数 | 细粒度，反映问题的普遍程度 |
| **case 通过率** | 通过的用例数 / 总用例数 | 粗粒度，直接对应"有几个问题没解决" |

**两个都要**：一个 case 里 99% 的帧通过、1% 失败，帧通过率很好看，但这个 case 本身是**失败**的（因为那 1% 就是问题所在）。反过来，case 通过率不能反映失败的严重程度。

### 9.4 准入规则

```
版本准入 = 目标专题达成预期提升
         AND 无 P0 恶化
         AND P1 恶化项已评审并有明确结论
         AND 全量回归完成
```

**"无恶化引入"这条规则的深层含义**：

每一个历史 bad case 背后，可能都是一次真实的客诉甚至事故。**允许它复现，等于让用户再经历一次。** 这就是为什么量产迭代慢——不是技术难，是每次改动都要证明"没有破坏任何已有能力"，而这个证明的成本极高。

**这套体系做的事，正是把这个证明成本从"两天人工"降到"半天自动"。**

### 9.5 噪声阈值

一个容易被忽略的细节：**多小的变化算"恶化"？**

模型训练本身有随机性（初始化、数据顺序、cudnn 非确定性），同一份配置训两次，指标可能差 0.3–0.5%。所以：

```
|Δ| < noise_threshold  → 判为"持平"
```

噪声阈值需要通过**同配置多次重训**实测得出，不能拍脑袋。否则会有大量假阳性的"恶化"，消耗大量排查时间。

## 10. 数据闭环上半环：难例挖掘

> `▸ 你的位置`：难例挖掘由你负责。

### 10.1 核心矛盾

**问题场景在数据湖里"捞不出来"。**

数据湖里有百万级 clip，但检索能力只有：

- 按时间、地点、车辆 ID；
- 按已有标签（如果标注过）；
- 按触发事件（接管、急刹）。

而你要找的是"地库闸机横杆导致误检"这样的场景——**它没有标签，因为没人标注过"闸机"这个东西**。

### 10.2 组合条件过滤

**思路：用已有的弱信号组合出目标场景。**

| 目标场景 | 组合条件 |
|---|---|
| 地库 | GPS 信号丢失 + 车速 < 20km/h + 环境亮度低 + 转向频繁 |
| 闸机 | 地库条件 + 车辆完全停止 + 停止时长 3–20s |
| 前车尾气 | 车速 > 40km/h + 前方有跟车目标 + 环境温度低 + 检出目标生命周期极短 |
| 隧道 | GPS 丢失 + 车速高 + 亮度骤变 |
| 施工区 | 检出锥桶类目标 + 高速路段 |
| 雨天 | 雨刮器状态 + 环境光 |
| 强逆光 | 时间为日出/日落时段 + 朝向与太阳方位角接近 |

**关键洞察**：车上有大量**非视觉的信号**（GPS、CAN 总线、IMU、雨刮、车灯、时间、天气 API），它们不需要标注就能用，组合起来可以精确地圈定场景。

### 10.3 基于模型行为的挖掘

比场景过滤更精准的一类：**用模型自己的异常行为来找难例。**

| 判据 | 找什么 |
|---|---|
| **时序突现突消** | 凭空误检（真实目标不会突然出现又突然消失）`▸ 项目一用的就是这条` |
| 高置信度但生命周期短 | 同上 |
| 置信度在阈值附近震荡 | 模型不确定的边界样本 |
| 相邻帧预测剧烈变化 | 不稳定场景 |
| 多模型分歧（Query by Committee） | 用几个版本的模型跑同一份数据，预测不一致的帧最有信息量 |
| 区域入侵报警 | 见 §6.8，免标注筛查 |
| 与规控决策冲突 | 感知说有障碍但人类驾驶员没减速 |

**这类挖掘的价值在于：它直接指向模型的能力边界**，比随机采样的数据信息量高一个数量级。

> **主动学习（Active Learning）** 的核心思想就是这个：标注预算有限时，优先标注模型最不确定的样本。

### 10.4 挖掘 → 送标 → 回灌链路

```
① 组合条件 / 模型行为判据 → 候选片段（可能几万帧）
        ↓
② 自动去重（相似帧只保留代表帧，避免标注冗余）
        ↓
③ 人工快速筛查（确认确实是目标场景，几秒/帧）
        ↓
④ 送标注（3D 框标注，是最贵的一环）
        ↓
⑤ 标注质检
        ↓
⑥ 构造专项训练集 / 评测集
        ↓
⑦ 回灌训练 → 新版本 → 评测验证是否收敛
```

**去重很重要**：10Hz 采样下相邻帧几乎相同，不去重的话会花大量标注预算买重复信息，而且会让训练集分布偏斜。

**常见去重方式**：时间间隔采样、特征相似度聚类、场景多样性采样。

### 10.5 回灌的副作用监控

**加数据一定有副作用**：

- 加大量地库负样本 → 地库误检下降，但**可能带来地库漏检上升**；
- 加某个场景的数据 → 训练分布偏移，**其他场景可能退化**。

所以每次回灌后都要跑**全量防护网**，而不只看目标专题。这又回到了 §9 的准入规则。

## 11. 数据闭环下半环：标注质检与错标治理

> `▸ 你的位置`：标注质检由你负责。

### 11.1 错标是一个被严重低估的问题

**公开数据集的错标率**（Northcutt et al., *"Pervasive Label Errors in Test Sets"*, NeurIPS 2021）：

| 数据集 | 测试集错标率 |
|---|---|
| ImageNet | 5.8% |
| QuickDraw | 10.1% |
| CIFAR-100 | 5.9% |
| MNIST | 0.15% |

**这是精心维护的公开数据集。**大规模外包标注的量产数据集，错标率只会更高。

**3D 标注的错标形式**：

| 类型 | 说明 |
|---|---|
| 漏标 | 远距、遮挡、小目标最常见 |
| 多标 | 把噪声点云标成目标 |
| 类别错误 | 卡车标成巴士 |
| 框不准 | 尺寸、朝向、位置偏差 |
| **朝向反向** | **yaw 差 180°，非常常见且危害极大**（速度方向全反） |
| ID 关联错误 | 跨帧 ID 串了 |

### 11.2 错标的双重危害

1. **污染训练**：模型学到错误的模式。尤其是系统性错标（某个标注员一贯的偏差），危害远大于随机噪声；
2. **污染评测**：**这个更隐蔽**。真值错了，模型对了，评测判模型错——你会去"修复"一个不存在的问题，浪费大量时间，甚至把模型改坏。

### 11.3 用模型推理反查标注 `▸ 你的方案`

**核心思路：把模型当成"第二标注员"。**

```
① 用当前最好的模型跑全量训练集推理
② 预测与标注做匹配
③ 挑出偏差最大的帧：
     · 模型高置信度检出，但标注里没有  → 可能是漏标
     · 标注里有，但模型完全没响应       → 可能是多标 / 噪声目标
     · 匹配上了，但尺寸/朝向差异巨大    → 可能是框标错
     · 朝向差约 180°                   → 高度疑似反向错标
④ 按偏差程度排序，推给人工复核
⑤ 复核结论回写，修正标注
```

**关键前提（必须说清楚）**：

> **偏差大 ≠ 标注一定错**，也可能是模型确实差。
> 所以**复核必须由人做，模型只负责排序**——它的作用是把有限的人力集中到最可能有问题的地方。

**效率对比**：

```
人工全量清查 50 万帧  →  不可能
模型排序后复核 top 5000 帧  →  几个人几天，能覆盖绝大部分严重错标
```

### 11.4 学界的对应方法

| 方法 | 思路 |
|---|---|
| **Confident Learning**（Northcutt et al., JAIR 2021） | 用模型的预测概率估计标注错误的联合分布，理论上有保证。开源实现 **cleanlab** |
| **Loss-based 筛选** | 训练时 loss 一直很高的样本，大概率是错标（模型学不会） |
| **Co-teaching** | 两个网络互相筛选干净样本训练 |
| **交叉验证反查** | K 折交叉验证，用没见过该样本的模型来判断它 |
| **多标注员一致性** | 同一批数据多人标注，取不一致的部分复核 |

> 你做的"模型反查 + 人工复核"，本质上就是 **Confident Learning 的工程化简化版**。这个对应关系值得知道——它说明这个做法不是土办法，是有理论支撑的标准做法。

### 11.5 标注质量的前置管理

修正错标是补救，更好的是**预防**：

| 措施 | 说明 |
|---|---|
| 标注规范 + 图示 | 每条规则配正例 / 反例 / 边界案例 |
| 金标准集考核 | 标注员上岗前必须通过 |
| 预标注模型 | 用离线大模型出初始框，人工只做修正，效率和一致性都更高 |
| 逐批抽检 | 每批交付抽 5–10%，不合格整批返工 |
| 一致性度量 | 多人标同一批，算 IoU 一致性 / Kappa |
| 争议案例评审 | 定期评审，结论更新进规范 |

## 12. 工程实现与性能

### 12.1 数据量级

```
一次全量回归：
  用例数        50+ 专题，数百条 case
  总帧数        10 万 – 50 万帧
  单帧目标数    10 – 100 个
  匹配计算      单帧 O(n×m)，全量数亿次
```

### 12.2 性能优化手段

| 手段 | 说明 |
|---|---|
| **多进程并行** | 按 case / clip 切分，`multiprocessing.Pool`。评测天然是尴尬并行（embarrassingly parallel） |
| **NumPy 向量化** | 3D IoU、距离矩阵的批量计算，避免 Python 循环。**这是最大的单点优化** |
| **pandas 聚合** | 结果统计用 groupby，比手写循环快一个数量级 |
| 缓存推理结果 | 推理和评测解耦，同一份推理结果可以跑多套 checker |
| 增量评测 | 只跑受影响的用例（调试时用） |
| 结果落库 | 历史结果持久化，支持任意两版本对比 |

**向量化的威力（3D IoU 为例）**：

```python
# 慢：Python 双重循环，1000×1000 需要数十秒
for p in preds:
    for g in gts:
        iou[i][j] = compute_iou_3d(p, g)

# 快：批量计算 BEV 交集面积 + 高度交叠，NumPy 广播，毫秒级
iou_matrix = batch_iou_3d(pred_boxes, gt_boxes)   # (N, M)
```

### 12.3 可重复性

评测系统本身必须是**确定性**的：

- 相同输入必须给出相同输出；
- 配置、代码版本、数据版本都要记录在结果里；
- 基线结果冻结存档，不能被覆盖。

否则会出现"上周跑的结果和这周不一样"这种无法排查的情况。

## 附录 A：3D IoU 与匹配算法细节

### A.1 3D 旋转框的 IoU 怎么算

3D 框（BEV 平面上带朝向的矩形 + 高度）的 IoU 不能直接用轴对齐框的公式。标准做法是**分解为 BEV 交集 × 高度交集**：

```
① BEV 平面交集面积：
   两个旋转矩形求交 → 凸多边形裁剪
   常用 Sutherland-Hodgman 算法 或 Shapely 库
   得到交集多边形 → 计算面积 A_inter

② 高度方向交集：
   h_inter = max(0, min(z1_top, z2_top) - max(z1_bottom, z2_bottom))

③ 体积：
   V_inter = A_inter × h_inter
   V_union = V1 + V2 - V_inter
   IoU_3D  = V_inter / V_union
```

**BEV IoU vs 3D IoU**：很多场景只用 BEV IoU（忽略高度），因为：

- 自动驾驶关心的是平面位置关系；
- 高度的标注和预测都不太准（尤其是 z 中心）；
- 计算更快。

### A.2 为什么 nuScenes 用中心距离

官方理由（可直接引用）：

1. **IoU 对小目标过于苛刻**：行人、锥桶等小目标，几十厘米的偏移就能让 IoU 归零；
2. **IoU 把两件事混在一起**：无法区分"检到了但位置略偏"和"完全没检到"；
3. **中心距更符合下游需求**：规控关心的是"那里有没有东西、大概在哪"，不是框的重叠度。

匹配用中心距离（0.5/1/2/4m 四档取平均），匹配成功后再单独统计 mATE / mASE / mAOE / mAVE / mAAE 五项误差。

**这套设计正是"匹配"与"精度"解耦的典范**，也是本项目分类别匹配策略的理论依据。

### A.3 匈牙利匹配代码骨架

```python
from scipy.optimize import linear_sum_assignment
import numpy as np

def match(preds, gts, cost_fn, max_cost):
    if len(preds) == 0 or len(gts) == 0:
        return [], list(range(len(preds))), list(range(len(gts)))

    cost = np.array([[cost_fn(p, g) for g in gts] for p in preds])
    cost[cost > max_cost] = 1e9          # 不允许的匹配设极大代价

    row, col = linear_sum_assignment(cost)

    matches, um_p, um_g = [], set(range(len(preds))), set(range(len(gts)))
    for r, c in zip(row, col):
        if cost[r, c] < max_cost:
            matches.append((r, c))
            um_p.discard(r); um_g.discard(c)
    return matches, sorted(um_p), sorted(um_g)
    #      匹配对    未匹配预测(FP候选)  未匹配真值(FN候选)
```

## 附录 B：指标定义速查

| 指标 | 定义 |
|---|---|
| **Precision** | TP / (TP + FP)，检出的里面有多少是对的 |
| **Recall** | TP / (TP + FN)，该检的检出了多少 |
| **帧通过率** | 通过的帧数 / 总帧数 |
| **case 通过率** | 通过的用例数 / 总用例数 |
| **稳定检出距离** | 连续 N 帧检出时，首次稳定那刻自车中心到目标的直线距离 |
| **检出时延** | 目标首次可见 → 连续 N 帧稳定输出的时间 |
| **连续丢失长度** | 同一 track 连续漏检的最长帧数 |
| **属性跳变次数** | 同一 track 上属性翻转次数 |
| **IDSW** | ID Switch，同一物理目标被分配了几个不同 ID |
| **MOTA** | 综合了 FP、FN、IDSW 的多目标跟踪准确度 |
| **mATE / mASE / mAOE / mAVE / mAAE** | nuScenes 的平移 / 尺寸 / 朝向 / 速度 / 属性误差 |
