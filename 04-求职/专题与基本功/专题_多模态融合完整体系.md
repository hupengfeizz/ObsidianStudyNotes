# 专题 · 多模态融合完整体系

> BEV 感知的核心。面试官问到融合时答「这是团队既有的」是把最重要的话题让出去——
> 做 BEV 的人不可能不清楚融合怎么走。**归属可以划边界，理解不能有缺口。**
>
> 本篇按 **概念分层 → 数据流全景 → 逐环节拆解 → 设计取舍 → 问答** 组织。
> ⚠️ 标【需核实】的按实际实现确认。

---

# 第一部分 · 概念澄清

## 1.1 前融合 / 特征级融合 / 后融合

融合发生在流水线的哪个位置，决定了它的全部性质。

### 前融合（Early Fusion / 数据级）

**在原始数据层面就把模态混起来，再送进一个网络。**

典型做法：把激光点云投影到图像平面，给每个像素额外加一个深度通道，图像就从 3 通道变成 4 通道，然后一个网络吃下去。或者反过来，把图像的颜色/语义"染"到点云的每个点上（PointPainting 就是这么做的）。

```
优点   信息损失最小——原始观测全保留，网络自己决定怎么用
缺点   ① 对时空对齐要求极高，标定差一点、时间差 20ms，两个模态就对不上
       ② 鲁棒性差：一个模态失效（相机被遮、激光下雨变脏），整个输入就脏了
       ③ 网络结构被绑死，换传感器要重新设计
```

### 特征级融合（Middle Fusion）—— 我们用的这种

**各模态各自提特征，在某个公共表示空间把特征融起来。**

BEVFusion 这条路线就是：相机走 LSS 转到 BEV、激光走点云编码转到 BEV，**在 BEV 空间融合**。

```
优点   ① BEV 是天然的公共坐标系，几何对齐比图像空间干净
       ② 各模态的 backbone 独立，可以分别优化、分别预训练
       ③ 单模态退化时另一路还能撑住，鲁棒性比前融合好
       ④ 融合是可学习的，不是手工规则
缺点   ① 各自提特征有算力开销，不如前融合省
       ② 融合前每个模态已经压缩过信息，不如前融合的上限高
```

### 后融合（Late Fusion / 目标级）

**各模态各自跑完整的检测，输出目标框，在结果层面做关联和融合。**

典型做法：相机检测出一批 3D 框，激光检测出一批，按 IoU 或中心距做匹配，匹配上的融合属性、没匹配上的按规则取舍。

```
优点   ① 模块完全独立，可以分别开发、分别验证、分别送测
       ② 单模态失效完全不影响其他，降级最自然
       ③ 出问题好定位——是哪个模态错了一目了然
缺点   ① 信息损失最大——只剩下框和几个属性，特征全丢了
       ② 融合规则是手工的、不可学习
       ③ 一个模态漏检了，后融合救不回来（它没有那个目标的任何信息）
```

### ⚠️ 一个高频的口径问题

**面试官问「你们是前融合还是后融合」时，工业界的习惯用法是二分的**：目标级融合叫后融合，其余（数据级 + 特征级）统称前融合。

所以答「前融合」不算错，但**更准确的答法是把三层说清楚**：

> 严格分是三层——数据级、特征级、目标级。我们是**特征级融合**，各模态各自出 BEV 特征、在 BEV 空间融合。如果按工业界"目标级叫后融合、其余叫前融合"的二分口径，那我们属于前融合。

**这么答比直接说"前融合"显专业得多**，而且堵住了"那你们是把点云投到图像上吗"这个后续追问。

## 1.2 前处理 / 后处理

**前处理**：数据进网络之前的所有操作。

```
图像   去畸变 → resize → 归一化 → 色彩变换 → 数据增强
点云   坐标变换（LiDAR系→自车系）→ 范围裁剪 → 运动补偿 → 体素化
共同   时间戳对齐、多相机同步
```

**后处理**：网络输出之后、交给下游之前的所有操作。

```
解码      heatmap → 峰值提取 → topK → 拼装 3D 框
过滤      置信度阈值、post_center_range 范围过滤
去重      NMS
跟踪      ID 关联、生命周期管理
平滑      卡尔曼滤波等
```

**关键性质：前后处理通常是不可学习的手工规则。**这是它们的软肋——参数靠调、逻辑靠写、没法端到端优化。所以行业趋势是把它们往网络里搬：One2One 匹配去掉 NMS、学习式跟踪头替代规则跟踪器。

# 第二部分 · 数据流全景

```
输入
 ├─ 针孔 ×7   1280×704 ─→ ResNet-Auto-FPN2 ─→ FPN(P3P4P5→256ch)
 │                              ↓
 │                        DepthNet(lite_decoder, 100bins+dustbin)
 │                              ↓
 │                        LSS 投影（外积 → 高度 pool → grid_sample）
 │                              ↓
 │                        MultiViewFusion（多针孔拼接）──→ Image BEV 64ch
 │
 ├─ 鱼眼 ×4   768×512  ─→ 独立 ResNet-Auto-FPN2（权重不共享）
 │                              ↓
 │                        FV2BEV Transformer（球面坐标位置编码 + cross-attn）
 │                              ↓                            ──→ Fisheye BEV 32ch
 │
 ├─ LiDAR    ─→ LidarVoxelEncoder(PointPillars) ─→ BEV 352×224
 │             max_voxels 60000, in_ch 4 (x,y,z,intensity)      ┐
 │                                                              ├─→ LidarNetsSingle
 ├─ Radar    ─→ RadarVoxelEncoder（与 LiDAR 同一个类）─→ BEV     │   （共用 UNet）
 │             max_voxels 1600, in_ch 10（含多普勒速度）        ┘        ↓
 │                                                                  LiDAR+Radar BEV 64ch
 └─ LiDAR 强度图 ─→ AscendNet + BiFPN ─→ 逐元素注入 BEV 中央近处区域
                                          [156:236, 96:128]（约 32×32 格）

                              ↓↓↓  MultiFusion  ↓↓↓

                        融合后 BEV 128ch
                              ↓
                        DenseMemoryManager（历史 3 帧缓存）
                        HDTempoFusion（时序融合，CONCAT）
                        CaDDNBEV（BEV backbone）
                              ↓
                        detection3d_head / nearby / DenseChild / Track
```

**融合发生在 `MultiFusion`——每个模态都已经变成 BEV 特征之后。**

# 第三部分 · 逐环节拆解

## 3.1 为什么必须先统一到 BEV 空间

这是整套设计的地基。

相机给的是**透视视角**的二维特征，激光和毫米波给的是**三维空间**的点。它们的坐标系、维度、密度分布完全不同，**不转到同一个空间就没法逐元素对齐**。

BEV 之所以是那个"同一个空间"：

```
① 激光和毫米波天生就在 BEV 视角下——它们本来就是 3D 观测，
   沿高度压扁就是 BEV，几乎零成本

② 相机需要一次视图变换才能过来（LSS 或 Transformer），
   这是整条链上唯一"贵"的一步

③ BEV 和下游规控用的是同一个坐标系，融合结果直接可用

④ 在 BEV 上，同一个物理位置在所有模态里就是同一个格子——
   融合退化成逐元素操作，简单且可学习
```

**如果不转 BEV，在图像空间融合会怎样**：激光点投到图像上是稀疏的散点，和稠密的图像特征在空间分布上完全不匹配；而且多相机之间没有公共的图像空间，七路针孔的特征没法互相对齐。

## 3.2 LiDAR 与 Radar 的两阶段融合 —— 最值得讲的设计

架构里 Radar 和 LiDAR **融了两次**，这是个很有信息量的设计。

### 第一阶段 · 在 UNet 入口处

```python
lidar_feat = Conv1x1(64 → 32)   # 各自独立的 1×1 卷积
radar_feat = Conv1x1(64 → 32)
feat = lidar_feat + radar_feat  # 逐元素相加
→ 一起送进 LidarNetsSingle 这一个 UNet
```

**为什么用独立的 1×1 卷积再相加，而不是直接 concat**：
- 独立 1×1 相当于给每个模态一个可学习的通道重映射，让它们在相加之前先"对齐语义"
- 相加比 concat 省通道、省算力
- 相加是隐式的加权融合，网络可以通过 1×1 的权重决定谁的贡献大

**为什么共用一个 UNet 而不是各自一个**：省算力，而且强制两个模态在同一组卷积核下学到互补的表达。

### 第二阶段 · 在 MultiFusion 里再叠一次

```python
if rc_fusion:
    radar_feat = Conv1x1(64 → 64)
    fused = fused + radar_feat    # 原始 Radar 特征再注入一次
```

**为什么要融两次**：因为 Radar 的信息在 UNet 里会被稀释。

Radar 的点数比 LiDAR 少一个多数量级（`max_voxels` 1600 vs 60000），在 UNet 五层下采样再上采样之后，它那点稀疏信号很容易被 LiDAR 的稠密特征淹没。**保留一份原始 Radar 特征在最后再注入，是为了让它的独特信息——尤其是多普勒速度——不被冲掉。**

> 这个设计细节是"真读过代码"的证明。它不是论文里的标准做法，是工程上针对 Radar 稀疏性做的补偿。

### Radar 和 LiDAR 的处理差异

| | LiDAR | Radar | 说明 |
|---|---|---|---|
| VoxelEncoder 类 | `LidarVoxelEncoder` | 同一个类（别名 `RadarVoxelEncoder`） | **完全复用** |
| 体素化方法 | PointPillars (PFNLayer) | 相同 | 完全一致 |
| `max_voxels` | 60000 | **1600** | Radar 点数少一个多数量级 |
| `in_channels` | 4 (x, y, z, intensity) | **10**（含多普勒速度等） | **Radar 每点信息更丰富** |
| UNet | `lidar_backbone/unet.py` | `radar_backbone/unet.py` | 结构相同、**权重独立** |
| 融合位置 | UNet 入口 | 同上 + MultiFusion 再叠一次 | **两阶段** |

**`in_channels` 4 vs 10 这个对比很能说明问题**：LiDAR 每个点只有位置和强度，Radar 每个点带多普勒速度、RCS 等更多维度。**Radar 点少但每点信息密度高**——这也是为什么它值得单独再注入一次。

## 3.3 LiDAR 强度图的特殊注入

除了点云走体素化那一路，LiDAR 还有第二路：**把点云投影成 2D 距离图（640×256，5cm/pixel 分辨率），过第二个图像 backbone（AscendNet + BiFPN）**。

然后在 UNet 输出前，把这份强度图特征**逐元素注入到 BEV 的一个特定小区域**：

```
[156:236, 96:128]    约 32×32 格网    ← 只注入中央近处区域
```

**为什么只注入近处**：强度图是把点云当图像处理，能提取到点云体素化丢掉的纹理和反射特性——但这只在点云足够密的近处才有意义。远处点云本来就稀，投成图像也是一片空白，注入进去只会增加噪声。

**这是一个典型的"用算力换近场精度"的取舍。**近场是安全关键区域（AEB、VRU），值得单独加一路。

## 3.4 相机侧的两条支路先各自成 BEV

针孔和鱼眼**不共享 backbone**（`img_backbone` / `img_backbone_fish`，权重独立），各自转到 BEV 之后才汇合。

```
针孔  7 路 → LSS 显式几何投影 → MultiViewFusion 拼接 → Image BEV
      BEV 范围 ~179.2 × 89.6m，0.4m/格，448 × 224

鱼眼  4 路 → Transformer 隐式学映射 → Fisheye BEV
      BEV 范围 ~12.8 × 12.8m，0.8m/格，16 × 16
```

**注意两者的 BEV 网格完全不同**——范围差 14 倍、分辨率差 1 倍。所以融合前必须做**尺度对齐**：鱼眼那份要上采样并 zero-pad 到主网格尺寸，只在它覆盖的近场区域有非零值。

## 3.5 MultiFusion 的实际操作

```python
# 配置
feature_fusion:
  arch: 'concat'              # 默认策略
  common:
    image_conv: True          # 图像特征先过 3×3 Conv
    num_bev_features: 128     # 输出通道

# 实际流程
# ① 相机 BEV + LiDAR BEV
image_feat = Conv3x3(64 → 64)                    # image_conv=True
fused = concat([lidar(64), image(64)], dim=1)    # → 128ch

# ② + Radar BEV
if rc_fusion:
    radar_feat = Conv1x1(64 → 64)
    fused = fused + radar_feat                   # 逐元素相加

# ③ + 鱼眼 BEV
if use_fisheye_transformer:
    fused = 鱼眼特征经近处理后 mean 聚合到 fused
```

**三种模态用了三种不同的融合方式，这不是随意的：**

| 模态对 | 方式 | 为什么 |
|---|---|---|
| 相机 ↔ LiDAR | **concat** | 两者信息量相当、互补性强，concat 保留各自完整信息让网络自己学怎么用 |
| + Radar | **add** | Radar 是补充性的、信息维度少，add 省通道；而且它已经在 UNet 里融过一次，这是二次注入 |
| + 鱼眼 | **mean 聚合** | 鱼眼只覆盖近场小区域，用 mean 是为了不让它在自己的区域内压过主支路 |

**图像特征为什么要先过 3×3 Conv（`image_conv=True`）**：相机 BEV 是经过视图变换得来的，空间上有"投影伪影"——同一条射线上的特征被涂在一串格子里，相邻格子高度相关。3×3 Conv 做一次局部平滑和重映射，让它的空间统计特性更接近激光那边的 BEV，融合时才不会因为分布差异导致某一路主导。

## 3.6 可切换的七种融合策略

配置里可以通过 YAML 切换：

| 策略 | 注册名 | 方法 | 特点 |
|---|---|---|---|
| 通道拼接 | `concat` | `torch.cat` 或 `torch.add` | 当前使用，最简单 |
| Conv+Concat | `conv_concat` | 3×3 Conv 对齐通道后拼接 | 拼接前先对齐 |
| 门控融合 V2 | `gated_fusion_v2` | 可学习的 per-pixel sigmoid 门控 | **每个位置自适应决定信谁** |
| 门控融合 V4 | `gated_fusion_v4` | V2 + ResNet Block | 门控 + 残差 |
| 交叉注意力 | `attention_fusion` | 跨模态 Multi-head Cross-Attention | 表达力最强、最贵 |
| 选择性核 | `sk_layer` | SKNet 风格多分支融合 | 多尺度自适应 |

**为什么最后用的是最简单的 concat**：

这个问题值得展开——**不是因为它效果最好，是因为性价比。**

门控融合和交叉注意力在论文上通常更强，因为它们能做到"这个位置激光更可信就多用激光、那个位置相机更可信就多用相机"。但代价是：

```
① 算力：cross-attention 在 448×224 的 BEV 上开销很大
② 训练稳定性：门控参数在多模态不平衡时容易塌向某一路
③ 部署：注意力算子在车端芯片上的支持和优化不如卷积成熟
```

**concat + conv 本身就有隐式的门控能力**——卷积核可以学到"这个通道组合下更信激光"，只是不如显式门控灵活。在量产的算力预算下，这个折中是合理的。

> **能把"配置里有七种但用了最简单那种、以及为什么"讲出来，比只知道用了 concat 强得多。**

# 第四部分 · 融合的设计取舍与失效

## 4.1 融合面临的四个真实难点

### 难点一 · 时空对齐

**空间**：外参标定误差有杠杆效应——偏 0.1 度，100 米外横向偏 0.17 米，接近半个 BEV 格子。相机和激光标定不准，融合时同一辆车在两个模态的 BEV 上就错位，融出来是重影或者被拉长。

**时间**：多相机靠硬件触发同步，激光转一圈 100ms，需要在扫到某个相机视野方向时触发该相机。差 20ms，60km/h 的车跑 0.33m，接近一个格子。

> **空间对不齐和时间对不齐，表现出来是一样的。**这句话能说出来，说明你真处理过。

### 难点二 · 模态间的密度与分布差异

```
相机 BEV   稠密但"虚"——每个格子都有值，但远处是深度不确定涂出来的
激光 BEV   稀疏但"实"——有点的地方很准，没点的地方是真空
Radar BEV  极稀疏——1600 voxel vs LiDAR 60000
```

直接融合的问题：**稠密的相机特征会在数值上淹没稀疏的激光特征**。所以需要 `image_conv` 做分布对齐，需要 Radar 二次注入防止被稀释。

### 难点三 · 单模态失效时的退化

激光在雨雾里点云变脏、距离衰减；相机在逆光、夜间、雨天成像质量下降；Radar 受影响最小但分辨率最低。

**融合网络如果训练时各模态都健康，推理时某一路突然退化，输出会不可预测**——因为网络已经习惯了依赖那一路。

对策方向：训练时随机 drop 某个模态（modality dropout），强迫网络在缺模态时也能工作。【需核实实际是否做了】

### 难点四 · 融合权重的隐式偏置

用 concat + conv 的话，各模态的贡献是隐式的，**没法直接观测网络到底更信谁**。如果激光特征的数值尺度天然比相机大，卷积会自然偏向激光——这不是设计意图，是数值巧合。

对策：BN 或特征归一化让各路数值尺度可比；或者用显式门控让权重可观测。

## 4.2 为什么不做前融合（数据级）

```
① 对标定和同步的要求高一个量级——前融合是逐点/逐像素对齐，
   特征级融合是格子级对齐，后者对误差的容忍度大得多
② 鲁棒性差：把点云深度作为图像的额外通道，激光一坏，
   整个输入张量就脏了，相机分支也跟着崩
③ 灵活性差：换传感器配置（加一路相机、换激光型号）要重新设计网络
```

## 4.3 为什么不做后融合（目标级）

```
① 信息损失最大——只剩框和几个属性，特征全丢了
② 一个模态漏检，后融合救不回来（它压根没有那个目标的任何信息）
   而特征级融合下，相机的弱响应 + 激光的弱响应可能加起来就过阈值了
③ 融合规则手工写、不可学习，长尾场景调不动
```

**特征级融合的核心价值就在第二条**：它能让两个"都不够确定"的观测加起来变成一个确定的检出。这是后融合做不到的。

# 第五部分 · 关于 tracker 与后处理滤波

## 5.1 tracker 是什么

**多目标跟踪器**：把逐帧的检测结果在时间上关联起来，给每个物理目标一个稳定的 ID，并维护它的状态（位置、速度、生命周期）。

```
经典规则式   SORT / DeepSORT / ByteTrack（2D）、AB3DMOT（3D）
             = 卡尔曼滤波预测 + 匈牙利匹配关联
学习式       我们用的 TrackHeadRe —— Transformer 做 ID 匹配，
             embedding 128 维、最大 ID 513、Memory 时间窗 2 秒
```

**tracker 能做四件事**：

```
① 平滑     用运动模型压掉逐帧抖动
② 补帧     漏检时用预测填充，维持轨迹连续
③ 过滤     生命周期短的判为误检（我们的 valid/invalid 二分类）
④ 出速度   从轨迹差分得到更稳的速度估计
```

## 5.2 后处理滤波的原理

最常用的是**卡尔曼滤波**：

```
状态    位置、速度（有时加加速度）
预测    用运动模型（匀速 CV / 匀加速 CA）从上一帧推出当前帧的先验
更新    用当前帧的观测修正先验
        权重由「观测噪声」和「过程噪声」的相对大小决定
```

**核心思想**：观测噪声大的时候更信预测，观测稳定的时候更信观测。**用时间上的冗余压随机噪声。**

其他常见的：滑动窗口平均、指数移动平均（EMA）、中值滤波。原理都一样——**假设噪声是零均值随机的，多帧平均掉。**

## 5.3 为什么滤波替代不了模型端的设计

**这是那个高频追问的答案，也是滤波的根本局限：**

```
随机噪声（零均值）   滤波有效 —— 多帧平均会收敛到真值
系统性偏差（bias）   滤波无效 —— 每一帧都偏同一个方向，
                     平均之后偏差原封不动，只是变平滑了
```

举例：如果模型对低速目标系统性地估成零速，那么**每一帧都是零速**，卡尔曼滤波平均出来还是零速——它只会让这个错误更"稳定"，看起来更可信。

**滤波还会引入延迟**：为了平滑，它必然对新观测反应迟钝。目标真的开始动了，滤波器要几帧才跟上——而低速跟车这种场景恰恰要求快速响应。

**所以正确的分工是：**

```
模型端    把表示和 loss 设计对，消除系统性偏差
tracker   压残余的随机噪声、维持 ID 连续、提供生命周期信息
```

**顺序不能反。**先用滤波掩盖模型的系统性问题，问题会一直在，而且被掩盖之后更难发现。

# 第六部分 · 归属边界怎么说

融合模块是团队既有的，但**"不是我做的"和"我不了解"是两回事**。

**推荐说法：**

> 融合这一块的架构是组里既有的，我没有从零设计过。但因为做深度和视图变换的优化必须清楚下游怎么消费我的输出，这条链我是通的——从各模态怎么各自成 BEV、在哪一步汇合、用什么方式融、为什么这么选，包括配置里那七种可切换策略和为什么最后用的是最简单的 concat。

**不推荐说法：**

> ~~这一块是团队既有的模块，不是我做的~~ ← 停在这儿，等于把最核心的话题让出去

**分寸在于**：先答技术内容，最后一句带出归属，而不是用归属把问题挡回去。
