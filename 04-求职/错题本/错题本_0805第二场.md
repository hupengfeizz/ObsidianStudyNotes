## 第1题　BEVPoolv2 的查找表是哪个方向（答反）

**他问的**：这个查找表是 BEV 空间的每个格子回头去找相机坐标系的特征值，还是相机特征值根据这个表投影到 BEV 空间？

**我答的**：是第一种，从 BEV 空间的每个格子去相机坐标系找它对应的特征值。

**错在哪**：反了。BEVPoolv2 优化的是 LSS 的 **Splat** 那一步，方向是**前向**的。"从 BEV 格子回头取图像特征"那是 BEVFormer 的后向 query 做法。这题问得很精准，说明他清楚答案。

**应该这么说**：

> 是后者，相机特征按表投到 BEV，方向是前向的。
>
> BEVPoolv2 优化的是 LSS 里 Splat 那一步——先在图像上预测深度分布、把特征抬升成视锥，再按内外参把视锥点投到 BEV 格子里累加。查找表记录的就是「每个视锥点落到哪个 BEV 格子」这个索引关系。因为这个映射只由内外参决定，而内外参在车上是固定的，所以可以离线预计算成表，运行时直接按索引累加，不用排序、不用 cumsum，也不用把那个巨大的视锥张量物化出来。
>
> 从 BEV 格子回头去图像上取特征，那是 BEVFormer 那条后向 query 的路线，我们没走。

**一句话记忆**：**LSS / BEVPoolv2 是 push（特征被推到 BEV），BEVFormer 是 pull（query 去图像拉特征）。查找表在 push 这一侧。**

## 第2题　一个 BEV 格子被多个相机看到，多份特征怎么处理（答偏）

**他问的**：这个格子在原始相机中可能被多个相机都能看到，那每个相机都会提供不同的特征，这个具体是怎么处理的？

**我答的**：十一个视锥体通过内外参转换到统一的自车坐标系，进行了坐标系的统一，这样特征就对齐了。

**错在哪**：答的是"怎么保证它们在同一个空间里"，他问的是"落到同一个格子的多份特征怎么合成一份"。前者是前提，后者才是问题。

**应该这么说**：

> 落到同一个 BEV 格子的所有视锥点，做的是 sum / average pooling，直接聚合，不做加权——我们的配置里 weighted_aggr 是关掉的，用的就是标准 LSS 的平均池化。
>
> 所以重叠区的处理是天然的：一个格子被两个相机同时看到，两路的视锥点都会落进来一起被聚合。这既是好事——重叠区证据更多、特征更强；也有风险——如果两个相机的标定或时间同步有偏差，同一个目标会被投到相邻的不同格子上，聚合之后就是一个被拉长或者重影的目标。所以重叠区对标定精度和时间同步的要求特别高。
>
> 另外多相机之间还有一层 MultiViewFusion：各视图的 BEV 特征先 zero-padding 对齐到统一坐标系，再沿通道维 concat，最后过 3×3 卷积压到 64 通道。**格子内的聚合是 pooling，视图之间的融合是 concat 加卷积，这是两层。**

## 第3题　雷达支路的特征具体是怎么得到的（第三次说错）

**他问的**：雷达那个分支你可以再稍微讲一下，它的输入是点云的三维信息，那这个特征是怎么得到的？怎么转到 BEV 空间？

**我答的**：先做 voxel 体素化，在雷达坐标系下……只需要在它的 3D 空间里进行一个 **3D Backbone** 的特征提取，提取完之后在三维空间上拍扁成 BEV 特征，拍扁的时候不考虑深度值，只考虑图像的语义特征。

**错在哪**：两处。一，**没有 3D Backbone**——这是 v1.1 已经纠正过、这是第三次说错。二，"只考虑图像的语义特征"——雷达支路根本没有"图像语义特征"这回事，这句是把相机支路的说法串过来了。

**应该这么说（三句话，背到肌肉记忆）**：

> 第一，点云做 pillar 体素化，用的是 PointPillars 那套（PFNLayer）。**这一步的输出直接就是 BEV 特征图**——352×224、0.4 米一格、高度切 16 层，输出 [B, 64, 352, 224]。高度维在编码阶段就压进通道里了，**不存在「先用 3D 卷积提特征、再拍扁」这个中间过程**。
>
> 第二，激光和毫米波走的是同构的管线——共用同一个体素编码器类，区别只在配置：激光体素上限 6 万、每点 4 维特征（xyz 加强度）；毫米波上限 1600、每点 10 维（多了多普勒速度这些）。两路在同一个 UNet 里融合，入口处各过一个独立的 1×1 卷积降到 32 维，再逐元素相加。
>
> 第三，出来的 64 通道 BEV 特征，再和相机的 BEV 特征在通道维 concat。
>
> **为什么不用 3D 稀疏卷积**：车端算力是硬约束。PointPillars 把高度维一次性压进通道，后面全走 2D，比 VoxelNet / SECOND 那条 3D 稀疏卷积路线省很多。代价是高度信息编码得粗，但 BEV 检测最后本来就要压掉高度，这个代价可以接受。

## 第4题　除了 LSS 和 Transformer，2D 转 3D 还有哪些方式（答不出）

**我答的**：还有 BEVFormer……另外的我可能有点想不起来了。

**错在哪**：BEVFormer 就是 Transformer 那一类，等于没答出新的。这是知识广度题，答不出显得只会自己那一套。

**应该这么说（四类，按几何先验的强弱排）**：

> 我按「用了多少几何先验」来分，大概四类。
>
> **一、几何假设最强的 —— IPM，逆透视变换。** 假设世界是一个平面，用单应矩阵把图像直接映射到 BEV。几乎零算力，但只对贴地的东西成立，任何有高度的物体都会被拉出长长的畸变尾巴。现在主要用在车道线、可行驶区域这类要素上。
>
> **二、显式深度的前向投影 —— LSS 系**，我们走的这条。同一类里还有 **Pseudo-LiDAR**：先估深度图、反投影成伪点云，然后直接套点云检测的方法。它和 LSS 的区别是——Pseudo-LiDAR 生成的是显式的点，LSS 涂的是特征。
>
> **三、注意力的后向 query —— BEVFormer 系**，BEV 格子一个 query 去图像上做 deformable cross-attention，不显式估深度。更稀疏的一支是 PETR（用 3D 位置编码让 2D 特征自带空间信息）和 Sparse4D / StreamPETR（固定数量的实例 query，算力和覆盖范围解耦）。
>
> **四、完全不用几何的 —— MLP 直接映射**，像 VPN、PON 那一类，直接用全连接学「图像特征图 → BEV 特征图」。简单，但没有几何先验、参数量大、标定一变就废，基本被淘汰了。
>
> 这四类的核心差异就是几何先验用了多少——IPM 用最强的先验所以最省但最受限，MLP 完全不用所以最灵活但最不可靠，LSS 和 attention 在中间。选哪个取决于算力预算和场景约束。

## 第5题　端侧精度掉了，你实际碰到过什么问题（追五轮只给流程）

**他问了五轮**，最后明说：「**首先刚刚问的是你在那个项目当中真实碰到一个问题，就不是流程上。**」

**我答的**：一直在给流程——分别评测对比、看日志、分块分析、算子是另一个部门搞的……

**错在哪**：他要的是**一个具体案例**。而我手上明明有现成的（RK3588 那两个），却拖到很后面才说，前面全在讲流程。

**应该这么说（流程要快，案例压轴）**：

> 流程上我一般分三层定位：先确认 gap 出在哪一环——同一批数据分别跑 PC 浮点、端侧浮点、端侧量化三组对比，如果端侧浮点就掉了，那是转换或前后处理的问题，跟量化无关；确认是量化引入的，再逐层看激活值分布找差异最大的层；最后查算子有没有在目标平台上不被支持、被回退成低效或不等价的实现。
>
> 另外**第零步其实是查前后处理对齐**——resize 方式、归一化参数、通道顺序、letterbox 填充值，只要和端侧推理链路对不上，精度就会莫名掉一大截，而且这类问题查激活值是查不出来的。成本最低、命中率最高，应该先查。
>
> **我自己实际碰到过两个，是在 RK3588 上部署 YOLO 的时候：**
>
> **一是算子不支持。** YOLOv8 用的 SiLU 激活函数，3588 的 NPU 没有原生支持，跑起来会回退到低效实现、性能很差。我的解法是在模型侧换成 ReLU 重训——NPU 对 ReLU 有原生支持，实测精度没有明显损失。这里的判断是：算子不支持有两条路，让算子侧去开发、或者模型侧换成等价且被支持的算子。**模型侧能绕开的就不要去改算子**——改算子周期长风险高，换激活函数只要重训验证一次。
>
> **二是全量 INT8 掉点严重。** 解法是混合精度：backbone 走 INT8，检测头保持浮点。因为检测头直接输出置信度和框坐标，量化误差会一比一变成精度损失，而且它计算量占比小、量化省不下多少；backbone 计算量占大头，量化收益最大，而且输出的是中间特征，对量化误差容忍度高得多。
>
> 至于 BEV 那个项目，量化部署是组内专门的同学做的、算子开发是另一个部门，我负责的是定位——拿到量化前后的评测结果，判断退化集中在哪些场景、哪个指标上，是不是模型侧的问题。

**注意归属边界放在最后一句**，不要一开口就说"这块不是我做的"。

## 第6题　BEV 网格分辨率是统一的还是分场景的（越答越乱、疑似现编）

**我的回答轨迹**：
1. "网格上是统一的一个尺寸，没有差异，0.4 米"
2. 被追问机械车库只剩十几公分 → "特殊场景会提高标注帧率和网格分辨率"
3. 追问怎么落地 → "离线配置 + 场景识别分类器 + 配置映射表动态切换"
4. 追问泊车具体多少 → "大概 0.2 米……记不清了，可能 0.05 或 0.11……这块我没怎么做调整"

**错在哪**：**不是答不上丢分，是听起来像在现编。** 前面越具体，最后"记不清"的杀伤力越大。这是面试里最危险的一种失分。

**应该这么说（口径定死，不要临场加细节）**：

> 网格统一 0.4 米一格，全场景一套模型，不按场景切换分辨率。定位到某个场景有问题的时候，我们是通过数据侧的定向挖掘和回灌去解决，不改网络配置。
>
> **被追问「0.4 米对机械车库这种十几公分间隙够吗」**：
>
> 坦白说不够，这是这套方案的边界。0.4 米的网格在极窄空间里确实分辨不出来——但这类场景我们不是靠 BEV 检测框去解的。极窄间隙的通过性判断靠的是占据网络，它的体素分辨率是 20 厘米量级，比 BEV 细一倍；更近的还有超声波。BEV 3D 框负责的是动目标的实例级检测，机械车库那种间隙判断本来就不在它的职责范围内。

**这个答法的价值**：把"我们做不到"转成"这不是这个模块该做的事，系统里有别的模块负责"——这是真实的系统分工，不是找借口。

**通用原则**：**不确定的细节，宁可说"这块我没做过、不确定"，也不要临场推演出一套听起来很具体的机制。** 编出来的东西经不起第三轮追问。

## 第7题　Sparse 全图目标消失，现在回看是什么原因（只说可能是 bug）

**我答的**：可能是代码上出现了一些 bug 之类的，但当时也觉得不至于出现这么低级的问题，部门最近在定位。

**错在哪**：这是**技术判断力题**，答"可能是写了个 bug"等于放弃回答。他特意加了"你现在已经做过一个完整量产之后再回过头看"，就是想看你的复盘能力。

**应该这么说**：

> 现在回头看，「全图目标整体消失」这种全或无的失效模式，指向的是某个**全局性的东西崩了**，而不是局部精度问题。我能想到三个方向：
>
> **一是数值问题沿时序链路传播。** 稀疏路线的 query 是 recurrent 传递的——上一帧的 instance 状态直接传到下一帧。如果某一帧出现 NaN 或 Inf，会顺着时序链路污染后续所有帧，表现就是从某一帧开始全图突然什么都没有、而且持续一段时间。**这个和当时的现象最吻合。**
>
> **二是注意力权重坍缩。** 如果所有 query 的注意力都集中到极少数采样点上，或者位置编码在某些极端输入下溢出，query 取到的特征就全是无效的，输出自然全空。
>
> **三是置信度整体低于阈值。** 不一定是没检出，可能是所有目标的分数都掉到后处理阈值以下被过滤光了。这一类最好验证——把阈值调到 0 看还有没有框。
>
> **怎么验证**：先看是不是可复现、和特定输入相关；然后把中间的 instance 特征和注意力权重 dump 出来看是不是 NaN 或退化；再去掉后处理阈值看原始输出。
>
> **如果当时有这套观测手段，定位应该不会那么难——这也正好是 dense 路线可解释性优势的具体体现：dense 有中间的 BEV 特征图可以可视化，稀疏路线中间没有可观测的稠密表示。所以我们当时切回 dense，本质上不是精度选择，是可调试性选择。量产上一个定位不了根因的失效模式，比精度低几个点严重得多。**

## 第8题　共享 backbone 特征不匹配，怎么提高单任务精度（被点破没有优化）

**我答的**：在检测头上设计，在 neck 部分优化，针对性微调，增加 neck 的卷积，放大锥桶这种小目标的检出性能。

**他的评价（原话）**：「**你这个应该好像更偏向说我怎么设计，把这个网络设计出来，然后有一个初始的版本，好像没有太多优化的部分。**」

**错在哪**：说的是"结构长什么样"，不是"你做了什么让它变好"。**优化必须有「改之前是什么样 → 改了什么 → 改之后好了多少」三段。**

**应该这么说**：

> 共享 backbone 的核心矛盾是：backbone 是被所有子任务的梯度共同塑造的，它学到的是一份「大家都能用」的通用特征，对单个子任务不是最优。能做的有三层——
>
> **第一层，不动 backbone，加任务专属容量。** 我这条线上是加深 neck、在检出头前加针对小目标的多尺度结构，让专属分支去补 backbone 没给足的部分。这一层最安全，不影响其他任务。
>
> **第二层，调 loss 权重。** 某个子任务在共网上掉点明显，可以提高它的 loss 权重，让它在梯度竞争里占更大比重。代价是可能拖累别的任务，所以要跑全任务对照。
>
> **第三层，冻结 backbone 后单独微调后段。** 这也是我们实际的做法——第一阶段联合训练把 backbone 训好，之后冻结，各子任务在冻结的 backbone 上单独训自己的 neck 和 head。好处是各任务能独立迭代、独立发版，代价是放弃了后期的联合优化空间。
>
> **怎么判断改动有效**：单任务基线 → 并进共网 → 逐任务对比是否恶化。核心看的是相对单任务基线掉了多少，压到可接受范围才合入。

## 第9题　鱼眼那条算力不满足怎么优化（答得泛）

**我答的**：考虑做模型轻量化，把一些比较重的模块变轻一点，另外像 BEVPoolv2 这种在精度不降的情况下减算力。

**错在哪**：太泛，任何模型都能这么说。而且他随后提示「BEVPool 这种对鱼眼来说效果没那么好，你退回去精度可能就不达标了」——这是在考**取舍怎么权衡**，我没接住。

**应该这么说**：

> 先说清楚鱼眼那条的算力构成：它走的是 Transformer，成本正比于 BEV query 数，也就是正比于覆盖面积除以格子边长的平方。所以第一优先级是**砍覆盖范围和网格分辨率**——鱼眼本来就只管近场七米，如果算力不够，可以把格子从 0.8 米放粗，query 数按平方下降，这是收益最直接的。
>
> 第二是**砍 Transformer 的层数和采样点数**。我们用的是两层 decoder，可以降到一层；deformable attention 的采样点数也能减。
>
> 第三才是砍 backbone 容量。
>
> **注意 BEVPoolv2 这类优化对鱼眼是没用的**——它优化的是 LSS 的 splat 步骤，鱼眼根本不走 LSS。这一点要说清楚，不然会显得在套模板。
>
> 如果砍到精度不达标了，那就要重新审视需求：鱼眼这条的作用是补近场盲区，如果算力实在不够，退路是缩小它的职责——比如只保留正前方和正后方两路，侧向靠超声波兜底。**先砍范围和职责，再砍模型容量，最后才是接受精度下降。**

## 第10题　融合之后那一段做过什么探索（答还没做过）

**我答的**：这一块我目前还没有做过额外的调整，主要是考虑到开头的深度如果落得不准，对后面也会造成影响，所以主要考虑融合之前的优化。

**问题**：回答本身诚实、理由也成立，但**只说了"没做过"，没有给出任何判断**，显得工作范围窄。

**应该这么说（诚实 + 给判断）**：

> 融合之后那一段我确实没有做过结构上的改动，我的工作集中在融合之前——主要是相机支路的深度估计和视图变换。
>
> 这个分工其实也反映了我们对瓶颈的判断：LSS 路线下，图像特征落在哪个 BEV 格子完全由深度决定，深度歪了后面的 BEV backbone 是救不回来的。所以在深度还不够准的阶段，投入产出比最高的是前段。
>
> 如果要做后段，我能想到的方向有几个：BEV backbone 上的多尺度结构（远近目标尺度差异很大）、BEV 空间的 attention 来建立超出卷积感受野的长程关联、以及检测头的解耦设计。但这些的前提是前段的深度已经足够稳，否则改后段是在给一份错位的特征做优化。

## 第11题　辅助小网是什么（说得模糊）

**我答的**：速度真值是帧间差分算的，模型直出会有速度跳变，我们有一个额外的修框辅助网络，修正框之后速度输出会好一些；是另一个同事开发的。

**问题**：说得含糊，"修框之后速度就好了"这个因果链没讲清。

**应该这么说**：

> 它是挂在主模型后面的一个独立的框修正网络，和主模型的训练完全解耦。
>
> 做法是：主模型全部训好并冻结，跑出初步的 3D 框；把这些框连同 BEV 特征一起送进一个小网络，让它去学「预测框和真值框之间的残差」，输出修正后的框。
>
> **为什么修框能改善速度**：因为速度真值本身是从相邻帧的框位置差分来的。框位置有抖动，差分之后抖动被放大成速度噪声——位置误差 10 厘米除以 0.1 秒就是 1 米每秒。所以把框修稳，速度的稳定性自然跟着改善。
>
> 实际效果要如实说：收益有限、不是很明显。线下回归评测里我们不带它，只在线上出。而且它训一次之后就一直用，前面主模型更新了也不影响它。这块是另一位同事开发的，我参与过一次问题定位。

## 第12题　算子不支持怎么定位、怎么解（全推给别人）

**我答的**：那是部署那块同学搞的，算子开发是我们另外一个量化部门来搞，我们只是调用他们的算子，具体修算子还是他们来修，我们只负责定位。

**问题**：整段都在划边界，**没有任何技术内容**。诚实是对的，但"我不做这个"不能作为答案的主体。

**应该这么说（技术内容在前，边界在后）**：

> 定位上，转换日志是第一手线索——不支持的算子通常会有 fallback 或 warning，能直接看出哪一层被回退了。再就是逐层对比转换前后的输出，找第一个出现明显偏差的层。
>
> 解法有三条，按代价从低到高：
>
> **一是模型侧等价替换。** 用被支持的算子拼出等价的功能，比如把不支持的激活函数换成 ReLU、把某些特殊的 reshape 拆成支持的组合。这条最快，只要重训验证一次。我在 RK3588 上就是这么解的——SiLU 换 ReLU。
>
> **二是拆分或降级。** 把不支持的算子那一段拿到 CPU 上跑，其余留在 NPU。代价是数据要在两个器件之间来回搬，时延会上去，只适合计算量小的算子。
>
> **三是让算子侧开发。** 周期最长、风险最高，只有前两条都走不通才用。
>
> 在 BEV 那个项目里，算子开发是专门的部门在做，我这边负责的是从评测结果反推问题定位——判断退化集中在哪些场景，是不是模型侧的问题。

## 附题　LSS 和 Transformer 到底哪个更费算力（必考）

**背景**：面试官说他们考虑走 Transformer 是因为 LSS 计算量大；而我说针孔不用 Transformer 是因为 query 数会爆炸。这两句听起来矛盾。

**真相：不矛盾，因为两者的算力对「覆盖范围」的敏感度是相反的。**

| | 成本主要取决于 | 对 BEV 覆盖范围 |
|---|---|---|
| **LSS** | 相机数 × 深度 bin 数 × 图像特征图面积 | **基本不敏感** |
| **Query（BEVFormer 类）** | BEV 格子数 = 覆盖面积 ÷ 格子边长² | **极其敏感** |

**我们自己的两条支路就是这条规律的两个实例**：

| | 覆盖范围 | 网格 | query 数 |
|---|---|---|---|
| 针孔 | 179.2 × 89.6 m | 448 × 224 | **100,352** |
| 鱼眼 | 12.8 × 12.8 m | 16 × 16 | **256** |

**差 392 倍。**

**应该这么说**：

> 这两个说法不矛盾，因为两种方案的算力对覆盖范围的敏感度是相反的。
>
> LSS 的成本主要由相机数、深度 bin 数和图像特征图面积决定，跟 BEV 格子数关系不大——BEV 网格扩大一倍，LSS 的主要计算量几乎不变。而 query 方案的成本正比于 BEV 格子数，也就是正比于覆盖面积除以分辨率的平方。
>
> **所以覆盖范围大的时候 LSS 划算，覆盖范围小的时候 query 划算。**
>
> 我们内部针孔走 LSS、鱼眼走 Transformer，遵循的就是这一条规律——针孔要覆盖 179×89.6 米、十万个格子，用 query 算力扛不住；鱼眼只覆盖 12.8×12.8 米、256 个格子，差将近 400 倍，Transformer 的代价完全可以接受，而且还顺带解决了畸变的问题。
>
> 而贵司做的是纯泊车，覆盖范围本来就只有十几米，在那个尺度上 query 方案确实更划算，我理解你们的选择。

**加深一句**：BEVFormer 用的是 deformable attention，复杂度对 query 数是线性的；如果用 vanilla cross-attention，复杂度是 query 数乘 key 数，针孔那边直接就不可行了。

## 元教训　这场的三条

**一、"为什么"题不能用"我们是这么分工的"来答。** 组织架构、任务清单、别人负责，都不是理由。理由必须落在技术属性的差异上。

**二、不确定的细节，宁可说"不确定"，也不要临场推演出一套听起来很具体的机制。** 网格分辨率那一段就是反面教材——编出来的东西经不起第三轮追问，而且会连带让人怀疑你前面说的所有内容。

**三、被问"实际碰到过什么问题"时，必须给具体案例。** 流程谁都会讲，案例才是证据。讲流程要快，案例压轴。
