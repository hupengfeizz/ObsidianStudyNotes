## 第1题　多帧点云聚合时动态目标怎么处理（追七轮没讲清）

**他问的**：怎么样把这个多帧点云融合放到一起呢？特别是有动态物体的时候。

**我答的**（被拆成七个来回）：历史三帧通过内外参和坐标系位移到当前帧 → 会有残影，对残影部分直接 mask 掉 → 判断残影的方式是空间距离超阈值、或者和真值标注框做尺寸对齐，不在框范围内就 mask → 被问"那不就缺少运动物体的深度监督了吗"，我说"不会，深度监督在图像支路"。

**问题在哪**：不是答错，是**没有一次性把逻辑说完整**。面试官反复确认"我们不是在讨论运动物体要变稠密吗？你要 mask 掉？"——说明他一直没听懂我在说什么。而这是我简历上的核心优化点之一，讲不清等于这条作废。

**应该这么说（一次说完，四段）**：

> **第一段，先说清楚问题。** 多帧点云聚合的前提是「同一块物体表面在不同帧被扫到」。对静止的东西，把历史帧按自车位姿变换到当前帧，点就精确重合，叠加之后密度真的上去了。但对运动目标，它自己在这几帧里也移动了，自车位姿补偿不了这部分——历史帧的点投过来会落在目标已经离开的位置上，形成一条拖影。如果不处理，等于在深度真值里凭空制造了一片错误的深度。
>
> **第二段，关键前提：这是离线做的，不是在线做的。** 生成深度真值是训练数据准备阶段的事，所以我有三样在线模型没有的东西——一是**标注真值**，动态目标的框和跨帧关联标注里就有，不用靠模型去检；二是**未来帧**，离线处理时第 N 帧的前后帧都在手里；三是**算力**，不受时延约束。这三样决定了离线能做得比在线干净得多。
>
> **第三段，三种处理方式，各有取舍。** 一是直接剔除——用真值框把动态目标圈起来，历史帧落在框里的点全删掉，只保留当前帧的点，最可靠；二是按目标自身速度单独补偿——除了自车位姿补偿，再用真值标注的目标速度把历史点推到当前时刻，能保住密度但依赖速度真值精度；三是只对静态区域聚合，动态那块不叠，实现最简单。
>
> **第四段，收益在哪。** 多帧聚合的主要收益其实在**静态背景和中远距离**——那才是深度监督最缺的地方，单帧点云投到图像上覆盖率不到 5%，60 米外相邻线束间隔已经超过一米。动态目标本来就多在近处、点相对密，即使退化成单帧也够用。**所以这是一个有意的取舍，不是缺陷。**

**被追问"那不就缺少运动物体的深度监督了吗"时**，不要咬定"不会"，要这么答：

> 动态目标那块确实退化成单帧的稀疏度了，这个我承认。但它**没有失去监督**——当前帧的点云本来就在，只是没有变得更密。而且那不是深度监督最缺的地方，最缺的是中远距的静态区域，多帧聚合恰好补的就是那里。

**记忆钩子**：**承认代价，再说明代价为什么可接受**——比咬定"没有问题"可信得多。

## 第2题　CBGS 的采样权重具体怎么设（答成"手工调"，被追四次）

**他问的**：具体的权重该怎么设呢？→ 类别平衡采样这块具体怎么设？→ 参数映射是什么意思？→ **我其实问的就是它怎么样去映射呀？** → 就是还是手动调是吧？

**我答的**：先给一个初始权重，然后通过验证集不断微调，调到一个比较合适的权重……车 100 台、行人 10%、骑行人 1%，权重给 0.3 / 3 / 10 这样一个列表……对，还是手动调。

**问题在哪**：**CBGS 是一个有明确公式的方法，不是靠手调的。** 答成手工调，等于说明没真正理解这个方法，只是在用配置文件里现成的数。面试官连问四次就是在确认这一点。

**应该这么说**：

> CBGS 全称是 Class-Balanced Grouping and Sampling，它的采样比例不是手调的，是**按类别频率算出来的**。
>
> **第一步是分组**：把类别按尺寸和形状的相似性分成若干组，比如车和卡车一组、行人和骑行人一组，组内共享检测头。这样做是避免尺度差异过大的类别在同一个头里互相干扰。
>
> **第二步是重采样**：统计每个类别在训练集里出现的样本数，算出一个采样比例——目标是让**每个类别在一个 epoch 里被采到的期望次数大致相当**。具体是对含有稀有类别的样本做重复采样，重复次数正比于「目标均衡比例 ÷ 当前占比」。**这个数是算出来的，不是试出来的。**
>
> **工程上会在公式基础上做软化**：完全均衡有时会让稀有类别过采样过头、导致过拟合，所以常见做法是对频率倒数开平方根来软化，或者给重复次数设一个上限。**这一层才是需要看验证集调的部分——调的是软化系数，不是从零试权重。**

**再补一句区分两种手段**：

> CBGS 和类别 loss 加权是互补的：**重采样改变的是「样本被看到的频率」，loss 加权改变的是「同一个样本的梯度贡献大小」**。前者从数据侧补，后者从损失侧补。我们的 loss 权重大致是行人 2、骑行人 1.5、车 0.5 这个量级。

## 第3题　训练集规模到底多少（第三次变口径 + 被当场验算）

**他问的**：这个大概每次迭代一次要多长时间？→ 多少卡？→ 训几轮？→ **8卡几千万帧，两天能跑完吗？700多轮跑不完吧？**

**我答的**：两天、8 卡、100 到 120 轮，几千万帧。

**问题在哪**：两个。

一是**口径已经变了三次**：8/4 第四场说"几百万帧"又改口"200 万帧"；8/4 第六场说"几百万帧"；这场说"几千万帧"。三次三个量级。

二是**这四个数放在一起，数学上很难成立**。面试官是在验算——几千万帧 × 120 epoch ÷ 8 卡 ÷ 两天，这个吞吐率不现实。他一算就发现了。

**应该这么说**：

> 训练集在**百万帧量级**。训练在昇腾集群上跑，常规 8 卡并行，一次完整训练大约两天。

**被追问更具体时**：

> 我看到的配置里是两百万帧左右这个量级。全量数据是数据组在维护，总量我没有经常去核对——我这边关注的主要是每一轮新增的数据是否符合预期。

**通用原则（这条比数字本身重要）**：

**不要把「训练集规模 + epoch 数 + 卡数 + 训练时长」四个数一起报。** 四个数一起给，对方必然会验算，而四个里只要有一个不准，整组就崩，还会连带让人怀疑你前面说的所有数字。

**安全做法**：只给能确定的那部分。「8 卡训一版大约两天」这一句是安全的，因为它是你亲身经历过的；「几千万帧 × 120 轮」是听来的，不该主动往外报。

## 第4题　每个 epoch 都要遍历几千万样本吗（答成 DataLoader）

**我答的**：不会，通过 DataLoader 提前进行集中处理，后面每次直接迭代这个处理好的数据。

**问题在哪**：**DataLoader 不改变「一个 epoch 遍历多少样本」这件事**，它只负责取数和拼 batch。这个回答说不通，而且面试官紧接着问"这个 DataLoader 部分不是你实现的是吗"——他已经判断出你没写过这块。

**应该这么说（两条，我们两条都用了）**：

> **一是 CBGS 重采样本身就改变了 epoch 的构成。** 重采样之后，一个「epoch」不再是「把原始数据集完整过一遍」，而是「按重采样后的索引列表过一遍」——稀有类别的样本被重复，常见类别可能被下采样。所以 epoch 的实际长度和原始样本总数不是一回事。
>
> **二是多任务共训时按 iteration 对齐，不按 epoch 对齐。** 共网里 BEV、GOD、可行驶域几个任务各有独立数据集、规模差一个数量级，做法是统一跑固定的 iteration 数，各任务实际跑了几个 epoch 各不相同。对齐的是迭代次数，不是轮数。

**如果这块确实不熟**，正确的回法是：

> 数据管线这块是框架里既有的，我没有改过它的实现。我了解的是策略层面——我们用了 CBGS 类别重采样，所以一个 epoch 不等于原始数据完整过一遍；多任务共训那边是按 iteration 对齐的。具体的 DataLoader 实现细节我不敢说得太细。

## 第5题　数据迭代有系统性规划吗（答成救火式）

**他问的**：你们有没有一些迭代计划？还是说发现了 corner case 然后立马就去采一堆数据，没有一个系统化的迭代方案？

**我答的**：目前是看模型问题在哪就有针对性地解，因为版本交付压力比较大，一般就是列一些场景然后去采集。

**问题在哪**：这是**诚实但没有章法**的回答。同样的事实，说出来像"哪里着火救哪里"，听不出方法论。

**应该这么说（同样的事实，讲出闭环）**：

> 我们的迭代节奏是由**版本目标倒推**的，不是随机救火。
>
> **第一步，版本目标先定**：比如某个版本要求关键场景的抽检通过率达到某个门槛，这是交付要求，先明确。
>
> **第二步，差距分析**：拿当前版本在场景化防护网上的结果，按误检、漏检、速度动静、检出距离这些专题拆开，看哪些专题离目标最远——**这一步决定这一轮做什么**。
>
> **第三步，数据规划**：定位到具体的弱项场景，制定挖掘策略或者下发定向采集需求。量级是有经验数的——单个场景专项上量两三百个 clip（每个 clip 三四十秒、10Hz 标注，约四百帧）通常就能在该专题的指标上看到收益；高危场景会加到四百 clip。
>
> **第四步，回灌与回归**：新数据加进全量训练集重训，再跑一遍完整防护网，确认目标专题涨了、其他专题没恶化，才算这一轮完成。

**为什么这么说重要**：同样的事实，按「版本目标 → 差距分析 → 数据规划 → 回归验证」讲出来是一套闭环方法论；按「哪里有问题修哪里」讲出来是救火。**事实没变，对方对你的判断完全不同。**

## 第6题　检测和跟踪做成端到端了吗（漏掉自己模型里的 TrackHead）

**他问的**：你没有使用检测跟踪端到端的方案吗？就是跟踪也通过 query 的方式去做。

**我答的**：目前应该就是……确实在卡尔曼滤波这一块还不是完全的端到端。

**问题在哪**：**我们模型里其实有一个 Transformer 的 ID 匹配跟踪头**，这个完全没提，只说了卡尔曼。等于把自己模型里更先进的那部分藏起来了。

**应该这么说**：

> 我们是**混合的**。检测头之后有一个时序实例增强模块，再接一个 Transformer 的 ID 匹配跟踪头——这一段是学出来的、在网络里的。之后仍然保留了一道轻量的卡尔曼滤波，做运动平滑和轨迹的生命周期管理。
>
> **为什么保留卡尔曼**：学习式的跟踪在关联上更强，但它没有显式的运动模型——漏检时补不出预测帧、也给不出平滑的速度。卡尔曼提供的是这一层的兜底和可解释性。量产上这类「学习模块 + 传统模块」并存的结构很常见，本质是用确定性去兜住学习模块的不确定性。
>
> 完全端到端的跟踪，比如 MOTR、TrackFormer 那类用 track query 跨帧传递的做法，我了解思路，但我们没有全量走这条路。

## 第7题　Smooth L1 替代 L1 的机理（术语用错）

**我答的**：L1 是一个比较粗糙的损失函数，对于零点几每秒这个区间它精度不高，它是**一个整数的损失函数**……Smooth L1 解决了零点附近梯度不连续的问题。

**问题在哪**：「精度不高」「整数的损失函数」都不是准确的表述（"整数"应该是"常数"，可能是口误或转录问题，但"精度不高"这个说法本身就不对——损失函数没有"精度"）。后半句"零点附近梯度不连续"倒是对的。

**应该这么说（用梯度讲，不要用"精度"）**：

> 根子在**梯度行为**，不在精度。
>
> L1 的梯度在整个区间上是**常数**（正负 1），误差再小梯度也不变小。低速目标的速度值本身就在零点几这个量级，误差落在零点附近，常数梯度会让参数在最优点附近来回震荡、收敛不到精确值。
>
> Smooth L1 在误差小于阈值 beta 的时候是**二次的**，梯度随误差线性减小、趋近于零——所以在零点附近能精细收敛；误差大于 beta 时退化成线性、梯度恒定，这一段保留了 L1 对离群样本的鲁棒性。
>
> **beta 怎么定**：设在真值噪声的量级上。我们的速度真值是相邻帧标注框位置差分来的，位置标注误差约 10 厘米除以 0.1 秒帧间隔，噪声在 1 米每秒量级，所以 beta 取这个量级。含义是——误差比噪声还小的时候用二次项精细收敛，误差远大于噪声时按线性处理、不让坏真值主导梯度。
>
> **为什么不用 L2**：L2 的梯度和误差成正比，离群样本的梯度会被线性放大。速度真值噪声本来就大、远距能到 3 米每秒，用 L2 的话少数坏真值就能主导整个 batch 的梯度方向。

## 第8题　每次只加 200 clip 却要全量重训，代价不是很高（没正面回应）

**他问的**：你本来是一个几千万帧的大池子，每次只用 200 个 clip 过来，就要把整体去微调一遍，我觉得这个代价非常高啊。

**我答的**：您的意思是说只用这 200 个去训吗？还是说其他的那个整个模型对其他目标，那不就……（没有正面回答）

**问题在哪**：这是一个**很好的技术质疑**，我把它当成了误解去澄清，没有正面回应"为什么明知代价高还这么做"。

**应该这么说**：

> 这个代价确实高，我们是清楚的。但全量重训是有意选择的，原因有三个：
>
> **一是灾难性遗忘。** 只用新增的 200 个 clip 微调，模型会迅速在这批数据上过拟合、同时把其他场景的能力忘掉。量产的底线是「不允许任何一项恶化」，增量微调很难守住这条线。
>
> **二是数据分布必须重新平衡。** 我们用 CBGS 类别重采样，新增数据会改变各类别的占比，采样比例要跟着重算。这个平衡是在全量数据上算的，只训增量的话这套机制就失效了。
>
> **三是回归验证的成本才是大头。** 训练两天，但送测前要跑一遍完整的场景化防护网、确认没有恶化项，这一步的成本和风险都比训练本身高。既然无论如何都要跑全量回归，训练侧省那点时间意义不大。
>
> **如果算力更紧张**，可行的折中是：先冻结 backbone、只微调后段（我们共网的第二阶段就是这么做的），或者用少量老数据混合新数据做 rehearsal 来抑制遗忘。但在算力够用的前提下，全量重训是最稳的。

**这题的价值**：**能说出「我知道这样代价高，但为了守住某条底线而接受」，比说「我们就是这么做的」高一个层级。**

## 第9题　手撕代码环节（直接弃权，第二次了）

**现场**：对方说还有一个 coding 环节 → 我答"目前还没有做准备" → "其实不用准备，你身边有电脑吗" → "有，但没有环境" → "没有编辑器吗" → "没有" → 环节取消。

**问题在哪**：**这已经是第二次了。** 8/4 曹工那场同样情况，事后写进了《工程基本功速查》——"编辑器提前开好、准备一个能跑的 scratch.py"——但没有落实。

**从现在起，每场面试前的固定动作（三分钟）**：

1. 打开编辑器（VS Code 或任意），**关掉 Copilot / AI 补全**
2. 新建一个空的 `scratch.py`，跑一次 `print(1)` 确认环境能用
3. 开一个终端窗口备着
4. 测一下屏幕共享，知道要分享哪个窗口

**不管 HR 有没有说会考代码。**

**被问到时的正确回法**：不是"没准备"，而是——

## 元教训　这场的三条

**一、机制层的问题，要一次说完整，不要挤牙膏。** 动态目标那题被拆成七个来回，根本原因是我每次只说一小块，对方拼不出全貌。**复杂机制的正确讲法是先给结论和框架，再填细节**——「这件事分三种做法，各有取舍，我们选的是第一种，原因是……」。

**二、别人的方法要知道它的原理，不能只知道配置里的数。** CBGS 那题暴露的就是这个——用过、但不知道它的采样比例是算出来的。**凡是简历上写了名字的方法，都要能讲出它的核心机制，否则等于给自己埋雷。**

**三、数字要么全对，要么少说。** 训练规模、epoch、卡数、时长四个数一起报，对方必然验算。**只报你亲身经历过的那部分，听来的数字宁可说"这块是数据组维护的，我没有经常核对"。**
