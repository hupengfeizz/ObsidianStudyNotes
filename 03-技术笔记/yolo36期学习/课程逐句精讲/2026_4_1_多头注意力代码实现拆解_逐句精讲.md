## Part 1 · 从一句话到一个张量：字典 · 嵌入 · 文本对齐（00:07:04 – 00:20:00）

**【本段在讲什么】** 正式讲代码前，谢博先把"文本怎么进神经网络"的完整链条复述一遍：查字典 → 嵌入 → 对齐 → 张量。这段看起来是复习，其实是在给后面 40 分钟的 shape 推导铺地基——因为 `(2, 4096, 320)` 这三个数字分别来自"批处理""对齐长度""嵌入维度"，你不知道它们的出身，后面切片就永远在猜。他还顺手补了两个高频面试点：embedding 模型的本质、以及"为什么 NLP 用 LayerNorm 不用 BatchNorm"。

---

### 01 第一步查字典：把文字变成数字，才能用数学（00:07:55 – 00:08:10）

> **谢博**：「我们说第一步要查字典。查字典就把它变成数字了。这个变成数字就可以用数学的方法来搞定它了，听懂这意思吧。」

- **【直译】** 神经网络只会算数，不认识汉字。第一步是把每个字/词映射成词汇表里的一个整数 ID。
- **【推导/代码】** 这一步就是 tokenizer：`tokenizer(sentences, padding=True, truncation=True, return_tensors="pt")` 产出 `input_ids`。【画面】00:15:14 的 PPT 第 25 张里能看到真实值：`'input_ids': tensor([[101, 2769, 1599, 3614, 782, 2339, 3255, 5543, 511, 102, 0, 0, ...]])`——101 是 `[CLS]`、102 是 `[SEP]`、后面一串 0 是补位。
- **【连接】** 对照视觉：你做 YOLO 时"查字典"这一步是不存在的，因为像素本身就是 0–255 的数字，可以直接归一化进网络。NLP 多这一步，是因为符号是离散的、没有天然的数值序关系。

---

### 02 第二步嵌入：数字变向量，embedding 模型其实就是一层全连接（00:09:33 – 00:11:53）

> **谢博**：「嵌入实际上这个嵌入模型呢，实际上它是一个神经网络，对不对。那用什么样的神经网络呢……实际上这个嵌入的神经网络很简单，我们自己可以设计一个，就设计一个全连接就可以了。嵌入的目的，是不是要把一个数字比如说 10，变成一个向量，这个长度 768，你可以自己定。怎么样把一个数字变成一个向量？我是不是用一层全连接就可以搞定了。所以这个 embedding 模型也很简单。」

- **【直译】** 别被"嵌入模型"四个字唬住。它的输入是一个 token ID，输出是一个定长向量（例如 768 维），中间就是一层线性变换。
- **【推导/代码】** PyTorch 里就是 `nn.Embedding(vocab_size, 768)`。它在数学上等价于：把 token ID 变成 `vocab_size` 维的 one-hot 向量，再乘一个 `(vocab_size, 768)` 的权重矩阵——所以它**确实是一层全连接**，只不过因为输入是 one-hot，可以退化成"查表"来省掉 99.99% 的乘法。
- **【为什么】** 老师此刻讲这个，是要打掉"embedding 是某种神秘外挂"的印象：它和你 MNIST 模板里的 `nn.Linear` 是同一个东西，只是用途不同。这样后面讲 `w_q = nn.Linear(320,320)` 时你才不会觉得"注意力里怎么冒出全连接"。
- **【连接】** ⚠ 老师说"输入节点是不是一个啊"——严格讲输入节点是 `vocab_size` 个（one-hot），不是 1 个。这一点见纠错表 B-5。

---

### 03 用现成 embedding 模型只需盯两件事：输出维度 + 词汇表大小（00:12:08 – 00:14:20）

> **谢博**：「但是 embedding 模型又不是只有一个呀。就像分类网络难道只有一个神经网络吗，这不到处都是吗。你总不可能用卷积吧，你卷积怎么卷呢，它的输入是一个一个数啊……假如说你不去设计这个 embedding 模型，你就可以拿来用。当然我们用这个模型，那你要关注它的什么东西呢？你关注它输出的维度，你要关注它的词汇表的大小，至少这两个你要关注。」

- **【直译】** 自己训 embedding 也行，用现成的（BERT 之类）也行。用现成的时候只需要问两个数：输出多少维、认识多少个词。
- **【为什么】** 这两个数直接决定下游网络的接口：输出维度 = 下游第一层的 `in_features`；词汇表大小决定 OOV（未登录词）概率。老师顺带否掉了"用卷积做 embedding"——卷积要求输入是 CHW 的网格结构，而这里输入是一个孤立的整数，没有邻域可滑。
- **【连接】** 这就是你在 BEVFusion 里选相机 backbone 的同款思路：你不关心 Swin-T 内部怎么算，只关心它吐出来的多尺度特征通道数是 `[96,192,384,768]`——因为那决定了 FPN neck 的 `in_channels` 怎么填。
- **【画面】** 00:15:14 的 PPT 第 25 张里，项目树可见 `bert-base-chinese/`（含 `vocab.txt`、`tokenizer.json`、`model.safetensors`）与 `google_bert.py`——这是他上节课的实操文件。

---

### 04 文本对齐：神经网络对输入形状是有硬要求的（00:14:50 – 00:17:10）

> **谢博**：「这里面就涉及到一个句子对齐的问题，叫文本对齐。为什么要文本对齐呢？是因为我们对这个神经网络的输入 tensor，它是不是有要求啊，形状是不是有要求啊。它是不是 B，然后叫 sequence length，然后再乘以 embedding length……比如说你写的 B × 4096 × 768，意思是这个神经网络最长一个句子是 4096 个 token，每个 token 的 embedding 长度是 768。那我并不是说我要处理的每句话都是 51 个 token 啊，有长有短。那是不是也要凑成 51 个 token 呢？那就用 padding 嘛。」

- **【直译】** "文本对齐"这个洋气的词，实际意思就是：神经网络的输入张量形状是写死的，短句子必须补齐到规定长度。
- **【推导/代码】** 输入张量的三元组一律是 `[batch_size, seq_len, embed_dim]`。本课的 `(2, 4096, 320)` 就是 B=2、L=4096、D=320。老师故意举了个"51 × 72"的怪例子，就是想说明这三个数完全是设计者定的，没有神圣性。
- **【连接】** 这和你 YOLO 里的 letterbox 是同一件事：`640×640` 是网络写死的输入，任意尺寸的图必须 resize + 灰边填充凑上去。区别在于 YOLO 补的是灰色像素（114），NLP 补的是 `[PAD]`（id=0）。
- **【画面】** 00:15:14 PPT 第 25 张标题就是红底黄字：**「文本对齐，text alignment，不足补 0」**，下方调试器里 `input_ids` 那一串尾部的 `0, 0` 被红框圈出，`attention_mask` 对应位置是 `1,1,1,...,0,0`。

### 05 补 0 引出的经典面试题：为什么 NLP 用 LN 不用 BN（00:14:40 – 00:14:47 + 00:17:16 – 00:17:35）

> **谢博**：「然后提到这个问题的时候我们解释了，为什么不能用 BN，要用什么？要用 LN……那一 padding 的话，就补了很多零出来了嘛。那零一出来，如果说你还像图像一样做 batch normalize，是不是它其他有数的值也被拉到你这个位置来了呀。那你特征不就一 normalize 就丢失掉了吗。」

- **【直译】** BatchNorm 是"跨样本、同一个特征位置"求均值方差。一批句子里补了一堆 0，这些假 0 会把真实 token 的统计量往下拽，特征就被冲淡了。
- **【推导/代码】** BN 在 `(B, L, D)` 上是沿 B（和 L）方向统计；LN 是**在单个 token 的 D=320 个数内部**统计。后者完全不碰别的样本，padding 补多少 0 都影响不到有效 token。
- **【为什么】** 除了 padding，还有两个理由值得一起背：① NLP 的 batch 内序列长度差异极大，BN 的统计量抖动剧烈；② 推理时 batch=1 或流式解码，BN 的滑动均值失效，LN 没有这个问题。
- **【连接】** 反向印证你熟悉的一侧：图像分类里所有样本都 resize 到同尺寸、没有"无效像素"，所以 BN 好用。而 Transformer 系的 BEV 模型（BEVFormer、DETR3D）里全是 LayerNorm，就是这个原因的延续。

---

### 06 为什么要 batch：GPU 并行，8 张图一次前向 ≠ 8 倍时间（00:17:50 – 00:19:40）

> **谢博**：「就是因为我一次性需要让它输入多句话，就像你做视觉一样，让它一次性输入多张图片，一起做前向传播，结果一起出来了。为什么有这个要求呢？效率高嘛。我八张图片是不是一次前向传播就做出来。那我一次做八张，和我跑八次，难道时间不一样吗？那可不一样。你一次做，有个 batch size 进去可能是十秒；那你如果八张分开做，可能不一定是八十秒，但是可能是六十秒。这就是显卡它能并行处理。」

- **【直译】** batch 存在的唯一理由是效率：GPU 有几千个核心，一次只喂一个样本等于让绝大多数核心闲着。
- **【推导/代码】** 一次前向的时间 ≈ 固定开销（kernel launch、数据搬运、权重读取）+ 与 batch 近似线性的计算量。batch 越大，固定开销被摊薄得越狠，所以 8 张一起做只要 60 秒而不是 80 秒。
- **【为什么】** 这条对你不是纸上谈兵：你在 4060 上跑 BEVFusion 实测 **0.481 s/iter**，如果把 batch 从 1 提到 2、时间没有翻倍，那多出来的就是并行红利；如果几乎翻倍，说明显存带宽已经打满、GPU 早就没有空闲算力了——这个判断是你调 batch size 的直接依据。
- **【连接】** 这也是为什么 batch 维在后面所有算子里都是"透明"的：它只是把同一份计算复制 N 遍，不产生任何跨样本的信息流。这个性质在 Part 3 会被反复用到。

**【小结】** ① 一句话进网络的完整链条是：查字典拿 token ID → 嵌入成向量 → padding 对齐 → 组成 `[B, L, D]` 张量。② embedding 模型的本质是一层全连接（等价于 one-hot 查表），用现成的只需盯"输出维度 + 词汇表大小"。③ padding 补 0 是"NLP 用 LN 不用 BN"的直接原因，而 batch 存在的唯一理由是 GPU 并行的效率红利。

## Part 2 · 为什么是注意力、为什么是多头（00:20:00 – 00:26:01）

**【本段在讲什么】** 张量准备好了，接下来要"理解这句话"。谢博用两问两答完成动机推导：第一问"为什么不用卷积/全连接而用注意力"，答案是语义随语境变，必须让 token 互相询问；第二问"为什么要多个头"，答案是一次询问只能问出一个角度的关系，换个角度就得重问一遍。这两段是 3_29b 原理课的浓缩复述，但他在结尾抛出了本课真正的靶子：**看着结构图写出代码不难，难的是从代码里把"头"重新拆出来**。

---

### 07 注意力在干什么：让 token 互相问"我跟你什么关系"（00:20:00 – 00:21:00）

> **谢博**：「变成一个 tensor 之后，我就要去理解这句话是什么意思。怎么去理解它呢？我们说用卷积不行的，用全连接不行的，要用注意力机制。为什么注意力机制那么适合理解一个句子到底是什么意思呢？让这些 token 不断地去问别人：我跟你是什么关系。你看跟卷积就不一样，卷积是说一张图片我用一个核，然后去移动去提特征。」

- **【直译】** 注意力的物理图像是"询问"：每个 token 主动向句子里所有 token 提问，得到一组关系强度，再按这组强度把别人的信息汇总过来。
- **【推导/代码】** 和卷积的根本差别在**感受野**：卷积核是固定大小的窗口，token 只能看到左右 k 个邻居；注意力是全连接的图，任意两个 token 之间都有一条直接边，距离 4095 也是一步到位。
- **【为什么】** 语言的依存关系是长程且不规则的——"武汉市长江大桥"里的歧义要靠整句话消解，一个 3×3 的窗口永远看不到。
- **【连接】** 这条差异正在被搬到 BEV 里：BEVFormer 的 `SpatialCrossAttention` 让每个 BEV query 直接去 6 路相机特征上采样，而不是像 LSS 那样靠固定的深度分布 + 卷积聚合。你现在读的这套 Q/K/V shape，就是那份代码的基础形态。

---

### 08 为什么不能把语义写死：因为有语境（00:21:02 – 00:21:30）

> **谢博**：「你为什么要让它去问呢？为什么不把这些语义做死呢，固定死呢？我们说不行呢，因为有语境呢。所以同样一个词在不同的句子里面，它有不同的意思。所以它要结合它的上下文一起去问，它才能知道在这句话里面具体是什么意思。」

- **【直译】** 词向量表里的"苹果"只有一个固定向量，但"吃苹果"和"苹果发布会"里的苹果不是一个东西。所以必须有一层机制，根据上下文把静态词向量刷新成动态的语境向量。
- **【推导/代码】** 这正是 Self-Attention 的输出语义：输入 `x[t]` 是**静态**嵌入，输出 `output[t]` 是**已经融合了全句信息**的动态表示。同一个词在两句话里，输入相同、输出不同。
- **【画面】** 00:21:35 PPT 第 26 张《断句大挑战》给了三个绝佳的中文歧义例子：**「用蛇毒毒毒蛇，毒蛇会不会被蛇毒毒死？」「要是行，干一行，行一行，行行行。」「武汉市长江大桥。」** 谢博在这张片上手写标注了 H1、H2（两个头）——他是想说：光靠一个头去问"你是谁的主语"是不够的，"行"这个字的读音/词性/角色需要多个角度同时判定。
- **【连接】** 这也是你后面理解位置编码的钥匙：如果没有位置信息，"武汉市长江大桥"和"江大桥市长武汉"在纯注意力眼里是一模一样的集合。

---

### 09 一个头的定义：每个 token 都要问一遍所有人（00:21:38 – 00:22:25）

> **谢博**：「我们讲的例子是 OBS 去问 PEPS。那把这个模型往这里一套，那就是用这个 token 去问谁呢，问其他的这些 token。然后我们说这样问还不够，比如说第一个 token 问完了，第二个是不是也要问呢？每个人都要问，问一次整个句子里面其他的 token。这样就构成了每个人都问了一遍，他对这个句子就理解深刻一点了。」

- **【直译】** "一个头"= 把"每个 token 询问全部 token"这件事完整做一轮。做完一轮，每个 token 都拿到一条融合了全句的新特征。
- **【推导/代码】** 一轮的计算量正是 `4096 × 4096` 次点积——这就是后面 `scores` 张量最后两维的来源。注意这个 O(L²) 才是 Transformer 显存爆炸的根源：4096² × 4 字节 ≈ 64 MB，**一个头一句话就 64 MB**，16 组就是 1 GB 出头。
- **【连接】** 你后面要读的 FlashAttention、稀疏注意力、Linear Attention，全部都是在攻这个 `4096×4096`。先把它是怎么长出来的看清楚，那些优化才有意义。

---

### 10 第二个头 = 换个问题再问一遍（00:22:27 – 00:23:28）

> **谢博**：「但是这样还不够啊。我还要从另外一个角度，再把刚刚那个故事重复一遍。什么意思呢？还是那个 token 又来问，但是问的是另外一个问题。所以这个就产生什么呢，这叫一个头，这叫第二个头。就相互问候一遍——只能问候自己哈，不能问候别人。那我给你的例子里面，问候几遍呢？问候八遍，所以叫八个头嘛。」

- **【直译】** 多头 = 把"全员互问"这个流程重复 8 遍，每遍关注的关系类型不同（谁是主语、谁是修饰语、谁和我构成一个词……）。
- **【推导/代码】** 8 遍之间**完全独立**：各自的 Q/K/V 来自不同权重、各自算各自的 4096×4096 分数、各自提各自的 40 维特征。唯一的交汇点是最后 concat。这一点谢博在 00:55:31 说得极准："**每个头在计算 QKV、以及计算权重分数、以及去提取特征的时候，它们都是没有关系的，都是独立自己做自己的，最后才把这些特征合在一起。**"
- **【为什么】** 为什么不直接把单头的维度从 40 加到 320？因为单头 softmax 后只有一个概率分布，一个 token 最终只能"重点看"少数几个位置；8 个头就是 8 个分布，可以同时在 8 个不同的位置集群上聚焦。这是表达力的差别，不是参数量的差别（参数量完全一样）。
- **【连接】** 对照你熟的 YOLO CA（Coordinate Attention）：那是"沿 H 和沿 W 两条路径分别做池化再融合"，同样是"多角度看一遍再合并"的思路，只是它的角度是人工指定的（H 方向、W 方向），而多头的角度是学出来的。

### 11 本课的靶子：看图写代码不难，从代码里拆出"头"才难（00:23:43 – 00:25:52）

> **谢博**：「这个问题我们有两个层次要求去理解它。第一个，它是不是这个网络的结构图已经给你画出来了呀，最低的一个要求是什么呢？你看到这个是不是要能把它代码写出来。这个对我们来说没有什么难度……人家已经把图给你了呀，你就按部就班地，碰到哪里在 PyTorch 里面用哪个算子，是不是就可以了。所以这件事情不难。第二件事情是什么呢？我们说这个叫多头注意力，我们要去理解它呀，理解它怎么就是多头。我们上一节课讲到这里的时候结果卡壳了……他就是把多个头一次性算出来了，其实本质还是我们那个 OBS 观察 PEPS。」

- **【直译】** 照着结构图翻译成 PyTorch 是体力活；难点在于代码把"8 个头"折叠进了张量维度，你要能反向把它展开回"OBS 观察 PEPS"那套朴素流程。
- **【为什么】** 老师明确点出这是**上节课的遗留卡壳点**，学员花了几天还是没通。所以本课的整个方法论是"拆"——用切片提问反复验证你能否在折叠后的张量里定位任意一个头的任意一个 token 的任意一段数。
- **【连接】** 这个"折叠/展开"的能力就是你转 BEV 岗位最需要的。BEVFusion 的多相机分支把 `(B, N_cam, C, H, W)` reshape 成 `(B*N_cam, C, H, W)` 去过 backbone，再 reshape 回来做视锥变换——和本课的 `(2,8,4096,40) → (16,4096,40)` 是同一个动作、同一个坑。

**【小结】** ① 注意力适合理解语言，是因为语义随语境变、且依存关系是长程的，卷积的固定窗口做不到。② "一个头"= 全体 token 互问一轮；"八个头"= 换 8 个角度重做 8 轮，8 轮之间从 QKV 到分数到特征全程独立，只在最后 concat 才汇合。③ 本课的真正任务不是写代码，而是从"一次算完"的张量里把 8 个头重新定位出来。

### 13 x 的三个维度分别是什么（00:32:17 – 00:32:50）

> **谢博**：「这里是我们输入的 tensor，`(2, 4096, 320)`。我们要理解这个是什么意思啊。这里是不是有两句话呀，这个 2 代表是不是有两句话呀。有两句话，每句话有多少 token 呢，4096。然后每个 token 的嵌入是多少呢，320。听懂这个逻辑，你先要明白这件事情。」

- **【直译】** 逐维翻译：2 = 两句话；4096 = 每句话有 4096 个 token；320 = 每个 token 用 320 个数表示。
- **【推导/代码】** 【画面】01:04:25 调试器里可直接读到 `x = {Tensor: (2, 4096, 320)}`、`batch_size = {int} 2`、`seq_len = {int} 4096`、`embed_dim = {int} 320`。这三个变量是 `forward` 第一行 `batch_size, seq_len, embed_dim = x.shape` 解包出来的——注意**解包顺序就固化了维度语义**。
- **【连接】** 记住这个"2 · 4096 · 320"的三元组，本课接下来所有的 16、40、4096×4096 都是从它推出来的，没有第四个来源。

### 14 batch 维是独立的：第 0 句话永远不会观察第 1 句话（00:32:51 – 00:33:26）

> **谢博**：「两句话我们现在是自注意力哦。第 0 句话会观察第 1 句话吗？不会。因为前面你要记住这个是 batch size，这两句话是独立行动的。就像你做图像的识别、分类一样。所以这两句话它是没有关系的，它实际上就是批处理。」

- **【直译】** batch 维只是"把 N 份独立计算并排放在一起"，不同 batch 之间不存在任何信息流。
- **【为什么】** 老师反复强调这一点，是因为后面第 0 维会被改造成 16（2 句 × 8 头），如果你以为 batch 维会交叉，那 16 这个数字就永远解释不通。
- **【连接】** 和 BN 对比一下就更清楚：BN 是**唯一**会让 batch 内样本互相影响的算子（因为它跨样本统计均值方差）。这也从另一个角度解释了 Part 1 的 BN/LN 之争——LN 保证了 batch 维的严格独立性。

### 15 用"拆开跑再拼回来"验证 batch 的语义（00:33:27 – 00:34:33）

> **谢博**：「我们把 x0 输进去和 x1 输进去，让它做两次前向传播，然后再把这个结果合并起来；跟把这个 x 直接输到这个神经网络里面去，然后这个神经网络产生的结果是一样的。这个就叫 batch，叫批处理。不会存在说 x0 里面的东西来观察 x1 里面的东西，不存在的事情。」

- **【推导/代码】** 这是一个可以真跑的等价性验证：
  ```python
  y_full, _  = self_attention(x)                       # (2,4096,320)
  y0, _ = self_attention(x[0:1])                       # (1,4096,320)
  y1, _ = self_attention(x[1:2])
  torch.allclose(y_full, torch.cat([y0, y1], dim=0))   # → True
  ```
  只要网络里没有跨 batch 的算子（BN、某些 pooling），这个断言必然成立。
- **【为什么】** 老师给的是"定义式验证法"：一个维度是不是 batch，判据不是它叫什么名字，而是**拆开算再拼起来结果是否一致**。这个判据在 Part 5 会被直接复用来解释 16 这个维度。
- **【连接】** 这个技巧你调 BEV 模型时特别有用：怀疑某个自定义算子写错了 batch 处理，就用 batch=1 和 batch=2 各跑一遍对比数值，一秒定位。

### 16 建对象、进 forward：注意力分三步（00:34:54 – 00:35:40）

> **谢博**：「这个地方我们把这个传进去，生成这个注意力机制这个类的对象，然后把一些参数传进去。我们现在是要做几个头啊，八个头，你可以改。然后 embedding 的长度是 320。然后我们看这个，盯它的 forward。第一步我们要干嘛呢……我们说注意力机制是不是分三步啊。第一步干嘛？计算 QKV，用全连接去算。」

- **【直译】** 注意力的标准三步：① 线性变换算出 Q、K、V；② Q·Kᵀ 算分数、缩放、softmax 得权重；③ 权重乘 V 加权求和。代码里就是这三段。
- **【画面】** 00:40:27 单帧抄下了完整的 `__init__`：
  ```python
  class MultiHeadSelfAttention(nn.Module):
      def __init__(self, embed_dim, num_head):
          self.embed_dim = embed_dim
          self.num_head  = num_head
          assert self.embed_dim % self.num_head == 0, "embed_dim 必须能被 num_heads 整除"
          self.head_dim  = self.embed_dim // self.num_head   # 每个头的维度，如 320 // 8 = 40
          # Q, K, V 的线性映射，输入和输出都是 embed_dim 维
          self.w_q = nn.Linear(self.embed_dim, self.embed_dim)
          self.w_k = nn.Linear(self.embed_dim, self.embed_dim)
          self.w_v = nn.Linear(self.embed_dim, self.embed_dim)
          # 输出的线性映射，将多头拼接后映射回 embed_dim 维
          self.w_o = nn.Linear(self.embed_dim, self.embed_dim)
  ```
  调试器同步显示 `embed_dim = 320`、`head_dim = 40`、`num_head = 8`，四个 Linear 全是 `Linear(in_features=320, out_features=320, bias=True)`。
- **【推导/代码】** 那句 `assert` 就是整个多头设计的硬约束：**embed_dim 必须被 num_head 整除**，否则 320/7 不是整数，切不出等长的头。这是面试常问的"为什么 d_model 一定要能被 h 整除"的代码级答案。

**【小结】** ① 全课的常量只有一组：B=2、L=4096、D=320、H=8，推出 head_dim=40 和 B×H=16。② batch 维的判据是"拆开算再拼起来结果不变"，自注意力里两句话永不交叉。③ `__init__` 里四个 Linear 全是 `320→320`，`assert embed_dim % num_head == 0` 是多头能成立的硬前提。

## Part 4 · 第一刀：8 个 Linear(320,40) 怎么变成 1 个 Linear(320,320)（00:35:00 – 00:45:03）

**【本段在讲什么】** 这是全课含金量最高的十分钟，也是"代码看不懂"的第一个真正病灶。按原理讲，8 个头应该有 8 组独立的 `W_q`，每组把 320 维压到 40 维；但代码里只有一个 `nn.Linear(320, 320)`。谢博当场在 IDE 里**手写出等价的展开版代码**（`self.w_q1 = nn.Linear(320, 40)`、`Q_1 = self.w_q1(x)`……），逐条论证"一层宽的 = 八层窄的并排"，还顺手枪毙了一个学员最容易犯的错误写法。

### 17 每个 token 都要产生自己的 Q、K、V，因为角色有两个（00:35:45 – 00:36:11）

> **谢博**：「QKV 是谁去算？是不是每个 token 会产生自己的 QKV。为什么它要产生自己的 QKV 呢？因为它去问别人的时候需要 Q；但是当别人来问它的时候需要什么呢，需要它的 K 和 V。所以每个 token 它要产生 QKV。」

- **【直译】** 每个 token 同时扮演两个角色：作为提问者时用自己的 Q，作为被提问者时用自己的 K（对暗号）和 V（交出内容）。所以三样都得备齐。
- **【推导/代码】** K 和 V 分工的关键：**K 决定"你能被匹配到多少"，V 决定"匹配上之后你贡献什么"**。这两件事被解耦成两个矩阵，是注意力设计里最精妙的一笔——如果 K=V，那"相关性"和"内容"就被绑死，模型没法学出"这个词很重要但携带的信息很少"这种情况。
- **【连接】** 自注意力里 Q/K/V 来自同一个 x；交叉注意力里 Q 来自 A 序列、K/V 来自 B 序列。老师在 01:55:12 收尾时点了这句：「交叉注意力就是他的观察者和被观察者不是同一个句子。」

### 18 一行代码算出"两句话每个 token 的八个头的 Q"（00:36:12 – 00:36:54）

> **谢博**：「我们看这里产生 Q，先产生 Q。它的 Q 是什么呢？是两句话里面的每个 token 产生的 Q，是不是一次性就给你算出来了呀。而且注意这个算的是什么呢，是两句话每个 token 的八个头的 query，一次就算出来了。」

- **【直译】** `Q = self.w_q(x)` 这一行，把 2 句 × 4096 token × 8 头 = **65536 组 query** 一次性算完了。
- **【推导/代码】** 代码原文（【画面】01:04:25）：
  ```python
  # 1. 线性变换得到 Q, K, V
  Q = self.w_q(x)   # [batch_size, seq_len, embed_dim]
  K = self.w_k(x)
  V = self.w_v(x)
  ```
  调试器：`Q = {Tensor: (2, 4096, 320)}`、`K`、`V` 同形。`nn.Linear` 只作用在最后一维，前面 `(2, 4096)` 全部当成"批"，所以形状进去什么样出来还什么样。
- **【为什么】** 这就是"看不懂"的起点：一行 40 个字符的代码，背后是三层嵌套循环的语义。老师后面 00:43:47 一针见血：「**为什么我们看这个代码又看不懂呢？是因为他把很多事情放在一个算子里面去操作了。**」

### 19 关键提问：w_q 的输出为什么是 320 而不是 40（00:37:02 – 00:38:26）

> **谢博**：「实际上我们每个 token 产生 Q，这个 Q 的长度是多少？是 40。那么我们按照正常的逻辑来讲，应该是这样子的……我们现在看这个 self.w_q，这个 self.w_q 是个什么东西啊？是不是一层全连接层。320，输入是 320，输出也是 320。为什么输入是 320 呢？因为它的每个 token 的 embedding 是 320。然后为什么输出是 320 呢？8 × 40。」

- **【直译】** 单个头里，一个 token 的 Q 只有 40 维。但 `w_q` 的输出是 320 维——因为 320 = 8 × 40，它一次把 8 个头的 Q 全吐出来了。
- **【推导/代码】** 两个数字的出身要分清：
  - `in_features = 320` ← **由 embedding 长度决定，铁定不变**（老师原话：「输入 320 是铁定不会变的，就取决于你的那个 embedding 的长度是多少」）。
  - `out_features = 320` ← 由 `num_head × head_dim` 决定，是**巧合等于 in_features**。如果你把 head_dim 设成 64、8 个头，out 就该是 512，和 in 的 320 不相等，代码照样能跑。
- **【为什么】** 这个"巧合"是标准 Transformer 的默认约定（`d_model = h × d_k`），目的是让残差连接 `x + attn(x)` 能直接相加。但**它不是数学必需**，把它当成必需就会在读变体代码时懵。
- **【连接】** ⚠ 00:38:11 老师口误说了"4×80"，随即被学员纠正为"8×40"，他自己补了一句「这个地方不满足交换律是吧」——见纠错表 B-4。

### 20 展开版写法：8 个 Linear(320, 40)（00:38:33 – 00:40:38）

> **谢博**：「按照正常来讲这个地方应该是 40，因为我的 query 是 40 嘛。正常来讲这个地方应该是我要构建一个 W_q，它的输入是 320……你看这行代码等价是什么呢？假如我把它等价的话，应该是这样子的：Q1 = self.w_q1(x)，这是第一个头，然后点点点，到 Q8 = self.w_q8(x)。但是我前面是不是要有这样的代码：self.w_q1 = nn.Linear(320, 40)。」

- **【画面】** 谢博真的在 `__init__` 里敲了两行进去（00:40:27 / 00:42:02 单帧）：
  ```python
  self.w_q1 = nn.Linear(self.embed_dim, 40)
  self.w_q2 = nn.Linear(self.embed_dim, 40)
  ```
  又在 `forward` 里敲了（00:39:52 单帧）：
  ```python
  Q = self.w_q(x)   # [batch_size, seq_len, embed_dim]

  Q_1 = self.w_q1(x)
  Q_2 = self.w_q2(x)
  ```
  IDE 的悬浮提示确认：`Instance attribute w_q1 of MultiHeadSelfAttention → w_q1: Linear = nn.Linear(self.embed_dim, 40)`。
- **【推导/代码】** 展开版的语义是：`Q_1` 形状 `(2,4096,40)` = 全部 token 在**第 1 个头**下的 query。8 个这样的张量沿最后一维 concat，就得到 `(2,4096,320)`——正好等于 `self.w_q(x)`。
- **【为什么】** 老师之所以真的敲代码而不是口述，是因为这段"等价性"是本课全部推理的地基。他 00:40:47 收口：「那这里的 Q 就相当于把这里的 Q1、Q2……Q8 合在一起了，然后他也不需要有八个全连接了。」

### 21 枪毙错误写法：8 个头共用一个 Linear（00:41:10 – 00:41:50）

> **谢博**：「那你说我们也有同学还可能这里还会犯错误。他可能会说，这 Q1，然后这里是不是也是 Q1 呢，用同一个全连接呢？……那这样子你看你产生出来的 Q1、Q2 和 Q8 是不是一样的。为什么是一样的？因为同样的一个是同样的权重啊。」

- **【直译】** 如果 8 个头共用同一个 `nn.Linear(320,40)`，那 8 个头产生的 query 一模一样，8 个头的分数、8 个头的输出全部相同，"多头"退化成"一个头复制 8 遍"，白算 8 倍算力。
- **【推导/代码】** 这是"权重必须不同"的充分论证：多头的表达力**完全来自 8 组权重的差异**。而合并写法之所以自动满足这一点，是因为 `Linear(320,320)` 的权重矩阵是 `(320, 320)`，切成 8 段后每段 `(40, 320)` 都是独立的参数、独立初始化、独立更新。
- **【为什么】** 这是一个"负例教学"：先让你看到错误写法长什么样，再回头看正确写法你才知道它防的是什么。
- **【连接】** 这个坑在你写自定义模块时很容易踩：`nn.ModuleList([layer] * 8)` 是 8 个**同一对象的引用**（共享权重），必须写 `nn.ModuleList([make_layer() for _ in range(8)])` 才是 8 组独立权重。

### 22 核心论证：一层宽全连接 = 八层窄全连接并排（00:42:13 – 00:43:37）

> **谢博**：「现在我们突然发现写代码的时候我们发现，这八个全连接层，哦，原来可以用一个全连接层把它代替掉。可以啊，你就想嘛，你的 x 输入是什么，这个全连接层是不是 320 输入，然后按照正常来讲这个全连接层是 40 个节点，然后你有八个这样的网络。现在我把这层全连接层直接扩展到 320 个，是不是就可以了呀。然后你看这个神经元，它是不是也会计算 320 个数据输入过来进行计算呢。然后我们把这个 320 分成八个区啊，前面 40 个一个区，中间 40 个一个区，后面再接下 40 个一个区，你会发现这是不是跟你这样写等效的呀。权重是不是也不一样啊。」

- **【直译】** 全连接层的每个输出神经元，都独立地吃全部 320 个输入、用自己的一套权重。所以把 8 个"40 神经元的层"并排放，和造一个"320 神经元的层"再把输出切成 8 段，是**完全等价**的——包括每段权重互不相同这一点。
- **【推导/代码】** 严格的矩阵语言：
  ```
  展开版： Q_h = x @ W_h^T + b_h,   W_h ∈ R^(40×320),  h = 1..8
  合并版： Q   = x @ W^T   + b  ,   W   ∈ R^(320×320)
  只要令 W = [W_1; W_2; ...; W_8]（沿行拼接）、b = [b_1; ...; b_8]，
  则  Q[..., 40h : 40(h+1)]  ≡  Q_h
  ```
  因为矩阵乘的每一行输出只依赖 W 的对应行，行与行之间零耦合——这就是等价性的全部数学内容。
- **【为什么】** 为什么工程上要合并？① 一次大 GEMM 比 8 次小 GEMM 快得多（kernel launch 开销、GPU 利用率）；② 参数管理简单，一个 Linear 而不是 8 个；③ 后面 reshape 就能免费拆开，零成本。
- **【连接】** 同款技巧你在 YOLO 里见过：检测头把 cls、box、obj 三路输出**合并成一个 Conv2d** 输出 `(5+nc)*na` 个通道，再按通道切片解码。合并算、切片用，是同一个模式。

### 23 单 token 视角复述：T1 进去，出来 320 个数按 40 切八份（00:44:00 – 00:45:10）

> **谢博**：「就是八个全连接合并成一个全连接这件事情能不能理解……你看我这个输入一个 x，320，我一个 token，我就不说 4096 个 token 一起进来，我就一个 token 进来，比如说 T1。T1 本来它应该是用八个全连接层产生 Q1、Q2 到 Q8。我现在就建这样一个全连接，320 个节点，然后把 T1 这个 token 输进去，然后产生了 320 个数据出来，然后我直接把它切分，按 40 一个切分，那这前面这个每一个 40 是不是对应我原来这个 Q1、Q2、Q3 呢？有什么区别呢？」

- **【直译】** 把 batch 和 seq 全部去掉，只看一个 token：输入 320 个数 → 输出 320 个数 → 按 40 一刀切成 8 段 → 第 h 段就是第 h 个头的 query。
- **【为什么】** 老师故意"降维打击"：先把 4096 和 2 这两个干扰维度拿掉，让你在最小例子上确认等价性，再把维度加回去。这是他全课的标准手法——你自己复习时也该这么干。
- **【连接】** 老师紧接着说：「**为什么要是八个呢？就是因为是八个头。你看它是不是同一个 token 产生了八个不同的 query，八个不同的 query 就准备把这个问问题这件事情做八遍。**」这句是本 Part 的一句话总结。

### 24 方法论：看代码要"会拆"（00:43:40 – 00:43:56 + 00:45:14 – 00:45:20）

> **谢博**：「都说了注意力机制的原理已经讲完了。那为什么我们看这个代码又看不懂呢？是因为他把很多事情放在一个算子里面去操作了，打眼一看我们就看了一点迷糊了。现在我又把这个代码拆开给你看……所以你看你看代码的时候就要会拆，听懂这意思吧。」

- **【直译】** 原理和代码之间隔着一层"折叠"。读代码的能力 = 把折叠还原成展开的能力。
- **【推导/代码】** 拆的具体操作有三招，本课全用上了：① **写等价的展开代码**（w_q1…w_q8）；② **降维到最小例子**（只看一个 token）；③ **切片提问**（这个数在哪个下标）。第三招是 Part 5 的主角。
- **【连接】** 这套方法迁移到你的 BEV 工作上：mmdet3d 里 `BEVFusion` 的 `view_transform` 一行 `bev_feat = bev_pool(x, geom)`，背后是"每个相机每个像素每个深度 bin 落到哪个 BEV 格子"的三重循环。你要能反向把它展开，才敢改。

**【小结】** ① `w_q = Linear(320, 320)` 的输出 320 = 8 头 × 40 维，它一次算完了所有头的 query。② 一层 320 神经元的全连接，严格等价于 8 层 40 神经元全连接的并排，因为矩阵乘的行与行之间零耦合；合并写法自动保证 8 个头权重不同，共用一个 Linear 则会让 8 个头完全相同。③ 读代码的核心能力是"拆"：写展开版、降维到单 token、切片定位。

## Part 5 · 第二刀：reshape 与 permute —— 把 Q/K/V 摆到能算的位置（00:45:03 – 01:19:22）

**【本段在讲什么】** Q 算出来了，形状是 `(2,4096,320)`，但这个形状**不能直接拿去算注意力**——直接算的话，320 个数会被当成一个头的一整条 query，8 个头就糊成一个了。这一 Part 谢博用三个连续的形变（reshape → permute → reshape）把 Q/K/V 摆成 `(16, 4096, 40)`，中间穿插了六七轮"切片提问"，逼学员在每个形状下都能定位到"第几句话·第几个头·第几个 token"。这是全课最耗时也最有训练价值的一段。

### 25 Q 的 (2,4096,320) 到底装了什么（00:45:53 – 00:46:28）

> **谢博**：「好我们现在 Q 是不是计算出来了呀，(2, 4096, 320)。注意这个 Q 是什么呢？是里面的每一个 token 产生的八个 query。所以这里面有多少个 token 呢？两句话，是不是 2 乘 4096 啊。每个 token 是不是产生 8 个 Q 啊，每个 Q 长度是不是 40 啊。所以这个地方是不是 320 呢。」

- **【直译】** `Q[i, t, :]` 这 320 个数 = 第 i 句话第 t 个 token 的**八个头的 query 首尾相接**。
- **【推导/代码】** 数一遍总量：2 × 4096 × 8 = 65536 条 query，每条 40 维，总共 2,621,440 个浮点数 = 2×4096×320。✔ 对得上。
- **【连接】** 这种"总数守恒校验"是你验证任何 reshape 是否写对的第一道防线：reshape 从不改变元素总数，只改变解读方式。

### 26 第一次切片提问：T0 的 Q1 在哪（00:48:55 – 00:52:10）

> **谢博**：「现在我问你，这个 T0 这个 token，它是不是产生了八个 query，Q1 到 Q8。现在我问你，它的 Q1 在哪里啊，你把它切出来，在这个 tensor 里面哪个位置？……首先这个 T0 在哪去找呀，是不是在第 0 句话里面呢，它第几个 token 啊，是不是第 0 个呀。然后它的 Q1 是不是第 1 个 Q，它的位置在哪里呢，0 到 40。这一串数据就是 T0 这个 token 产生的 Q1，这个还到 39 啊。」

- **【推导/代码】** 答案：`Q[0, 0, 0:40]`。三个下标各有出处——
  | 下标 | 值 | 含义 |
  |---|---|---|
  | dim0 | `0` | 第 0 句话 |
  | dim1 | `0` | 该句的第 0 个 token（T0） |
  | dim2 | `0:40` | 第 1 个头（Python 左闭右开，实际取 0…39） |
  推广公式：**第 i 句、第 t 个 token、第 h 个头（0-based）的 query = `Q[i, t, 40*h : 40*(h+1)]`**。
- **【为什么】** 老师花了 3 分钟在这一个下标上，还被学员追问 "39 是什么"。这不是啰嗦——**这个公式就是"多头折叠"的定义式**，写不出它，后面的 reshape/permute 全是玄学。
- **【连接】** 这个训练直接对应你以后读 BEVFormer：`sampling_offsets` 的形状是 `(bs, num_query, num_heads, num_levels, num_points, 2)`，六个维度，你要能瞬间说出任意一个数的身份。今天练的就是那块肌肉。

### 27 复述一遍：切 dim2 全部 = T0 的八个头的 Q（00:51:47 – 00:52:11）

> **谢博**：「所以这个 320，这个 320 里面啊，我们假如说这个维度我们全切出来，全切是不是 320 个数据啊。320 个数据包含的是什么呢？是 T0 这个 token 八个头的 Q，八个头的 query。」

- **【直译】** `Q[0, 0, :]` 这 320 个数，是同一个 token 的 8 条 query 拼起来的，不是一条 320 维的 query。
- **【为什么】** 这句是下一张卡的引子——正因为它是"8 条拼起来的"，才绝对不能整条拿去做点积。
- **【连接】** 【画面】01:31:58 的手写便签把这层意思固定在屏幕上：「X: 第一句话 [T0, T1, T2, ..., T4095] / 第二句话 [T0', T1', T2', ..., T4095'] / 每个 Q 的长度是 40 / T0 → Q1, Q2, ..., Q8」——这张便签在后面一小时里一直挂着，是老师给自己立的坐标系。

### 28 为什么必须 permute：不 permute 就变成"1 个头 + 320 维 Q"（00:52:12 – 00:55:28）

> **谢博**：「为什么后面它要 permute，它要转维度？你不能用 320 这个数一起去计算。320 这个数一起计算，那你注意力不就错了吗？……我们注意力首先，这个注意力分数是这样算的：首先是一个矩阵相乘，前面是 Q，后面是 K。这里是 Token0 的 Q，Q 有几个数呢？40。它要跟谁相乘呢？这一行是不是乘这一列啊……如果你后面不 permute，不把最后一维搞成 40，那这个位置是多少呢？这不就 320 了吗。那这不就不符合注意力计算法则了吗，你就变成一个头了呀，就不是八个头了呀。那你说不 permute 我能不能算？从这个算子对操作数的要求来说，可以，完全可以算。但是味道就变了，就不是这个意思了。它就变成一个头，然后 Q 的长度是 320 了。」

- **【直译】** 矩阵乘只认最后一维的长度是否匹配。如果最后一维是 320，PyTorch 会照算不误，但语义上你算的是"1 个头、每条 query 320 维"的单头注意力，8 个头被糊成了 1 个。
- **【推导/代码】** 对比两种算法的分数：
  - 正确（8 头）：`score_h[t,s] = Σ_{d=0..39} Q_h[t,d]·K_h[s,d]`，得到 8 个不同的分数矩阵。
  - 错误（不拆头）：`score[t,s] = Σ_{d=0..319} Q[t,d]·K[s,d] = Σ_h score_h[t,s]`，8 个头的分数被**直接加总**成一个，softmax 只做一次，8 个独立的注意力分布塌缩成 1 个。
- **【为什么】** 这是本课最值得记的一句判断：**"能跑通"和"算对"是两回事**。张量算子只检查形状，不检查语义；语义是你自己维护的。
- **【连接】** 你在 BEV 里改 shape 最容易出的就是这类"静默错误"：permute 顺序写错、reshape 的 view 语义与内存布局不符，网络照跑、loss 照降，但精度就是上不去，且没有任何报错。老师 00:54:44 那句「**你必须要理解这个数据结构，你要能猜出来它是什么意思**」就是防这个的。

### 29 头与头之间全程独立，只在最后合并（00:55:31 – 00:56:07）

> **谢博**：「而且它每个头的计算它是分开的，头跟头是没关系的，它不影响。直到什么时候才有影响呢？叫每个头观察到的结果最后再把它合在一起。每个头在计算 QKV、以及计算权重分数、以及去提取特征的时候，它们都是没有关系的，都是独立自己做自己的。然后每个头会观察到一个特征出来，最后才把这些特征合在一起，作为最终观察结果。」

- **【直译】** 8 个头是 8 条完全平行的流水线，从 Q/K/V 到分数到输出特征全程不通信，唯一的汇合点是最后的 concat + `w_o`。

- **【连接】** 也解释了 `w_o` 为什么不可省：如果没有 `w_o`，8 个头的 40 维特征只是简单并排，彼此从未交互过；`w_o` 是唯一让 8 个头的信息互相混合的地方。

### 30 第一次 reshape：切成 (2,4096,8,40)，一切豁然开朗（01:04:11 – 01:07:03）

> **谢博**：「这个时候 QKV 准备好了，你看哈，这个实际上没做什么东西，它是在干嘛？是不是在变形呢。你看它是不是把这个 320 切出来啊，切成八个头。它切完之后我们是不是更好理解了……现在变成 8、40 了，这样是不是更清楚了。比如说我想问，这个 T_i' 这个 token 它的第五个头的 K，那你是不是很快就能切出来？这是在第几句话呀，在第 1 句话，所以我们这里是 1，然后它第几个 token 呢……」

- **【推导/代码】** 【画面】01:04:25 单帧原文：
  ```python
  # 2. 拆分为多头并转置维度 [batch_size, num_head, seq_len, head_dim]
  Q = Q.reshape(batch_size, seq_len, self.num_head, self.head_dim)  # view相当于numpy中的reshape
  K = K.reshape(batch_size, seq_len, self.num_head, self.head_dim)
  V = V.reshape(batch_size, seq_len, self.num_head, self.head_dim)
  ```
  `(2, 4096, 320) → (2, 4096, 8, 40)`。元素总数不变，只是把最后那 320 个数**显式地**分成 8 组 40。
- **【直译】** 上一张卡里那个需要心算的 `Q[0,0,40*h:40*(h+1)]`，现在变成了直接可读的 `Q[0, 0, h, :]`。切片提问的答案从"算术题"变成了"填空题"。
- **【为什么】** 这是整个 MHA 实现里最优雅的一步：**拆头不需要任何计算，只需要重新解读内存**。因为 `w_q` 的输出天然就是按头分段排列的（Part 4 的等价性论证），reshape 一刀就把段切出来了，零成本。
- **【连接】** 老师此处的答案：`K[1, i, 4, :]` = 第 1 句话、第 i 个 token、第 5 个头（0-based 索引 4）、完整的 40 维 K。

### 31 切片的两种写法与"苦练切片"（01:07:22 – 01:08:20）

> **谢博**：「我这样切也可以，知道这意思吗……你看这样是不是一样的呢？如果你不会这样切，那你就加冒号。看为什么上课上得这么慢，知道吗，哈哈。我是不是跟你们说过，要苦练切片。这个殊途同归，切对了吧，不重要，你会一种方式切就行了。」

- **【推导/代码】** 同一个元素的等价写法：`K[1, i, 4, :]` ≡ `K[1][i][4]` ≡ `K[1, i, 4]`（尾部维度可省略）。省略尾部维度和显式写 `:` 完全等价，取自己看得顺的那种。
- **【为什么】** "苦练切片"不是玄学要求。整个深度学习工程里，你 80% 的 debug 时间是在回答"这个数是谁"。切片写不利索，调试器打开也白搭。
- **【连接】** 建议你把这个练成条件反射：给定 `(B, N, C, H, W)` 的多相机特征，第 3 个相机第 5 个通道的特征图 = `feat[:, 2, 4]`；给定 `(B, num_query, 8, 40)`，第 7 个 query 第 3 个头 = `q[:, 6, 2, :]`。

### 32 permute(0,2,1,3)：用代数理解，不要用空间想象（01:08:24 – 01:09:15）

> **谢博**：「这些就是要交换维度啊。你看他怎么交换呢？这个看得懂吗？看不懂也没关系，你两个对比一下就知道了。你看 0 是不是不变，3 是不是也不变，原来的 1 用现在的 2，原来的 2 用现在的 1，所以它一交换是不是这两个维交换呢。**都说了交换维度不要用你的空间感去想象，用代数去理解。**」

- **【推导/代码】** 【画面】01:04:25 原文：
  ```python
  # 重新对维度交换permute（两种写法都可以）
  Q = torch.permute(Q, dims=(0, 2, 1, 3))
  K = K.permute(0, 2, 1, 3)
  V = V.permute(0, 2, 1, 3)
  ```
  `(2, 4096, 8, 40) → (2, 8, 4096, 40)`。读法：新张量的第 k 个维度 = 旧张量的第 `dims[k]` 个维度。这里 `dims=(0,2,1,3)` 表示"新0=旧0、新1=旧2、新2=旧1、新3=旧3"，即把 seq 和 head 对调。
- **【为什么】** 这句方法论值千金。四维以上的张量根本没有空间直觉可言（人只能想象三维），硬要"想象"必然翻车。正确姿势是**纯粹按下标映射规则做代数替换**：`new[a,b,c,d] = old[a,c,b,d]`。
- **【连接】** 老师顺带演示了 `torch.permute(Q, dims=...)` 和 `K.permute(...)` 两种写法，并吐槽这样混写不好：「当然这个代码这样写好不好？不好。你会哪种就用哪种。」——这是 AI 生成代码的典型特征（同一段里混用多种等价 API）。

### 33 第二次 reshape：合并成 (16, 4096, 40)，16 是什么（01:10:15 – 01:14:30）

> **谢博**：「这个地方是不是又在 reshape 啊，reshape 干嘛呢？现在是不是四维啊，这是不是要合并成三维呢。三维就是为了做矩阵相乘嘛……首先看前面的这个 16，16 代表什么呢？代表两句话八个头。前面 0 到 7 知道吗，是第一句话的八个头，然后 8 到 15 是第二句话的八个头。现在我要第几个头，第二句话的第 5 个……好，第二句话的第一个头是不是 8，现在第 5 个头，那是不是 8 加 5 减 1 啊。所以这是多少，12。」

- **【推导/代码】** 【画面】01:04:25 原文：
  ```python
  # 再次reshape成[16,4096,40]
  Q = Q.reshape(batch_size*self.num_head, seq_len, self.head_dim)
  K = K.reshape(batch_size*self.num_head, seq_len, self.head_dim)
  V = V.reshape(batch_size*self.num_head, seq_len, self.head_dim)
  ```
  `(2, 8, 4096, 40) → (16, 4096, 40)`。调试器（01:25:38 单帧）确认：`Q = {Tensor: (16, 4096, 40)}`、`K = (16,4096,40)`、`V = (16,4096,40)`。
- **【直译】** 新的第 0 维 16 = **句子编号 × 8 + 头编号**。0–7 是第 0 句的 8 个头，8–15 是第 1 句的 8 个头。
- **【推导/代码】** 定位公式：**index = i × num_head + h**（i 为句子号，h 为头号，均 0-based）。老师要的"第二句话第 5 个头"若按 1-based 数头则 h=4，index = 1×8+4 = **12**；他口算成"8+5−1=12"，结果一致但混用了两种基数——他自己也承认「如果你是多一个 1 少一个 1，我就原谅你」（见纠错表 B-2）。
- **【为什么】** 为什么合并成三维？因为 `torch.matmul` 对三维输入的处理最直观：第 0 维当 batch，后两维做标准矩阵乘。四维也能算（PyTorch 支持任意批维），但老师要用三维把"批量矩阵乘"讲透。
- **【连接】** ⚠ 这一步有个隐藏前提：**必须先 permute 再 reshape，不能反过来**。因为 reshape 是按内存顺序重新解读的，只有当 head 已经紧邻在 batch 后面时，合并出来的 16 才是"句 × 头"的语义。这就是 reshape 前必须有 permute 的深层原因，也是实战里最常见的静默 bug 源。

### 34 为什么要把 head 挪到最前面（01:15:35 – 01:16:00）

> **谢博**：「看这个，知道在哪里了吗？因为你到时候我们是不是一个头一个头地去算，一句话一句话地去算。知道他为什么把它放在前面吗？前面就是批处理。为什么要挪到这个维度呢？为什么不能放在后面两个维度呢？」

- **【直译】** head 必须挪到最前面，是因为它要扮演"批"的角色——批维必须在前，参与矩阵乘的两个维必须在后。
- **【推导/代码】** `torch.matmul` 的规则写死了：**最后两维做矩阵乘，前面所有维度按广播规则当批**。所以想让 8 个头各算各的，就只能把 head 塞到前面去；想让 `(4096, 40) @ (40, 4096)` 成立，就只能把 seq 和 head_dim 留在后两位。整个 permute 的动机就这一句话。
- **【连接】** 记住这条"**批在前、算在后**"的铁律，你以后设计任何自定义算子的 shape 都不会摆错。BEV 里 `(B*N_cam, C, H, W)` 送进 2D backbone、`(B*num_head, num_query, head_dim)` 送进 attention，全是同一条铁律。

**【小结】** ① 三步形变的完整链条：`(2,4096,320)` --reshape--> `(2,4096,8,40)` --permute(0,2,1,3)--> `(2,8,4096,40)` --reshape--> `(16,4096,40)`。② 不 permute 也能算，但语义会塌成"1 个头、query 长 320"——张量算子只查形状不查语义，这是最危险的一类 bug。③ 交换维度必须用代数（`new[a,b,c,d]=old[a,c,b,d]`）而非空间想象；合并出来的 16 = 句号 × 8 + 头号，且必须先 permute 后 reshape。

## Part 6 · 第三刀：批量矩阵乘算分数 + 缩放 + softmax（01:19:22 – 01:37:01）

**【本段在讲什么】** Q、K 都摆好了，现在算注意力分数。谢博在这里解决了第二个大障碍：`torch.matmul` 吃的是三维张量，"三维的矩阵怎么相乘"？他的答案是**先把前面那个 16 蒙住**——蒙住之后就是最朴素的 `(4096,40) @ (40,4096)`，谁都会；然后再把 16 放回来，理解成"16 个矩阵乘并排跑"。之后是缩放和 softmax，他还当场用 Evaluate 窗口验证了权重和等于 1。

### 35 K_transpose 与 matmul 那一行（01:17:07 – 01:18:09）

> **谢博**：「这里面 matmul 是吧，matmul 是矩阵相乘。矩阵相乘逻辑上来说，它是不是二维的？但是他现在这里进行矩阵相乘的这个 tensor、这个操作数是几维的呀？三维的是不是。那怎么来理解这个逻辑呢？前面两个看成一维是错的……我们现在看这里，K.permute(0,2,1) 是不是把这个 tensor 转置了呀，转置成什么呢，40 乘以 4096 啊。」

- **【推导/代码】** 【画面】01:36:00 / 01:31:58 单帧原文：
  ```python
  # 3. 计算 Q 和 K 的点积，得到注意力分数
  K_transpose = K.permute(0,2,1)
  scores = torch.matmul(Q, K_transpose)   # Q@K矩阵相乘. [16, 4096, 40] @ [16, 40, 4096]
  ```
  调试器：`K_transpose = {Tensor: (16, 40, 4096)}`、`scores = {Tensor: (16, 4096, 4096)}`。
- **【直译】** 第二次 permute 只转置后两维（`(0,2,1)` 保持批维不动），把 K 从 `(16,4096,40)` 变成 `(16,40,4096)`，好让它能被 Q 乘。
- **【为什么】** 注意这里 permute 的 dims 只有三个数了，因为张量已经是三维。同一个 API 在不同维数下写法不同，这也是老师说"要对比着看"的原因。

### 36 蒙住 16：三维矩阵乘的正确打开方式（01:19:49 – 01:21:52）

> **谢博**：「我现在告诉你，假如看到没有，假如没有前面这个 16，是不是很爽歪歪，是不是很好理解，一点都不抽象。那你看好怎么乘呢？这里面 Q，Q 是不是在前面这个矩阵，前面这个矩阵是不是 4096……这个地方我们说 4096 乘以 40，圈后面这个是什么呢，后面是不是 K，40 乘以 4096。首先我们问，这个结果出来是多少？结果是 4096 乘以 4096。」

- **【推导/代码】** 蒙住批维后就是最朴素的中学矩阵乘：
  ```
  (4096 行 × 40 列) @ (40 行 × 4096 列) → (4096 × 4096)
  ```
  行 = 观察者 token，列 = 被观察者 token。`scores[t, s]` = 第 t 个 token 的 query 与第 s 个 token 的 key 的点积 = "t 有多关注 s"。
- **【为什么】** 老师反复强调"要分得清楚哪个是行哪个是列"，因为一旦搞反，你就把"t 关注 s"读成"s 关注 t"，整个注意力的方向性就颠倒了。他原话：「**要不然你就对不上原理。**」
- **【连接】** 这个 4096×4096 的方阵就是注意力可视化图（attention map）的原始数据。你以后看 DETR/BEVFormer 论文里那些热力图，画的就是这个矩阵的某一行。

### 37 把 16 放回来：16 个独立矩阵乘，互不交叉（01:22:20 – 01:26:30）

> **谢博**：「这里是 16，这个是不是我们理解 batch，后面是不是个矩阵呢……我可以把 Q 看作是 16 个矩阵：Q0、Q1……Q15。K_transpose 它是不是也是 16 啊，我可以把它看作 16 个矩阵：K0、K1……K15。那这个矩阵它的形状是多少？Q0 这个矩阵是不是 4096 乘 40 啊……这两个矩阵相乘，做完之后会得到一个 score，实际上就等于 score 的 0 了。那 Q1 这个矩阵和 K1 这个矩阵是不是又可以相乘了……会出现 Q0 圈 K1 吗？不会啊。这个是在 batch 这一维啊，它是中间不会交叉的。」

- **【画面】** 01:25:38 单帧上老师用红笔在屏幕上直接写了这套记号：`Q: Q[0] 4096×40, Q[1], ..., Q[15]` / `K_tran: K[0], K[1], ..., K[15]` / `→ scores[0]`。
- **【推导/代码】** 批量矩阵乘的严格定义：
  ```
  scores[b] = Q[b] @ K_transpose[b]     b = 0, 1, ..., 15
  (4096,4096) = (4096,40) @ (40,4096)
  最终堆叠成 (16, 4096, 4096)
  ```
  **绝不会出现 `Q[0] @ K[1]`**——这正是 Part 3 那条"batch 维不交叉"公理的兑现：第 0 句的第 0 个头，绝不会去和第 1 句或别的头算分数。
- **【为什么】** 到这里，"多头折叠"的全部魔术就解释完了：8 个头 × 2 句话之所以能一次算完，是因为它们被伪装成了 16 个 batch，而 batch 天然就是"并排跑、不交叉"。
- **【连接】** `weights.shape = [16, 4096, 4096]` 这个 print 注释现在完全可读了：16 组（2 句 × 8 头）× 每组 4096 个观察者 × 每个观察者对 4096 个被观察者的分数。

### 38 定位注意力分数：scores[1, 2, :] 是谁（01:28:12 – 01:31:33）

> **谢博**：「我现在问，第二个头，T2 这个 token 去观察所有的人，然后他是不是就会形成一个注意力分数、注意力权重。他的这个注意力分数在这个 score 里面是不是放在这个位置呢？……首先我们要问，这个注意力分数它是不是个向量，它有几个数？4096。他观察几个就有几个分数……这是第一句话的第二个头，0 就是第一句话的第一个头，1 就是第一句话的第二个头。所以第一维这个 16 这个维度应该是几呢？应该是 1。」

- **【推导/代码】** 【画面】01:31:58 单帧的 Evaluate 窗口里，谢博输入的表达式是 **`scores[1,2,:]`**。逐位解读：
  | 下标 | 值 | 含义 |
  |---|---|---|
  | dim0 | `1` | 16 维里的第 1 号 = 第 0 句话（1÷8=0）的第 1 个头（1%8=1） |
  | dim1 | `2` | 观察者是 T2 这个 token |
  | dim2 | `:` | 对全部 4096 个被观察者的分数 |
- **【直译】** 结果是一条 4096 个数的向量：T2 在第 2 个头视角下，对全句每个 token（包括它自己）打的分。
- **【为什么】** 老师追问"它有几个数"这一步很关键：**被观察者有几个，分数就有几个**。这条直觉能让你以后看到任何 attention 的最后一维就知道那是"被看的人数"（key 的个数），交叉注意力里它就不等于 query 数了。
- **【连接】** 这也解释了为什么 causal mask（GPT 的因果掩码）是加在这最后一维上的：把 s > t 的位置置为 −inf，就等于"不许往后看"。

### 39 缩放：除以 √head_dim，而不是 √embed_dim（01:32:31 – 01:36:12）

> **谢博**：「而且这个分数我们还要对它缩放一下，是不是。缩放是不是除以根号这个维度……这个缩放不重要，我说放大一点说放小一点没关系。如果考试你就按 embedding 来说，就这么简单……这本来就是缩放的东西嘛，我们说它的缩放作用就跟那个 normalize 一样，为了把这个数放到 0 到 1 之间。为什么要这样做？目的就是防止有些不好的激活函数之后会导致它梯度消失。」

- **【推导/代码】** 【画面】01:36:00 单帧代码原文：
  ```python
  # 4. 缩放：除以 sqrt(head_dim)
  scores = scores / np.sqrt(self.head_dim)
  ```
  **代码里除的是 `√head_dim = √40 ≈ 6.32`，不是 `√embed_dim = √320 ≈ 17.9`。** 老师口头说"考试按 embedding 长度"是不严谨的（见纠错表 B-1），他自己随后也嘀咕了一句「这不是 query 的长度吗」——query 的长度正是 head_dim=40，所以代码是对的。
- **【为什么】** 标准 Transformer 的缩放因子是 `1/√d_k`，`d_k` 就是**单个头的维度**。数学理由：若 q、k 各分量独立、均值 0 方差 1，则 `q·k` 的方差是 `d_k`，标准差 `√d_k`；除掉它把分数拉回单位方差。不缩放的后果是分数量级随维度线性增大，softmax 进入饱和区，**梯度趋近于 0**——老师说的"梯度消失"就是这个（Whisper 把"梯度"听成了"T2"）。
- **【连接】** 注意老师那句"放到 0 到 1 之间"是口语化的近似说法，缩放并不保证落在 [0,1]，它只是把量级压回可控范围；真正映射到 [0,1] 的是下一步的 softmax。

### 40 softmax + 当场验证权重和为 1（01:32:49 – 01:34:04）

> **谢博**：「我们直接看 softmax 好吧。这个变量已经换了，score 是不是做完 softmax 之后变成 weights 了。只不过这个时候这 4096 个数是不是已经经过 softmax 了。已经经过 softmax 意味着他们加起来就要等于多少？……不就 4096 个数相加吗，多少？1。不是我是对的，是这个代码写对的——他如果不是 1，那就他代码写错了。」

- **【画面】** 01:36:00 单帧的 Evaluate 窗口是本课最硬的一条实证：
  ```
  Expression:  weights[1,2,:].sum()
  Result:      result = {Tensor: ()} tensor(1.0000, grad_fn=<SumBackward0>)
  ```
  代码原文：
  ```python
  # 5. Softmax. 得到注意力权重
  weights = F.softmax(scores, dim=-1)   # 每列归一化，加起来为1
  ```
- **【推导/代码】** `dim=-1` 表示沿最后一维做 softmax，即**每一行（每个观察者）**的 4096 个分数归一化成一个概率分布。⚠ 代码注释写的"每列归一化"是错的，应该是"每行"——这是 AI 生成注释的典型错误（见纠错表 B-3）。
- **【为什么】** `grad_fn=<SumBackward0>` 这个细节值得注意：它说明这是带梯度的计算图节点，不是脱离图的数值。你在调试器里 Evaluate 不会破坏计算图，可以放心用。
- **【连接】** "加起来等于 1"是你验证任何 attention 实现是否写对的**一秒钟自检法**：随便切一行求和，不是 1.0000 就说明 softmax 的 dim 写错了。这个技巧比读一百遍代码管用。

**【小结】** ① 三维 matmul 的正确理解方式是"蒙住前面的批维"：`(16,4096,40) @ (16,40,4096)` = 16 个独立的 `(4096,40)@(40,4096)`，绝不交叉。② `scores[1,2,:]` 的语义是"第 0 句·第 1 个头·T2 对全部 4096 个 token 的分数"，最后一维的长度由被观察者数量决定。③ 缩放除的是 `√head_dim`（代码实测 `np.sqrt(self.head_dim)`），softmax 沿 `dim=-1`，可用 `weights[i,t,:].sum()==1.0` 一秒自检。

## Part 7 · 第四刀：加权求和、拼回 320、输出投影（01:37:01 – 01:55:00）

**【本段在讲什么】** 最后一段，权重乘 V 提特征。谢博在这里挖到了全课最深的一层：**大多数人以为"一行乘一列就得到一条完整的 V"，其实一行乘一列只得到那条 V 的一个分量**。他用 `0.1×x₀ + 0.2×x₀' + ...` 手推了整整 8 分钟。最后三行代码（reshape/permute/reshape + `w_o`）反而一带而过，因为形变逻辑和 Part 5 完全对称。

### 41 weights @ V：形状怎么对上（01:37:18 – 01:39:44）

> **谢博**：「有了这个权重之后，我是不是就可以提取特征了呀。所以你看我怎么提取特征，是不是 weights 和 V 去提取。能不能矩阵相乘呢？我把这个 16 把它蒙掉，可以不看他，因为他就是相当于批处理呀……好 4096，4096 乘以 40，可不可以啊？可以啊，完全可以……这个是不是行列都是 4096，然后这个是行是 4096，列是 40。」

- **【推导/代码】** 【画面】01:54:35 单帧代码原文：
  ```python
  # 6. 用注意力权重对 V 加权求和
  head_outputs = torch.matmul(weights, V)   # weights@V矩阵相乘
  ```
  形状推导（蒙住 16 后）：`(4096, 4096) @ (4096, 40) → (4096, 40)`。加上批维就是 `(16,4096,4096) @ (16,4096,40) → (16,4096,40)`。调试器确认 `head_outputs = {Tensor: (16, 4096, 40)}`。
- **【直译】** 权重矩阵的每一行是一个概率分布（4096 个数、和为 1），V 的每一行是一个 token 的 40 维内容。相乘的结果是：每个观察者拿到一条 40 维的、按注意力加权混合出来的新特征。
- **【为什么】** 注意这次**不需要转置 V**。老师问了一句"还用转置吗"，答案是不用——因为 weights 的最后一维（4096，被观察者）正好对上 V 的第一维（4096，token），天然匹配。

### 42 提取到的特征为什么是 40 维（01:44:00 – 01:44:32）

> **谢博**：「首先我们知道他提取到总的特征，他是不是一个向量，有多少个数我问你？40 啊。为什么是 40 呢？因为大家每个 V 都是长度是 40 啊。是还是不是？因为我们大家长度都是 40 啊。」

- **【直译】** 加权平均不改变维度。你混合的是一堆 40 维向量，混出来的当然还是 40 维。
- **【推导/代码】** 定位公式和 scores 完全一样：`head_outputs[1, 2, :]` = 第 0 句·第 1 个头·T2 提取到的 40 维特征。老师原话：「是不是还是跟刚刚那个 score 一样的切。」
- **【连接】** 这就是"每个头贡献 40 维"的由来，8 个头 concat 回 320 维，正好和输入等长——闭环了。

### 43 ★最深的一层★ 一行乘一列只得到一个分量（01:45:06 – 01:45:43）

> **谢博**：「算了我直接说吧。我就告诉你，看到没有，这个 40 个数，不是这一行乘这一列就出来了。这 40 个数是这一行乘这一列、乘这一列、乘这一列、乘这一列……这一行乘这一列，只是这 40 个数里面的第一个数；这一行乘这另一列，才是这 40 个数里面的第二个数。」

- **【直译】** 矩阵乘的定义就是这样：结果的 `(t, j)` 位置 = 左矩阵第 t 行 × 右矩阵第 j 列。要凑齐 40 个数，得让同一行去乘 40 个不同的列。
- **【推导/代码】** 写成公式最清楚：
  ```
  head_outputs[t, j] = Σ_{s=0..4095}  weights[t, s] · V[s, j]
                        ↑ 固定 t 行     ↑ 遍历 4096 个 token   ↑ 固定第 j 个分量
  j 从 0 到 39 走一遍，才凑出完整的 40 维特征。
  ```
- **【为什么】** 老师专门停下来纠这个，是因为大多数人对矩阵乘的直觉停留在"行×列"，会误以为一次点积就产出一条完整的输出向量。这个误解会让你在推导任何 attention 变体时算错维度。他自己也说：「**所以不是你们理解的哈，这个矩阵相乘里面不是你们理解这一行乘以这一列一个 V 就出来了，这一行乘以这一列只是得到一个 V 的一个维度、某一个位置。**」
- **【连接】** 换个视角就通了：`head_outputs[t] = Σ_s weights[t,s] · V[s]`——**输出是 4096 条 V 向量的凸组合**（系数和为 1）。这个"凸组合"视角比"行乘列"视角更接近注意力的本意。

### 44 手推数值：0.1×V₀ + 0.2×V₁ + …（01:46:01 – 01:51:35）

> **谢博**：「这一行是不是代表比如说 T_i 去观察 T0、T1、T2 到 T4095 的一个权重分布。比如说这是 0.1，这是 0.2，然后点点点，这是 0.1，那这是不是 4096 个数啊，总共加起来是 1……那你看 T0 是不是有个 V，V0，V0 是一个什么呢，是不是长度为 40 的一个向量。比如说我叫他 x0、x1，然后到 x39 啊。这个 T1 是不是也有个 V，假如说我叫他 x0'、x1'，点点点，x39'……好，第一个数是怎么算来的？第一个数是不是 0.1 乘以 x0，加上 0.2 乘以 x0' 啊。这里有多少个数相乘相加，是不是有 4096 个呀。」

- **【画面】** 01:50:53 单帧上，屏幕左下角有老师的绿色手写：`V0: [x0, x1, ..., x39]`、`V1: [x0', x1', ..., x39']`，上方蓝色圈出权重行 `a0, a1, a2, ...`。这是全课唯一一次把抽象张量降到具体数字的推演。
- **【推导/代码】** 结果向量的第 0 个分量：
  ```
  out[0] = 0.1·x₀ + 0.2·x₀' + ... + 0.1·x₀⁽⁴⁰⁹⁵⁾     （4096 项相乘相加）
  out[1] = 0.1·x₁ + 0.2·x₁' + ... + 0.1·x₁⁽⁴⁰⁹⁵⁾
  ...
  out[39] = ...
  ```
  老师的总结：「**我对 T0 这个特征投入的注意力是 0.1，所以这个维度它只能占 0.1 分。**」——即每个被观察者按自己的注意力份额，等比例地贡献自己 40 个分量中的每一个。
- **【为什么】** 这是"提取特征"四个字的真实含义：不是复制、不是选择，而是**按注意力分布做加权平均**。注意力权重是每个 token 的"发言权比例"。
- **【连接】** 这个"权重×值再求和"的模式你早就见过：YOLO 的 CA 注意力、SE 模块的通道加权、乃至 BEV 里 LSS 的深度分布加权（`depth_prob × feature` 再 sum），全是同一个骨架。区别只在权重从哪来。

### 45 抓人比喻 + 位置编码的伏笔（01:52:06 – 01:53:57）

> **谢博**：「你看拆解出来是不是就是 OBS 观察 PPI、P4095，只不过是他把它放在一起了。放在一起你就不知道他们坐在哪里了。比如说我要抓小羊，如果这个房子里面没有其他同学，他很容易被我逮住；然后他就找其他同学混进来，混进来我是不是就不好定位他了呀……如果你不理解这个，其实你就不懂位置编码。因为位置编码做完之后，他整个大张量他的值是不一样的，但是我们又为什么说他实际上提取到的特征是一样的呢，就是你要去切他。」

- **【直译】** 折叠不改变计算内容，只改变"座位号"。你觉得难，纯粹是因为找不到人坐在哪。
- **【为什么】** 最后这句伏笔很有价值：位置编码是**加在输入嵌入上**的（`x = embedding + PE`），所以后面所有张量的数值都会变；但张量的**结构语义（谁在哪个下标）完全不变**。你要判断位置编码起没起作用，靠的还是切片定位这套本事。
- **【连接】** 这也预告了下一课的内容。你在读 BEVFormer 时会遇到同样的事：BEV query 加了可学习的位置嵌入，数值全变，但 `(bs, num_query, embed_dim)` 的结构语义一个字没动。

### 46 收尾三行：拼回 320 + 输出投影 + 交叉注意力（01:54:03 – 01:55:24）

> **谢博**：「这个其实就已经算出来了，到这里就已经结束了。后面你看这一步是干嘛，是不是又把它的形状转换过来，当然后面还有个全连接……concat 的 out 是不是 320 呢？320 是什么意思呢？因为我每个头观察到的这个特征是长度为 40 的。现在我是不是 8 个头啊，我把这 8 个头观察到的特征汇总在一起，他不是相加，他在这个维度 concat，是不是就变成 320 了吗。然后最后这里还有一个线性层，这个线性层是用来整理特征的。」

- **【推导/代码】** 【画面】01:54:35 单帧的完整收尾代码：
  ```python
  # 7. 转置并reshape 回 [batch_size, num_head, seq_len, head_dim]
  head_outputs = head_outputs.reshape(batch_size, self.num_head, seq_len, self.head_dim)
  # 重新对维度交换permute
  head_outputs = head_outputs.permute(0,2,1,3)
  # 再次reshape
  concat_output = head_outputs.reshape(batch_size, seq_len, self.num_head*self.head_dim)
  # 8. 最终的线性投影
  output = self.w_o(concat_output)
  return output, weights
  ```
  形状链：`(16,4096,40) → (2,8,4096,40) → (2,4096,8,40) → (2,4096,320) → (2,4096,320)`。调试器确认 `head_outputs = (2,4096,8,40)`、`concat_output = {Tensor: (2, 4096, 320)}`。**这三步和 Part 5 的三步严格互逆。**
- **【为什么】** 两个要点：① **是 concat 不是 add**——8 个头看到的是 8 类不同的关系，相加会把它们平均掉，拼接才保留全部信息；② `w_o` 不可省，它是 8 个头之间**唯一的信息交汇点**（Part 5 卡 29 已埋伏笔），"整理特征"就是让 8 路信息互相混合成一个统一表示。
- **【连接】** 老师最后一句把交叉注意力也带上了：「**交叉注意力也是一样地去理解，这个是自注意力。交叉注意力那就是他的观察者和被观察者不是同一个句子。**」代码上只改一处：`Q = w_q(x_query)`，而 `K = w_k(x_kv)`、`V = w_v(x_kv)`。形状推导除了 query 的 seq_len 可能不同于 key 的 seq_len，其余完全一致——这正是 BEVFormer 里 BEV query 去查相机特征的那个结构。

**【小结】** ① `weights @ V` 的本质是"4096 条 V 向量按注意力分布做凸组合"，一行乘一列只得到结果向量的**一个分量**，凑齐 40 个分量要乘 40 次。② 收尾的三步形变是 Part 5 三步的严格逆运算，最后 concat（不是 add）回 320 维，再由 `w_o` 做唯一一次跨头信息混合。③ 位置编码只改数值不改结构，所以判断它有没有生效，依然靠切片定位这套本事。

### 复习最小集（三句话背下来）

1. **拆头不用算，只用重新解读内存。** `w_q = Linear(320,320)` 的输出 320 = 8 头 × 40 维，一层宽全连接严格等价于 8 层 `Linear(320,40)` 并排（矩阵乘行与行零耦合），所以 `reshape(B, L, 8, 40)` 一刀就把 8 个头免费切出来了；共用一个 Linear 则 8 个头完全相同，白算。
2. **形变链条与它的逆。** `(2,4096,320)` →reshape→ `(2,4096,8,40)` →permute(0,2,1,3)→ `(2,8,4096,40)` →reshape→ `(16,4096,40)`；算完再原路逆回去 concat 成 `(2,4096,320)` 过 `w_o`。**16 = 句号 × 8 + 头号**，必须先 permute 后 reshape；permute 只能用代数理解（`new[a,b,c,d]=old[a,c,b,d]`），不能靠空间想象。
3. **批在前、算在后。** `torch.matmul` 只拿最后两维做矩阵乘，前面全当 batch 且绝不交叉——所以 `(16,4096,40)@(16,40,4096)` 就是 16 个独立的 `(4096,40)@(40,4096)`。分数除以 **√head_dim**、softmax 沿 **dim=-1**（自检：`weights[i,t,:].sum()==1.0000`）；`weights@V` 是 4096 条 V 的凸组合，**一行乘一列只出结果向量的一个分量**。
