## 2026-08-22

### 1. tensorboard 导入失败，训练起不来

- **现象**：`ImportError: GLIBCXX_3.4.29 not found`，训练在 hook 初始化阶段崩溃
- **原因**：系统 libstdc++ 只到 3.4.28，protobuf 的 C 扩展要 3.4.29
- **处理**：conda 激活脚本加 `PROTOCOL_BUFFERS_PYTHON_IMPLEMENTATION=python`，走纯 Python 实现绕开
- **教训**：conda 环境里有新版 libstdc++ 但不在链接路径上。改 `LD_LIBRARY_PATH` 会波及 CUDA 等所有库，风险大；改单个组件的实现方式更安全

### 2. SSH 频繁断线，VS Code 连不上

- **现象**：`Connection closed by ... port 2222`，时通时断
- **原因**：两个 systemd 用户服务跑同一份 frp 配置，互抢 proxy 名（日志刷 `proxy [ssh2] already exists`）
- **处理**：`systemctl --user disable connect.service`，只留 `frp-connect.service`
- **教训**：`pgrep -c` 会匹配到自己的命令行，数出来多 1。用方括号规避：`pgrep -f '[f]rp'`

### 3. PointPillars 配置 bug（仓库自带）

- **现象**：`The size of tensor a (16384) must match the size of tensor b (65536)`
- **原因**：配置只覆盖 `train_cfg.grid_size=[512,512,1]`，漏了 `test_cfg.grid_size`（继承成 1024）。而 `transfusion.py:166` 的位置编码网格取自 **test_cfg**
- **处理**：在 `test_cfg` 下补 `grid_size: [512, 512, 1]`
- **教训**：形状不匹配时，**先把两个数字反推成网格尺寸**（16384=128²、65536=256²），比盯着堆栈看快得多

### 4. 加大 batch 没有吞吐收益

- **现象**：每帧耗时 bs1=0.241 / bs2=0.233 / bs4=0.246 秒
- **原因**：显存只用 2GB/16GB，但 GPU 计算单元在 bs=1 时已跑满
- **处理**：所有实验固定 bs=1
- **教训**：**显存有余 ≠ 能提吞吐**。bs=4 时 data_time 从 0.005 涨到 0.209，dataloader 反成瓶颈

## 2026-08-23

### 5. spconv 随机崩溃（**未解决**）

- **现象**：`helper_launch.h:17  N > 0 assert faild ... got N= 0`。同配置同数据，有时 1 步就崩，有时跑 5350 步才崩
- **排查过程**（三次弯路，全部被数据否定）：
  - 怀疑点云文件损坏 → 扫描全部文件，0 个空文件，**否定**
  - 怀疑 sm_89 架构不匹配 → CUDA 同大版本二进制兼容，且 GitHub issue #297 报告者用 A100 也崩，**否定**
  - 在卷积入口拦 `indices.shape[0]==0` → 计数器显示**从未触发**，拦错地方
  - 打印全部入参 → indices=30107、batch_size=1、out_shape 都正常，**N=0 来自 C++ 内部**
  - 试 `CUDA_LAUNCH_BLOCKING=1` → 一次撑 5350 步，一次立刻崩，**不可靠**
- **现状**：上游已知 bug（mit-han-lab/bevfusion issue #82、#297）。影响 voxelnet / convfuser，**不影响 pointpillars / camera_only**（不用稀疏卷积）
- **教训**：**加了保护一定要能观测它有没有触发**。加计数器才发现保护形同虚设；只看「这次没崩」会得出完全错误的结论

### 6. 学习率过高导致训练发散

- **现象**：`ValueError: matrix contains invalid numeric entries`（scipy 匈牙利匹配）
- **原因**：配置 `lr=1e-4` 是为 8 卡（等效批量 8）调的，单卡等效批量 1，学习率相对高 8 倍。cyclic 策略还在往 10 倍 base 爬
- **数据**：

  | lr | loss | matched_ious |
  |---|---|---|
  | 2.31e-4 | 6.00 谷底 | 0.109 峰值 |
  | 3.76e-4 | 7.01 | 0.077 |
  | 5.16e-4 | 7.49 | 0.048 → NaN |

- **教训**：
  - **`matched_ious` 比 loss 更早报警**。loss 涨 8% 容易当成噪声，matched_ious 趋势更明确
  - **报错的组件（scipy）只是第一个不肯将就 NaN 的地方，不是病根**
  - **参数值也能导致报错，不只是代码逻辑**。特征：跑一段才崩 / 换参数就好 / 换种子结果不同

### 7. 前台跑长任务被终端连累

- **现象**：训练日志停在 03:06，进程消失，mmdet3d 日志里**没有任何报错**
- **原因**：命令是前台跑的（`... | tee`），真正的 Python 异常写在重定向文件里
- **教训**：
  - 长任务一律 `nohup ... > log 2>&1 &`
  - **mmdet3d 的 logger 只记 INFO，Python 异常不走它**。排查先看重定向的那个文件

### 8. shell 坑：grep -c 的退出码

- **现象**：脚本报 `[: 0\n0：需要整数表达式`
- **原因**：`grep -c` 匹配数为 0 时**照样输出 "0"，但退出码是 1**，写成 `$(grep -c ... || echo 0)` 会得到两行
- **处理**：`n=$(grep -c ...); [ -z "$n" ] && n=0`
- **教训**：把命令输出塞进变量再做数值比较时，先单独测边界情况

### 9. cyclic 学习率：判断安全性要看峰值不是 base

- **现象**：按 voxelnet 实测的发散临界点 2.3e-4，设 base=1.5e-5，结果 4 epoch 后 `matched_ious` 仅 0.018，**最终 mAP = 0.0000**
- **原因**：cyclic 策略 `target_ratio=(10, 1e-4)`，**峰值 = base × 10**。我把「临界点 2.3e-4」当成 base 来推，实际它对应的是峰值，导致 base 定得过低（峰值仅 1.5e-4，只有临界点的 65%）
- **处理**：跑学习率扫描实测，PointPillars 用 **base 3e-5**（峰值 3e-4）
- **教训**：
  - **调度器会放大 base，安全性判断必须看放大后的峰值**
  - **不要跨架构套用超参数**。voxelnet 的临界点不能直接用于 PointPillars
  - **「训练量不足」和「学习率不足」不可互相替代**：lr 1.5e-5 跑 4 epoch（28104 步）远不如 lr 3e-5 跑 1 epoch（7026 步）。学习率太小会把模型困在初始化附近的平坦区，加步数出不来

### 10. nuScenes 官方评测器不接受验证集子集

- **现象**：训练完第 1 个 epoch，评测阶段报
  `AssertionError: Samples in split doesn't match samples in predictions.`
- **原因**：`mmdet3d/datasets/nuscenes_dataset.py` 里
  `eval_set_map = {"v1.0-trainval": "val"}`，**评测器强制加载官方 val split 的全部 6019 帧作为真值**。
  而我们把 `--data.val.ann_file` 指向了 1529 帧的子集，两个集合对不上
- **处理**：**训练集可以切子集，验证集必须用全量**
- **教训**：
  - 缩减数据规模时要分清「训练用」和「评测用」——后者常有外部约束
  - 这也导致**原定的「训练集 vs 验证集」过拟合诊断在 nuScenes 上做不了**，
    改用「评测多个 checkpoint 的验证集 mAP 看曲线形状」替代（见下条）

### 11. 诊断方法变更：多 checkpoint 验证集曲线

- **背景**：阶段 A 拿到 val mAP 0.3153 后，需要判断瓶颈是「数据不足」还是「训练不足」
- **原方案**：同一 checkpoint 分别在训练集和验证集上评测，比较差距 → **因第 10 条不可行**
- **新方案**：评测 `epoch_5 / 10 / 15 / 20` 在**同一验证集**上的 mAP，看曲线形状

  | 曲线 | 诊断 | 下一步 |
  |---|---|---|
  | 一路上升，ep20 仍在涨 | 欠拟合，训练量不足 | 加 epoch |
  | ep15 见顶，ep20 回落 | 过拟合，数据不足 | 加数据 |
  | 见顶后持平 | 已收敛 | 当前配置到上限 |

- **教训**：**受外部工具约束时，换一个能测的代理指标，而不是硬改工具**

### 12. conda 环境未激活

- **现象**：`torchpack：未找到命令`，命令瞬间返回
- **原因**：新开的终端默认在 `base` 环境，BEVFusion 的依赖全在 `bev` 环境里
- **处理**：`conda activate bev`，然后用 `which torchpack` 确认
- **教训**：**跑任何命令前先看提示符前缀**。`(base)` 跑不了，`(bev)` 才行

### 13. 终端残留输入打断长任务

- **现象**：评测刚显示进度条 `[ ] 0/6019` 就出现 `^C` 并中断，但用户没主动按 Ctrl+C
- **原因**：前一条命令运行期间敲/粘贴的内容留在输入缓冲区，新命令启动时被一起送入终端
- **处理**：改用 `nohup ... > log 2>&1 &` 后台跑，再用 `tail -f log` 看进度。
  **`tail -f` 上按 Ctrl+C 只退出查看，不影响任务**
- **教训**：前台长任务对终端输入毫无防护。**后台运行 + 独立查看**是唯一稳妥的组合

### 14. 我自己重复踩了第 2 条的坑

- **现象**：`pgrep -cf 'test.py'` 返回 2，但 GPU 空闲、日志文件不存在
- **原因**：查询命令自身的命令行含 `test.py`，被自己匹配到
- **教训**：**这个坑 2026-08-22 就写进了本文档第 2 条，2026-08-23 我又踩了一次**。
  写进文档 ≠ 形成习惯。凡是 `pgrep`/`pkill` 一律用方括号形式

### 15. 评测耗时估算错了近一倍

- **现象**：我估计单个 checkpoint 评测约 13 分钟，实测 4.6 帧/秒 → 6019 帧需 22 分钟，加官方评测约 **25 分钟**
- **教训**：**没有实测就不要给具体数字**。三个 checkpoint 从「40 分钟」变成「75 分钟」，会影响当天的安排

### 16. 方法论错误：跳过「工具校准」直接测未知量

- **现象**：诊断多 checkpoint 曲线时，直接从 `epoch_5` 开始测，结果 mAP = 0.0000，
  与训练内评测给出的 `epoch_20` = 0.3153 反差巨大，无法判断是模型真差还是工具有问题
- **原因**：两个数字来自**不同代码路径**——
  0.3153 来自 `tools/train.py` 内部的 `DistEvalHook`，
  0.0000 来自独立脚本 `tools/test.py`。
  我**默认两者等价**，没有验证就开始测未知量
- **正确顺序**：手里既然有已知答案（epoch_20 = 0.3153），
  **应该先用 `tools/test.py` 测 epoch_20 校准工具**，
  确认两条路径一致后，再去测 ep5 / ep10 / ep15
- **代价**：若 `tools/test.py` 确有问题，先测的那次 ep5（25 分钟）完全作废，
  且其 0.0000 的结果会误导判断
- **教训**：
  - **有已知量在手时，先用它校准测量工具，再测未知量。** 这不是浪费时间，是前提
  - 这与「买新体重秤先称一袋标称 1 公斤的米」是同一件事
  - 本条与第 4、5、9 条属于**同一个失败模式**：存在一个可低成本验证的假设，
    却选择直接假设它成立。今日已重复四次（batch 提速、sm_89 架构、
    跨模型套用学习率、50% 数据够收敛），需要作为固定检查项

### 17. 「幽灵 ^C」真凶：VS Code 的自动激活环境功能

- **现象**：前台任务三次被 `^C` + `conda activate bev` 打断，用户没有敲过这些。
  没开新窗口也会自动出现 `conda activate bev` 被执行
- **原因**：终端是 **VS Code Remote-SSH 的集成终端**。Python 扩展的
  `python.terminal.activateEnvironment`（默认开启）会在它认为需要的时机
  **主动向终端注入激活命令；若终端正忙，先发 Ctrl+C 打断当前程序**。
  佐证：进程环境变量里有 `VSCODE_PYTHON_AUTOACTIVATE_GUARD`
- **处理**：VS Code 设置（Remote 标签页）里关掉
  `Python: Terminal Activate Environment`，即 `"python.terminal.activateEnvironment": false`。
  代价是新终端要手动 `conda activate bev`
- **教训**：
  - **IDE 集成终端不是"干净"的终端**——扩展可以往里注入输入、甚至打断进程
  - 之前误判为「终端残留输入」（第 13 条），实际是主动注入。
    **后台跑（nohup &）依然是正解**，因为它对两种情况都免疫
  - 排查「没人操作却发生了什么」时，把 IDE/扩展列入嫌疑名单

### 18. test.py 不认 torchpack 的路径覆盖参数

- **现象**：`test.py: error: unrecognized arguments: --dataset_root data/nuscenes-mini/`。
  同样的参数在 train.py 上一直好用
- **原因**：两个脚本的参数解析方式不同——
  train.py 用 `parse_known_args()`（未定义参数交给 torchpack 做路径覆盖），
  **test.py 用 `parse_args()`（严格模式，未定义参数直接报错）**。
  test.py 覆盖配置要用 mmdet 风格的 `--cfg-options key=value`
- **处理**：
  ```
  --cfg-options data.test.dataset_root=... data.test.ann_file=...
  ```
  注意要**同时覆盖 ann_file**：`--cfg-options` 作用于配置**插值求值之后**，
  那时 `${dataset_root + ...}` 已经固化成全量路径，只改 dataset_root 传导不过去
- **教训**：
  - **同一仓库里不同入口脚本的参数体系可以不一样**（train.py 是 torchpack 风格，
    test.py 是 mmdet 风格），别假设一致
  - torchpack 覆盖发生在插值**之前**（改变量，引用跟着变）；
    cfg-options 发生在插值**之后**（改哪个键就只有哪个键变）

### 19. gt_boxes 的 yaw 不是几何朝向（差一个 -y-90° 变换）

- **现象**：可视化脚本画的 GT 框与点云条纹对不上（看似差 90 度）；
  残影率自检失败——静止目标残影率 22%（应≈0）
- **定位**：最快目标速度方向 -164°，存储 yaw=73°；验证 -(73°)-90° = -163° ≈ 速度方向
  → **pkl 存的 yaw = -几何朝向 - 90°**（mmdet3d 旧版坐标约定，converter 写入时转换）
- **实证**：修正 yaw 后 GT 框内关键帧点数 441 → **558（+27%）**，四种解释中决定性胜出
- **教训**：
  - **模型管线内部自洽的量，拿出来单独用时要先验证语义**（yaw/速度/坐标系）
  - **对照组自检抓 bug**：静止目标残影率"应≈0"这个自检项失败，才暴露了 yaw 问题——
    没有它，错误的残影率就当真数据用了
  - 速度向量与朝向的一致性（直行车两者应共线）是坐标约定的免费验证器

### 20. nuScenes 激光坐标系：x=右、y=前（不是 KITTI 的 x=前）

- **现象**：相机-点云对照面板"上=车头"标注与实际相差 90°，用户发现相机里的东西在点云图里找不到
- **实证方法**：把 CAM_FRONT（车头相机）的光轴经 `sensor2lidar_rotation` 变换到激光系
  → 方位角 90.6° = **+y 轴才是车前方**；左向量 ≈ (-1,0) → +x = 车右方
- **两个后果**：
  - 主图直接画 (x,y) 时**碰巧**就是"上=前方"（与相机同向），但没人验证过、也没标注
  - panel 脚本按"x=前"的假设做了 90° 旋转，反而把方向转错了
- **教训**：
  - **坐标系约定必须实证，不能靠"常见约定"**（KITTI x=前 ≠ nuScenes y=前）
  - 实证方法可复用：**用已知朝向的传感器（车头相机光轴）反推未知坐标系的方向**
  - 与第 19 条（yaw 约定）同源：mmdet3d 的 -yaw-90° 变换正是为了适配这个旋转了的激光系

### 21. "相机看得见、激光打不到"的实例（不是 bug，是物理）

- **现象**：帧 1098 相机里自车道正前方清晰可见一辆车，点云图里既无点团也无 GT 框
- **真相**：该车在前方 58.2m（GT 存在），**num_lidar_pts = 0**（32线远距+施工区遮挡），
  且超出 54m 的绘图/point_cloud_range 范围，框未绘制
- **含义**：
  - 纯激光模型对这类目标**从输入层面就检不出**；`use_valid_flag` 会把 0 点 GT 从监督中剔除
  - 这是简历项目"叠帧稠密化造深度真值、检出距离 131m"要解决的问题的活体标本（专题 Q10）
  - 面试可说："亲眼见过 58m 外相机清晰、激光零点的帧"

## 2026-08-28

### 22. 发散阈值随输入配置变化：单帧组用叠帧组的 lr 直接炸

- **现象**：T1-A（sweeps=0 单帧）沿用 T1-B 验证过的 lr（base 3e-5，cyclic 峰值 3e-4），
  在 ep5、lr 爬到 **2.02e-4** 时 NaN 崩溃（`matrix contains invalid numeric entries`）。
  同配置下 T1-B（10 帧输入）曾稳定跑完 20 轮
- **证据链**：T1-A 的 grad_norm 早期即 125~255（梯度裁剪 max_norm=35 持续满负荷），
  T1-B 同期仅 6~10；T1-A 前 4 轮 iou 0.011→0.016，T1-B ep1 末已 0.118
- **机制**：单帧点数仅 1/9 → 激活柱子少 → 每步梯度集中且方差大 → 可承受 lr 更低。
  实测单帧发散阈值 ≈ 2e-4（10 帧组 > 3e-4 未触及）
- **处理**：为单帧组单独扫 lr（1e-5/1.5e-5/2e-5，`tools/lr_sweep_t1a.sh`），
  胜者重训；报告中注明该组 lr 与其他组不同及原因
- **教训**：
  - **教训 9 的推广：超参不仅跨模型不可套用，同模型换输入配置也不可套用**
  - 消融的"控制变量"遇到可行性冲突时，如实记录偏离，胜过硬凑统一超参
  - grad_norm 持续顶着裁剪上限 = 训练在悬崖边的早期信号（比 loss 灵敏）

### 23. 长训练崩溃后 GPU 空转 14 小时（第二次）

- **现象**：T1-A 于 16:00 崩溃，次日 06:30 才发现
- **土办法**：启动长训练后、睡前 10 秒检查：
  `pgrep -cf '[t]rain.py' && tail -1 <日志> | cut -c1-80`
- **待办**：崩溃自动通知机制（后续搞）

### 24. 无种子的 lr 扫描把"学习率效果"和"运气"混在一起

- **现象**：T1-A 扫描中 1.5e-5 组末期 iou 0.0164，比两边的 1e-5(0.223)、2e-5(0.236) 低十几倍。
- **原因**：扫描脚本未固定随机 seed，各组初始化与数据顺序不同。该组头 50 步内
  抽中坏初始化（首条 iou 0.0000 vs 兄弟组 0.0045），此后一直在废墟上缓慢恢复。
  学习率影响是单调的，中间值单独坏即可反证非 lr 所致。
- **处理**：结论只取两端健康组，胜者按"分差是否小于噪声 + 峰值离发散阈值的余量"综合选。
- **教训**：①对比实验要么固定 seed，要么接受"组间分差 < 噪声幅度时不可比"；
  ②脚本的"✅ 稳定"判定只查崩溃(Traceback/NaN)不查学习质量，
  "活着但残废"（loss 停在 7、iou 千分位）它看不出来——判读必须人眼看 iou 绝对值。

### 25. grep 数字正则会静默跳过 nan，验尸差点漏掉关键证据

- **现象**：用 `grep -oP 'grad_norm: \K[0-9.]+'` 提取梯度序列做 1.5e-5 验尸，
  首条显示 2568——实际日志第一条是 `grad_norm: nan`，被正则无声跳过。
- **原因**：`[0-9.]+` 匹配不了字母，nan/inf 直接不出现在结果里，且无任何报错。
- **处理**：重查用 `grep -c 'grad_norm: nan'` 专项计数，发现三组开局均有 nan、
  1.5e-5 另有第二次（ep1 步2350）。
- **教训**：检查数值序列必须先专项查 nan/inf 再提取数字；"没看到异常值"
  可能只是"正则看不见异常值"。

### 26. 行首锚定 ^ 在混有进度条输出的日志里会漏行

- **现象**：`grep -E '^mAP:' | tail -3` 想取 ep20 评测的三行清爽汇总，实际漏掉了
  ep20 的 mAP 行，混进上一次评测的 NDS 行。
- **原因**：评测器的清爽输出和进度条共享终端流，行首可能粘着 \r 进度条残留或空格，
  `^` 锚定不再命中。
- **处理**：改抓巨型汇总行里的 `object/map:` 字段；或去掉锚定用 `grep 'mAP:'` 再人工分辨。
- **教训**：对含进度条的日志做行首锚定前，先 `grep 'mAP' 日志 | cat -A | head` 看一眼
  真实行首长什么样。
